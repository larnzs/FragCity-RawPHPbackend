# FragCity — Initial Security Review


**دامنهٔ ممیزی:** بازبینی ایستای فایل‌های مرتبط با authentication، heartbeat، bulk sync و DatabaseSyncService در شاخهٔ `main` مخازن `FragCity-WebAPIClient` و `FragCity-RawPHPbackend`. این گزارش خط مبنای امنیتی است؛ تست نفوذ یا ممیزی پویا/کامل کل برنامه نیست.

> **وضعیت جاری — ۱۷ اکتبر ۲۰۲۶:** فایل‌های `settings/loader.php` و `settings/settings.example.json` در ریپو وجود دارند، اما حضور Loader به معنی مهاجرت کامل تمام صفحات قدیمی نیست. یافته‌های credential hard-coded، صدور/ثبت token، ستون‌های SQL برگرفته از payload و خطای heartbeat همچنان باز هستند؛ بدون تغییر/test مشخص، رفع آن‌ها یا Rotation credentialها را انجام‌شده فرض نکن.

### ۱۶.۱. موارد با اولویت فوری

#### A. اطلاعات دیتابیس hard-code شده در سورس

در چند فایل PHP، اطلاعات اتصال دیتابیس مستقیماً داخل کد قرار گرفته‌اند. این مقادیر در تاریخچه Git نیز می‌توانند باقی بمانند؛ حذفشان از نسخه جاری به‌تنهایی به معنی باطل‌شدن credential نیست.

**اقدام پیشنهادی:** پس از برنامه‌ریزی برای جلوگیری از قطعی، credentialهای جدید با حداقل دسترسی ایجاد شوند، انتقال به تنظیمات خارج از Git انجام شود و credentialهای قبلی به‌صورت هماهنگ چرخانده/باطل شوند. مقدار هیچ secretی نباید در README، commit message یا لاگ قرار گیرد.

#### B. SQL identifier از JSON در `sync_bulk.php`

اسم جدول به map مجاز محدود شده، اما نام ستون‌ها از کلیدهای هر ردیف وارد رشته SQL می‌شوند. parameterized query برای مقادیر ردیف مفید است، ولی شناسه SQL را خودکار امن نمی‌کند.

**اقدام پیشنهادی:** برای هر جدول، فهرست مجاز ستون‌ها را از یک schema تعریف‌شده/اعتبارسنجی‌شده تعیین کنیم؛ کلیدهای ناشناخته رد شوند. نام جدول/ستون نباید مستقیماً از payload آزاد در SQL قرار بگیرد.

#### C. جریان صدور و بررسی توکن هماهنگ نیست

`agent_login.php` توکن تصادفی را به کلاینت برمی‌گرداند، اما در همان مسیر رکوردی برای آن داخل `agent_tokens` نمی‌سازد؛ endpointهایی مانند `heartbeat.php` و `sync_bulk.php` توکن را از این جدول بررسی می‌کنند. علاوه بر آن، C# پس از Login یک `ApiClient` دیگر داخل `AgentService` می‌سازد و انتقال صریح توکن تازه‌گرفته‌شده به نمونه دوم دیده نمی‌شود.

**اقدام پیشنهادی:** جریان ثبت/صدور/انقضا/ابطال توکن یکپارچه شود؛ هر نود credential مستقل و scope محدود خود را داشته باشد و همهٔ endpointهای حساس از یک روش احراز هویت مشترک استفاده کنند.

#### D. هدر Authorization در bulk sync ارسال نمی‌شود

`ApiClient.SendBulkSyncDataAsync` برای `sync_bulk.php` درخواست POST می‌فرستد، اما برخلاف متدهای heartbeat/task، `AddAuthHeader` را فراخوانی نمی‌کند. بنابراین با اجرای endpoint فعلی انتظار می‌رود درخواست فاقد توکن با 401 رد شود.

#### E. خطای نحوی در heartbeat

در نسخهٔ فعلی `agent/heartbeat.php` عبارت `$existingNode = $checkStmt$checkStmt->fetch(PDO::FETCH_ASSOC);` همچنان وجود دارد. این عبارت از نظر PHP syntax نامعتبر است. قبل از استفاده باید `php -l agent/heartbeat.php` اجرا و مشکل اصلاح شود؛ تا آن زمان endpoint را سالم یا آمادهٔ Production فرض نکن. این بازبینی مستندات، کد اجرایی را اصلاح نکرده است.

#### F. مسیر سینک مستقیم دیتابیس خطر از دست‌رفتن داده دارد

`DatabaseSyncService.SyncDataOneWayAsync` قبل از درج داده‌ها، جدول مقصد را با `DELETE FROM` خالی می‌کند و سپس ردیف‌ها را جداگانه درج می‌کند؛ این چرخه transaction اتمیک برای پاک‌کردن و درج دوباره ندارد. اگر داده منبع خالی باشد، متد پیش از پاک‌کردن مقصد برمی‌گردد، بنابراین داده‌های حذف‌شده از منبع در مقصد باقی می‌مانند. همچنین تشخیص دیتابیس/جدول با تطبیق تقریبی suffix و همگام‌سازی گسترده، ریسک انتخاب مقصد اشتباه را ایجاد می‌کند.

**اقدام پیشنهادی:** این سینک عمومی تا طراحی دوباره نباید در محیط تولید فعال شود. منطق جدید باید allowlist دقیق schema/table و جهت synchronization داشته باشد و عملیات اتمیک، idempotent و بازیابی‌پذیر ارائه کند؛ حذف داده نباید از طریق پاک‌کردن سراسری جدول به‌صورت ضمنی انجام شود.

### ۱۶.۲. موارد امنیتی و قابلیت اطمینان دیگر

- اتصال‌های MySQL مستقیم در C# با `SslMode=none` ساخته می‌شوند. هرگز این تنظیم را برای انتقال credential یا داده روی شبکه غیرقابل‌اعتماد استفاده نکنیم؛ البته مسیر مستقیم 3306 فعلاً انتخاب نشده است.
- در `AgentService` برای نبودن `AgentSecret` مقدار پیش‌فرض hard-coded وجود دارد. رفتار درست fail-closed است: اگر secret تنظیم نشده، قابلیت وابسته شروع نشود؛ credential مشترک پیش‌فرض نباید وجود داشته باشد.
- فایل `agentsettings.json` حاوی تنظیمات و احتمالاً passwordهاست و به صورت JSON عادی ذخیره می‌شود. در Linux باید دسترسی فایل به حساب سرویس محدود شود و secretها تا حد ممکن از تنظیمات قابل‌commit جدا باشند.
- `sync_bulk.php` کلیدهای ردیف و حجم/تعداد ردیف‌ها را به‌اندازه کافی به schema و سقف payload محدود نمی‌کند و متن exception را در پاسخ 500 برمی‌گرداند. پاسخ عمومی باید پیام بی‌خطر داشته باشد و جزئیات فقط در لاگ داخلی محافظت‌شده ثبت شوند.
- heartbeat بخشی از هدرهای proxy برای IP را از درخواست می‌خواند؛ IPهای forwarded نباید بدون پیکربندی اعتماد به proxy معتبر تلقی شوند.
- `fetch_tasks.php` در نسخه دیده‌شده، به جای دریافت واقعی وظایف، آرایه خالی برمی‌گرداند. این قابلیت هنوز کامل نیست.
- خواندن کل جدول در حافظه و درج ردیف‌به‌ردیف در سینک فعلی برای جدول‌های بزرگ می‌تواند RAM/زمان را افزایش دهد؛ batching محدود و cursor لازم است.
- مسیرهای خطا و catchهای خالی در چند متد مشاهده شده‌اند؛ خطاهای authentication، شبکه و synchronization باید تفکیک، ثبت و برای retry با backoff مدیریت شوند.

### ۱۶.۳. ترتیب پیشنهادی اصلاحات

1. غیرفعال نگه‌داشتن سینک مستقیم عمومی و جلوگیری از هر اجرا روی دیتابیس تولیدی تا بازطراحی.
2. مدیریت امن و چرخاندن هماهنگ credentialهایی که در سورس قرار گرفته‌اند.
3. اصلاح PHP syntax و طراحی یک authentication flow یکنواخت با token مستقل برای هر نود، scope محدود، expiry و revocation.
4. تکمیل endpointهای sync و اعتبارسنجی دقیق جدول، ستون، نوع داده، اندازهٔ payload، node identity و مجوز هر endpoint.
5. تعریف جهت و معناشناسی sync برای هر پلاگین: push/pull، upsert، حذف رکورد، هم‌زمانی، retry و بازیابی.
6. ساخت Worker مخصوص Linux و اجرای آن با systemd و حساب غیر root؛ پس از آن تست‌های unit/integration و تست fault/retry روی دیتابیس آزمایشی.
7. اجرای بازبینی امنیتی دوباره پس از اصلاح و تنها سپس استفاده محدود در تولید.

**نتیجه ممیزی اولیه:** بله، این سیستم قابل اصلاح است و نیازی به بازنویسی کامل C# از صفر ندارد؛ اما نسخه موجود را نباید بدون اصلاح authentication، مدیریت secret و منطق مخرب/ناامن sync روی دیتابیس واقعی فعال کرد.

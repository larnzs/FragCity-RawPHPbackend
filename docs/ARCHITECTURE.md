# FragCity — Architecture

> وضعیت: معماری پیشنهادی برای PoC، نه طراحی نهایی Production.

## 1. اصول معماری

1. **Buy before build:** قابلیت‌های عمومی مدیریت سرور و فروش را تا حد امکان از پروژه‌های بالغ بگیریم.
2. **مرز مسئولیت:** سایت/فروش، پنل بازی و نودها مسئولیت‌های جدا داشته باشند.
3. **حداقل کد اختصاصی:** فقط قواعد ویژهٔ FragCity مثل منطق بستهٔ مدت‌دار، قراردادهای API و همگام‌سازی داده‌های پلاگین را توسعه دهیم.
4. **چندنودی از روز اول:** اضافه‌کردن نود با نصب تکرارپذیر و تنظیمات مختص نود انجام شود.
5. **امنیت و بازیابی:** جداسازی مشتری، نگهداری secret، log، backup و rollback جزو طراحی اولیه باشد.
6. **مهاجرت مرحله‌ای:** سایت و اطلاعات جاری تا قبولی PoC دست‌نخورده بمانند.

## 2. معماری کاندید

```text
                        مشتری
                          |
                 HTTPS / وب‌سایت FragCity
                          |
               فروش / سفارش / کیف پول
                  Paymenter (PoC)
                          |
           API امن و اتصال provisioning
                          |
                Pterodactyl Panel
                          |
                    API مدیریتی
                          |
                Wings + Docker
                          |
            CS2 instances روی Nodeهای Linux
                          |
               بازیکنان از پورت بازی
```

این نمودار مسیر A را نشان می‌دهد. GameAP مسیر B برای مقایسه است، نه چیزی که هم‌زمان با Pterodactyl در Production اجرا شود.

## 3. مسئولیت اجزا

| جزء | مسئولیت اصلی | آنچه نباید انجام دهد |
|---|---|---|
| سایت عمومی FragCity | برند، صفحات معرفی و اطلاعات عمومی | اجرای مستقیم process روی سیستم‌عامل |
| Billing/Store | حساب مشتری، محصول، سفارش، شارژ/خرید و صورتحساب | مدیریت مستقیم Docker و processهای بازی |
| Pterodactyl Panel یا GameAP | API مدیریتی، تخصیص منابع، چرخه عمر سرور | مالکیت منطق مالی نهایی خارج از قرارداد فروش |
| Wings/Daemon | اجرا و کنترل instance روی نود | تصمیم‌گیری مستقل درباره بدهی مشتری |
| MariaDB سایت | داده‌های وب/فروش بر اساس منبع حقیقت انتخاب‌شده | دسترسی عمومی به دیتابیس برای تمام نودها |
| FragCity API/Extension | شکاف‌های واقعی، وضعیت سفارش/انقضا و اتصال سامانه‌ها | تبدیل‌شدن به کپی کور تمام دیتابیس‌ها |
| نود Linux | اجرای سرورهای CS2 و سرویس نود | نگهداری secret مشترک با مجوز بیش از نیاز |
| ابزار پایش | مشاهده‌پذیری و هشدار | جایگزین Backup یا تست بازیابی‌شدن نیست |

## 4. مدل فروش: بستهٔ مدت‌دار

مدل مالی تأییدشده **پیش‌پرداخت مدت ثابت** است:
- مشتری کیف پول را شارژ می‌کند.
- قیمت کامل یکی از بسته‌های ۱/۳/۷/۱۵/۳۰ روزه هنگام خرید از کیف پول کسر می‌شود.
- پس از تأیید موفق خرید، `expires_at` تنظیم می‌شود.
- تایمر حتی اگر CS2 خاموش، متوقف یا Crash باشد ادامه دارد.
- در انقضا، عملیات suspend/stop طبق سیاست اجرا می‌شود؛ حذف داده‌ها سیاست مستقل دارد.

Paymenter از انواع محصول یک‌باره و دوره‌ای پشتیبانی می‌کند، اما اینکه تمام رفتار کیف پول موجود و expiry دقیق FragCity را بدون extension پوشش دهد باید در PoC تأیید شود. منبع بررسی محصول: https://paymenter.org/docs/guides/products/

## 5. داده‌ها و API

- دیتابیس سایت روی هاست اشتراکی cPanel می‌ماند تا زمانی که دلیل مستند برای تغییر آن داشته باشیم.
- اتصال Remote MariaDB از نود به TCP/3306 در هاست فعلی قابل استفاده نیست.
- نودها برای APIهای مجاز از HTTPS درخواست می‌فرستند؛ endpoint PHP روی خود هاست به MariaDB مجاز است.
- منبع حقیقت هر موجودیت باید مشخص باشد: مشتری، سفارش، سرور، اعتبار، انقضا، وضعیت نود و داده‌های plugin.
- از replication عمومی تمام دیتابیس‌ها یا جداول هم‌نام اجتناب شود.
- API پلاگین‌ها allowlist، محدودیت اندازه، توکن نود مستقل، مجوزهای مشخص، idempotency و سیاست retry داشته باشد.

## 6. ماژولار بودن نودها

پروفایل هر نود باید شامل این موارد باشد:
- `node_id` و `node_name` یکتا.
- آدرس مدیریتی و آدرس قابل‌دسترسی بازی، بدون hard-code در کد سایت.
- allocation/range پورت.
- ظرفیت RAM/CPU/Disk و محدودیت‌ها.
- نسخه‌های نصب‌شده و وضعیت سلامتی.
- secretها خارج از Git و قابل Rotation.

ثبت و نصب نود جدید باید از یک runbook پیروی کند؛ تغییر کد فروشگاه برای افزودن Node نباید لازم باشد.

## 7. استقرار و هاست فعلی

- سایت و MariaDB کنونی: shared cPanel.
- سرور کنترل و نود بازی: محیطی که اجرای سرویس ماندگار، Docker و تنظیم فایروال را پشتیبانی کند.
- Debian VM فعلی: آزمایشگاهی و غیرتولیدی؛ مشخصات واقعی در [Debian PoC Log](DEBIAN-POC.md) ثبت شده است.
- میزبان Windows با ۱۶ GB RAM همچنان میزبان فعلی و منبع تست است. ظرفیت سرورهای هم‌زمان باید مرحله‌ای سنجیده شود.
- ترافیک بازی معمولاً UDP و مستقل از HTTPS سایت است؛ پورت‌های لازم باید جداگانه تعریف شوند.

## 8. Pterodactyl File Manager و برنامهٔ C# فعلی

Pterodactyl خودش در رابط وب مشتری File Manager دارد و با مجوزهای سطح فایل می‌تواند مشاهده و ویرایش فایل‌های سرور را در اختیار صاحب سرور یا Subuserهای مجاز قرار دهد؛ مجوزهای فایل از دسترسی Console و Start/Stop/Restart جدا هستند. بنابراین در PoC، ویرایش فایل‌های `cfg/` و تنظیمات افزونه‌ها را ابتدا با File Manager داخلی تست می‌کنیم، نه اینکه همان قابلیت را بی‌دلیل در C# بازنویسی کنیم. مرجع: [Pterodactyl permissions](https://github.com/pterodactyl/panel/blob/1.0-develop/app/Models/Permission.php).

ریپوی `FragCity-WebAPIClient` حاوی Agent/Client فعلی است اما به‌عنوان سامانهٔ نهایی مدیریت همهٔ Instanceها فرض نمی‌شود؛ بخشی از کد به Windows/کنسول/مسیرهای Windows وابسته است. Pterodactyl پنل مشتری مستقل دارد؛ اتصال از سایت FragCity، لینک‌دهی یا SSO به یکپارچه‌سازی نیاز دارد و خودکار داخل پنل C# فعلی ظاهر نمی‌شود. ابزار/برنامهٔ C# فعلی حذف‌شده فرض نمی‌شود: ابتدا قابلیت‌های تکراری و شکاف‌های باقی‌مانده مشخص می‌شوند. Pterodactyl/Wings باید مالک اصلی چرخهٔ عمر Server record باشد؛ دو ابزار نباید هم‌زمان و بدون قرارداد مشخص همان Instance را Start/Stop یا بازنویسی کنند. هنگام Provisioning اولیه، baseline کامل KUS به فضای خصوصی هر Instance کپی می‌شود. پیش از هر Start بعدی، updater فقط پلاگین‌ها و Runtimeهای مدیریت‌شده را در همان فضای خصوصی به‌روزرسانی می‌کند؛ `cfg/`، فایل‌های `.txt` تنظیماتی/GameMode و کل `addons/counterstrikesharp/configs/` را تغییر نمی‌دهد. این مسیرها در هر Start باید حفظ شوند و هیچ payloadی به Base Game کپی یا merge نمی‌شود. آزمون باید ثابت کند File Manager به لایهٔ خصوصی Instance دسترسی دارد، ولی Base مشترک و Instanceهای دیگر از دسترس نوشتن مشتری خارج‌اند. اگر شکاف واقعی باقی ماند، Worker/ماژول محدود اضافه می‌شود.

## 9. معماری تولیدی هنوز نهایی نیست

موارد باز: جای نهایی Panel/Billing، SSO، مدل Wallet در Paymenter، رفتار تمدید/انقضا، سیاست نگهداری دادهٔ منقضی‌شده، درگاه پرداخت، API sync پلاگین و سیاست Backup. این موارد در [Decisions](DECISIONS.md) و [Roadmap](ROADMAP.md) پیگیری می‌شوند.

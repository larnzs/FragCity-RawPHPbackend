# FragCity — Debian/VMware PoC Log

> این سند جزئیات تاریخی پارت ۲، فرمان‌های بررسی‌شده و وضعیت واقعی VM را برای ادامهٔ آزمایش حفظ می‌کند. این محیط Production نیست.

## پارت ۲ — آماده‌سازی Debian و VMware و آزمایش نخستین سرور CS2

> **وضعیت:** برنامه اجرایی آماده است؛ تا وقتی نصب و آزمایش روی سیستم واقعی انجام نشده، هیچ‌کدام از مراحل این بخش «انجام‌شده» محسوب نمی‌شوند. پس از تست، نتیجه واقعی و تنظیمات نهایی در همین سند ثبت خواهد شد.

## ۱. هدف این پارت

در این مرحله قرار است روی کامپیوتر فعلی FragCity:

1. یک ماشین مجازی سبک Debian داخل VMware ساخته شود.
2. شبکه VM طوری تنظیم شود که لینوکس آدرس محلی مستقل داشته باشد.
3. ابزارهای پایه نصب و صحت سیستم‌عامل، شبکه، رم و فضای دیسک بررسی شوند.
4. نسخه Linux موجود سرور KUS به‌صورت محلی روی VM نصب شود.
5. ابتدا نصب و انتقال فایل‌ها بدون راه‌اندازی خودکار سرور انجام شود؛ سپس تنظیمات لازم بررسی و یک سرور CS2 به‌صورت آزمایشی اجرا شود.
6. RAM، CPU، پایداری و اتصال شبکه ثبت شوند تا مبنای تصمیم‌های ظرفیت‌سنجی باشند.

**در این پارت Pterodactyl نصب نمی‌شود.** ابتدا باید مطمئن شویم Debian و سرور CS2 با افزونه‌ها و تنظیمات موجود درست کار می‌کنند. اتصال این نصب آزمایشی به Pterodactyl در مرحله جداگانه بررسی می‌شود؛ ساختار اجرای مستقیم KUS و اجرای مدیریت‌شده داخل Docker یکسان فرض نمی‌شوند.

## ۲. نسخه Debian انتخاب‌شده برای آزمایش

نسخه منتخب برای نصب آزمایشی، **Debian 13.7 (Trixie)، معماری amd64** است. طبق صفحه رسمی Debian، نسخه 13.7 در ۱۲ سپتامبر ۲۰۲۶ منتشر شده و نسخه پایدار جاری در زمان تدوین این پارت است. در روز نصب، صفحه رسمی را دوباره بررسی می‌کنیم؛ اگر نسخه پایدار 13.x جدیدتری منتشر شده باشد، آخرین ISO پایدار را ترجیح می‌دهیم.

- [صفحه رسمی دانلود Debian](https://www.debian.org/distrib/)
- [Debian netinst — نصب شبکه‌ای](https://www.debian.org/distrib/netinst)
- [فهرست انتشارهای Debian](https://www.debian.org/releases/index.en.html)

### فایل ISO

فایل **64-bit PC netinst ISO (amd64)** را دانلود کن. با توجه به اینکه VM در زمان نصب اینترنت خواهد داشت، netinst انتخاب مناسبی برای نصب بدون محیط گرافیکی است. به ISO نسخه Live نیازی نداریم.

## ۳. تنظیمات اولیه ماشین مجازی

این مقادیر برای **مرحله نصب و آزمایش یک سرور CS2** پیشنهاد شده‌اند؛ تنظیمات نهایی ظرفیت چند سرور بعد از اندازه‌گیری تعیین می‌شوند.

| سیستم‌عامل مهمان | Debian 13، 64-bit | در صورت نبودن نسخه دقیق، نزدیک‌ترین گزینه Debian 64-bit |

| فایل‌های VM | روی SSD | عملکرد و زمان بارگذاری بهتر از دیسک کندتر |

### احتیاط درباره منابع

سیستم میزبان ۱۶ گیگابایت رم دارد؛ بنابراین هنگام روشن بودن VM بخشی از حافظه همچنان برای Windows و برنامه‌های ضروری میزبان لازم است. فعلاً ۶ گیگابایت به VM اختصاص داده می‌شود و تا قبل از سنجش مصرف واقعی، افزایش رم یا تعداد سرورها را قطعی نمی‌دانیم. قابلیت رزرو تمام حافظه VM در VMware فعال نشود.

پیش از ساخت دیسک، فضای واقعی خالی میزبان بررسی شود. Thin Provision به این معنی نیست که فایل‌های CS2 و به‌روزرسانی‌ها فضای فیزیکی مصرف نمی‌کنند.

## ۴. مراحل نصب Debian

در نصب‌کننده Debian از این مقادیر استفاده شود:

این پارتیشن‌بندی فقط روی دیسک مجازی انجام می‌شود. هنگام نصب، نام دیسک و خلاصه تغییرات را کنترل کن تا هیچ دیسک فیزیکی میزبان انتخاب نشود. چون مدیر پروژه فعلاً با لینوکس تازه آشنا می‌شود، محیط گرافیکی نصب‌شده حذف نخواهد شد؛ در صورت ساخت نودهای تولیدی بعدی، می‌توان نصب بدون محیط گرافیکی را جداگانه بررسی کرد.

## ۵. به‌روزرسانی اولیه و ابزارهای پایه

پس از اولین بوت و ورود با کاربر مدیریتی:

~~~bash
sudo apt update
sudo apt full-upgrade -y
sudo apt install -y git curl ca-certificates nano htop tmux jq rsync unzip tar xz-utils dnsutils netcat-openbsd openssh-server
sudo systemctl enable --now ssh
sudo reboot
~~~

پس از راه‌اندازی مجدد، بررسی اولیه انجام شود:

~~~bash
cat /etc/os-release
uname -m
ip -br address
ip route
free -h
df -h /
nproc
systemctl status ssh --no-pager
~~~

انتظار می‌رود نسخه سیستم Debian 13.x و معماری x86_64 باشد؛ رابط شبکه باید آدرس معتبر محلی و مسیر پیش‌فرض داشته باشد. مقدار واقعی RAM، فضای آزاد و تعداد CPU قابل مشاهده نیز ثبت شود.

## ۶. شبکه VMware و مسیریابی

**Bridged** حالت اولیه شبکه است تا VM یک آدرس IP محلی مستقل داشته باشد. پس از نصب:

- آدرس IP ماشین مجازی با دستور **ip -br address** مشخص شود.
- بررسی شود که دستور **ip route** مسیر پیش‌فرض معتبری نشان می‌دهد.
- اتصال اینترنت از داخل Debian آزمایش شود.
- ترجیحاً برای MAC ماشین مجازی در روتر DHCP reservation تعریف شود تا آدرس داخلی نود مرتب عوض نشود.
- Port Forwarding سرور آزمایشی باید به IP خود VM اشاره کند، نه به IP محلی Windows میزبان.
- پورت‌های مدیریتی SSH و پنل‌های مدیریتی را بدون نیاز و بررسی امنیتی به اینترنت عمومی باز نکنیم.
- اگر Windows و VM قرار است هم‌زمان سرورهایی با یک پورت مشابه اجرا کنند، مقصد و قواعد هدایت پورت باید جداگانه بررسی شوند.

پورت‌های نهایی و قواعد فایروال هنوز در این مرحله تثبیت نشده‌اند و پس از مشاهده IP واقعی VM تعیین می‌شوند.

## ۷. Clone کردن Repository لینوکس — وضعیت فعلی

در Debian، Git از ابتدا نصب نبود. کاربر مراحل نصب Git و دریافت مخزن را انجام داده است.

### فرمان‌های اجراشده / ثبت‌شده

نصب Git و گواهی‌های CA:

~~~bash
sudo apt update
sudo apt install -y git ca-certificates
git --version
~~~

Clone کردن شاخهٔ موردنظر در Home کاربر، داخل پوشهٔ پروژه‌ها:

~~~bash
mkdir -p ~/projects
cd ~/projects
git clone --branch integration/kus-monorepo --single-branch https://github.com/larnzs/cs2-kus-addons.git
~~~

مسیر محلی مورد انتظار با حساب فعلی Debian:

~~~text
/home/fragcityadmin/projects/cs2-kus-addons
~~~

برای بررسی محلی بودن Clone، شاخه و آخرین commit:

~~~bash
cd ~/projects/cs2-kus-addons
pwd
git status --short --branch
git log -1 --oneline
~~~

**وضعیت:** نصب Git و Clone مخزن طبق گزارش کاربر انجام شده‌اند. خروجی نهایی `git status` و `git log` در گفتگو ثبت نشده؛ در شروع نشست بعد باید اجرا شوند تا شاخه، commit و وضعیت working tree عیناً ثبت شود. مسیر بالا از دستور Clone به‌دست می‌آید؛ اگر مسیر Home یا نام کاربر متفاوت بود، مسیر واقعی `pwd` معیار است.

Repository: [larnzs/cs2-kus-addons — integration/kus-monorepo](https://github.com/larnzs/cs2-kus-addons/tree/integration/kus-monorepo)

## ۸. برنامهٔ امن نصب بومی Linux و بررسی سلامت

### تصمیم فعلی: نصب تازه، بدون جابه‌جایی فایل‌های بازی Windows

در این مرحله فایل‌های بازی یا پلاگین‌ها از Windows به Linux کپی یا جابه‌جا نمی‌شوند. نصب بومی CS2 و payload پلاگین‌ها از خود Clone ریپو و از مسیر Linux انجام می‌شود. فایل‌های Windows روی Shared Folder منبع این نصب نیستند.

ابتدا باید مشخص شود Clone روی شاخهٔ صحیح است و working tree تغییر ناخواسته ندارد:

~~~bash
cd ~/projects/cs2-kus-addons
pwd
git status --short --branch
git log -1 --oneline
~~~

بررسی Syntax (این دستورات فایل نصب یا اجرای سرور را اجرا نمی‌کنند):

~~~bash
bash -n linux/setup.sh
bash -n linux/install.sh
bash -n linux/update.sh
find linux/instances/instance-template scripts/update -type f -name '*.sh' -print0 | xargs -0 -n1 bash -n
~~~

اگر Clone تمیز است و VM snapshot گرفته شده، خط مبنای نصب را با مسیر زیر انجام بده:

~~~bash
sudo -E env RUN_PLUGIN_UPDATER=0 bash ./linux/setup.sh
~~~

این دستور باید از ریشهٔ Clone اجرا شود. با `RUN_PLUGIN_UPDATER=0`، مرحلهٔ اختیاری updater پلاگین‌ها که در `linux/setup.sh` شرطی است اجرا نمی‌شود؛ در نتیجه نباید آن مسیرِ commit/push افزونه‌ها فعال شود. با این حال، اسکریپت همچنان تغییرات سیستمی انجام می‌دهد: ممکن است بسته‌های Debian را ارتقا دهد، نیازمندی‌ها و SteamCMD را نصب کند، Steam Linux Runtime و CS2 بومی Linux را دریافت/به‌روزرسانی کند، payload ثبت‌شده را به‌صورت overlay روی مسیر runtime بنویسد و `gameinfo.gi` را برای MetaMod اصلاح کند. سرور CS2 را اجرا نمی‌کند.

**قبل از اجرای این دستور:**
- در VMware از VM یک Snapshot بگیر.
- مطمئن شو هیچ سرور CS2 در حال اجرا نیست.
- بررسی Syntax بالا را انجام بده.
- نسخهٔ فعلی `linux/setup.sh` را بخوان و مطمئن شو منطق آن با توضیح این سند تغییر نکرده است.
- Clone و سورس GitHub را در این مرحله ویرایش یا Push نکن.

### تفاوت سه ورودی Linux

| ورودی | رفتار | وضعیت در baseline فعلی |
|---|---|---|
| `linux/setup.sh` | نصب نیازمندی‌ها، SteamCMD، Steam Linux Runtime، CS2 Linux و overlay کردن payload؛ در پایان سرور را اجرا نمی‌کند. updater پلاگین فقط وقتی `RUN_PLUGIN_UPDATER=1` باشد اجرا می‌شود. | **مسیر پیشنهادی برای نصب پایه، با متغیر صریح `RUN_PLUGIN_UPDATER=0` و پس از بررسی فایل.** |
| `linux/update.sh` | شاخهٔ `integration/kus-monorepo` را انتخاب و `git pull --ff-only` می‌کند؛ پلاگین، بازی و runtime را نصب/به‌روزرسانی نمی‌کند. | فعلاً اجرا نکن؛ Clone تازه است و اول باید وضعیت شاخه ثبت شود. |
| `linux/install.sh` | ترکیب به‌روزرسانی Git، فعال‌کردن plugin updater، اجرای setup و نصب/overlay بازی؛ سرور را اجرا نمی‌کند. در نسخه بررسی‌شده برای اجرای updater، `RUN_PLUGIN_UPDATER=1` را به `setup.sh` پاس می‌دهد و updater می‌تواند تلاش کند تغییراتش را به شاخهٔ GitHub Push کند. | **برای اولین خط مبنا انتخاب نشود** چون Push خودکار بخشی از مسیر کامل آن است. |

> **تصحیح مستندات قبلی:** دستور `sudo env -u RUN_PLUGIN_UPDATER UPDATE_ONLY=1 bash ./linux/install.sh` به‌عنوان راه تضمین‌شدهٔ جلوگیری از plugin updater معتبر نیست؛ `install.sh` متغیر را برای فرزند خود صریحاً روی `1` قرار می‌دهد. همچنین در نسخهٔ بررسی‌شده، `UPDATE_ONLY=1` به‌تنهایی مسیر کامل نصب را به یک حالت امن بدون updater تبدیل نمی‌کند. از آن دستور استفاده نکن.

### بررسی سلامت بعد از نصب پایه

بعد از پایان اسکریپت، پیش از اجرای سرور موارد زیر بررسی می‌شوند:

1. وجود `/home/steam/cs2/game/bin/linuxsteamrt64/cs2` و `/home/steam/steamrt/run`.
2. وجود MetaMod و CounterStrikeSharp و بررسی صحیح `gameinfo.gi`.
3. بررسی اینکه payload و وابستگی‌های مورد انتظار در runtime نصب شده‌اند.
4. فهرست کردن plugin DLLها و مقایسه با manifest/README؛ وجود فایل به‌تنهایی موفقیت Load را ثابت نمی‌کند.
5. سپس ساخت یک Instance آزمایشی از template و تنظیم `instance.env` محلی با پورت و رمز RCON قوی و یکتا.
6. فقط Instance خودش سرور را از طریق `watchdog.sh` اجرا می‌کند. installerها و updaterها برای اجرای سرور استفاده نمی‌شوند.

پلاگین‌های وابسته به دیتابیس جداگانه بررسی می‌شوند؛ شکست اتصال دیتابیس با شکست Load شدن MetaMod/CounterStrikeSharp اشتباه گرفته نمی‌شود. فعلاً هیچ ادعایی دربارهٔ سلامت واقعی CS2 یا plugin runtime ثبت نشده است.

## ۱۰. خروجی مورد انتظار پارت ۲

> هدف فعلی پارت ۲، نصب بومی فایل‌های CS2 و payload پلاگین‌ها از Clone لینوکسی `cs2-kus-addons` روی Debian 13.7 و سپس اجرای یک Instance آزمایشی است. برای مرحله فعلی، ۴ vCPU و حدود ۵.۶ GiB RAM گزارش شده‌اند و محیط گرافیکی حفظ می‌شود. تصمیم قبلی برای کپی نصب Windows به Linux کنار گذاشته شده است؛ در این مسیر فایل‌های Windows از Shared Folder جابه‌جا یا کپی نمی‌شوند و فعلاً افزایش دیسک به ۳۰۰ GB وابسته به این کار نیست. تکمیل پارت به نصب و اجرای واقعی، بررسی Load پلاگین‌ها و ثبت مصرف منابع وابسته است.

**مرحله بعد پس از تست:** ثبت نتیجه واقعی و حل مشکلات احتمالی اجرای CS2؛ سپس تصمیم درباره نحوه انتقال نصب به معماری نودهای Pterodactyl، بدون بازنویسی یا تغییر شتاب‌زده زیرساخت موجود.

### تصمیم‌های جدید این پارت

1. به‌جای دانلود مجدد سورس و افزونه‌های KUS، ابتدا از فایل‌های موجود روی درایو میزبان استفاده می‌شود.
2. کاربر تصمیم گرفته است کل پوشه نصب فعلی بازی ویندوز، حدود ۹۰ GB، نیز به فضای محلی VM کپی شود تا فایل‌های موجود برای استفاده مجدد بررسی شوند.
3. هدف پیشنهادی اندازه دیسک مجازی به **۳۰۰ GB، از نوع Thin Provision** تغییر کرده است. این ظرفیت فعلاً هدف برنامه است و افزایش آن هنوز انجام نشده است.
4. فایل‌های منبع اصلی ویندوز نباید حذف یا جابه‌جا شوند. عملیات انتقال باید از اشتراک به یک مسیر محلی مجزا در Debian انجام شود و به‌صورت کپی باشد، نه انتقالی که منبع را پاک کند.
5. کپی نصب ویندوز به Debian به‌معنی قابل اجرا بودن فایل اجرایی ویندوز در Linux نیست. برای اجرای واقعی CS2 همچنان فایل‌های Linux و Steam Linux Runtime موردنیازند؛ کپی ویندوز صرفاً برای نگهداری و بررسی فایل‌های موجود و جلوگیری از دانلودهای غیرضروری است.

### مسیر اشتراک و نکته مالکیت Git

در پیکربندی فعلی، نام اشتراک VMware برابر **W** است و ریشه قابل مشاهده آن **/mnt/hgfs/W** است؛ این مسیر مستقیماً محتوای ریپوی KUS را نشان می‌دهد. مسیر **/mnt/hgfs/W/cs2-kus-addons** وجود ندارد و نباید به‌عنوان مسیر ریشه استفاده شود.

اجرای **git -C /mnt/hgfs/W rev-parse --show-toplevel** با پیام **detected dubious ownership** متوقف شد. این پیام به‌تنهایی نشان‌دهنده خرابی ریپو نیست و به نحوه گزارش مالکیت فایل‌ها از طریق Shared Folders مربوط می‌شود. برای بررسی فایل‌ها نیازی به اجرای Git روی این mount نیست؛ بنابراین فعلاً **safe.directory** به تنظیمات Git اضافه نشده است.

**برای حفاظت بیشتر از سورس:** قبل از عملیات کپی بعدی، Shared Folder بهتر است از تنظیمات VMware به حالت **Read-only** تغییر کند. VM باید بتواند فایل‌ها را بخواند و در فضای محلی خودش کپی کند، بدون اینکه بتواند سورس میزبان را تغییر دهد. این گزینه هنوز نیاز به تأیید در تنظیمات VMware دارد؛ صرف مشاهده فایل‌ها به معنی Read-only بودن اشتراک نیست.

### موارد Pending — هنوز انجام نشده‌اند

- [ ] بررسی فضای آزاد واقعی در درایوی که فایل‌های VMware روی آن قرار دارند؛ Thin Provision از پرشدن واقعی دیسک میزبان جلوگیری نمی‌کند.
- [ ] خاموش‌کردن VM و افزایش اندازه دیسک مجازی از مقدار فعلی به هدف **۳۰۰ GB** در VMware.
- [ ] پس از افزایش دیسک مجازی، بررسی ساختار واقعی دیسک با **lsblk -o NAME,SIZE,FSTYPE,TYPE,MOUNTPOINTS**، **lsblk -f**، **findmnt /** و **df -h /**.
- [ ] تنها پس از مشاهده خروجی دیسک، تعیین روش لازم برای بزرگ‌کردن پارتیشن و فایل‌سیستم Debian؛ افزایش ظرفیت مجازی VMware لزوماً فایل‌سیستم مهمان را خودکار بزرگ نمی‌کند.
- [ ] تأیید Read-only بودن Shared Folder و ادامه استفاده از ریشه **/mnt/hgfs/W** برای خواندن فایل‌های منبع.
- [ ] کپی غیرمخرب و کامل پوشه نصب ویندوز از **/mnt/hgfs/W/server** به مسیری محلی و جدا در VM؛ مسیر مقصد نهایی پس از بررسی اندازه دیسک مشخص شود.
- [ ] بررسی کپی محلی، اندازه فایل‌ها و وجود فایل‌های موردنیاز Linux. هیچ فایل اجرایی Windows نباید به‌عنوان فایل اجرایی Linux فرض شود.
- [ ] آماده‌سازی payload فعلی KUS برای نصب Linux، بدون اجرای updaterی که ممکن است به GitHub push کند.
- [ ] اجرای نخستین سرور CS2 روی Linux، بررسی لاگ‌ها و ثبت مصرف واقعی RAM و CPU.

### هشدارهای عملیاتی که پابرجا هستند

- در این مرحله **linux/update.sh** اجرا نشود؛ نسخه بررسی‌شده آن می‌تواند مسیر updater افزونه‌ها را فعال کند و آن فرایند برای push کردن تغییرات به شاخه مخزن تلاش کند.
- پیش از هر اجرای اسکریپت نصب Linux، محتوای همان نسخه باید دوباره بررسی شود؛ برای مرحله نصب فایل‌ها، حالت **UPDATE_ONLY=1** و غیرفعال‌کردن **RUN_PLUGIN_UPDATER** در نظر گرفته شده است، ولی نباید یک فرمان را بدون بررسی نسخه فعلی اسکریپت اجرا کرد.
- هیچ commit، push، ویرایش یا پاک‌سازی در ریپوی **larnzs/cs2-kus-addons** از این مرحله انجام نمی‌شود. همه کارهای این پارت فقط برای آماده‌سازی VM و تست محلی‌اند.
- هیچ ادعایی مبنی بر اجرای موفق یک سرور CS2 روی Debian ثبت نشده است؛ سرور Linux هنوز اجرا نشده است.

### وضعیت فعلی پارت ۲

**وضعیت کلی: Pending — آماده‌سازی Debian و اتصال Shared Folder انجام شده؛ توسعه فضای دیسک، کپی نصب بازی و اجرای آزمایشی CS2 هنوز انجام نشده‌اند.**

### ۱۲.۲. بررسی اتصال اینترنت

    getent hosts github.com

### ۱۲.۳. نصب و بررسی ابزارهای VMware Shared Folders

فرمان اجراشده:

    sudo apt install -y open-vm-tools open-vm-tools-desktop fuse3 rsync

خروجی نشان داد هر چهار بسته نصب بوده و نسخه‌های فعلی به‌روز هستند؛ بسته جدیدی نصب یا به‌روزرسانی نشد.

فرمان زیر:

    vmware-hgfsclient

خروجی:

    W

سپس اشتراک با این فرمان‌ها mount شد:

    sudo mkdir -p /mnt/hgfs
    sudo vmhgfs-fuse .host:/ /mnt/hgfs -o allow_other
    ls -la /mnt/hgfs

در ادامه برای mount مجدد، این فرمان‌ها هم اجرا شدند:

    sudo umount /mnt/hgfs
    sudo vmhgfs-fuse .host:/ /mnt/hgfs -o allow_other
    vmware-hgfsclient
    ls -la /mnt/hgfs

نتیجه نهایی نشان داد اشتراک W زیر مسیر /mnt/hgfs/W نمایش داده می‌شود.

**تفسیر مسیر:** فهرست واقعی /mnt/hgfs/W شامل DEPENDENCIES.json، .git، game، linux، server، steamcmd، tmp و دیگر اجزای ریشه ریپوی KUS است. بنابراین در پیکربندی فعلی، محتوای ریشه قابل مشاهده ریپو در /mnt/hgfs/W قرار دارد. مسیر /mnt/hgfs/W/cs2-kus-addons وجود ندارد؛ اسم W نام Shared Folder گزارش‌شده توسط VMware است.

> Shared Folder در حال حاضر mount شده است، اما Read-only بودن آن هنوز تأیید نشده است. پیش از هر عملیات پرریسک باید این گزینه در تنظیمات VMware بررسی و در صورت امکان فعال شود. فایل‌های منبع Windows نباید پاک، جابه‌جا یا بازنویسی شوند.

### ۱۲.۴. مسیرهای اشتباه امتحان‌شده و اصلاح آن‌ها

این مسیرها بررسی شدند اما در ساختار فعلی وجود نداشتند:

همه این مسیرهای درون‌اشتراک با خطای No such file or directory مواجه شدند. علت، مطابق فهرست موفق بعدی، این است که ریشه محتوای ریپو از قبل در /mnt/hgfs/W قابل مشاهده است و فولدر cs2-kus-addons یک سطح دیگر داخل آن نیست.

### ۱۲.۶. خطای Git در Shared Folder

فرمان اجراشده:

    fatal: detected dubious ownership in repository at '/mnt/hgfs/W'

فعلاً دستور پیشنهادی Git برای افزودن safe.directory اجرا نشده است. برای کپی فایل‌ها و اندازه‌گیری پوشه‌ها لازم نیست Git روی Shared Folder اجرا شود. این پیام به‌تنهایی نشانه خرابی مخزن نیست.

### ۱۲.۷. تصمیم Storage — نسخهٔ جاری (تصمیم قبلی لغو شده)

در زمان ثبت‌های قبلی، کپی پوشهٔ `server` از Shared Folder ویندوز با اندازه تقریبی ۹۰ GB و افزایش دیسک VM به ۳۰۰ GB پیشنهاد شده بود. **این برنامه با تصمیم جدید کاربر در ۱۶ اکتبر ۲۰۲۶ جایگزین شده است: بازی و پلاگین‌ها از Clone ریپوی Linux نصب می‌شوند و هیچ پوشه‌ای از نصب بازی Windows جابه‌جا یا کپی نمی‌شود.**

- منبع Windows در `/mnt/hgfs/W/server` فقط در صورت نیاز برای مقایسهٔ read-only باقی می‌ماند؛ مبنای نصب Linux نیست.
- فایل اجرایی Windows در `server/game/bin/win64/cs2.exe` برای اجرای مستقیم در Linux استفاده نمی‌شود.
- افزایش دیسک به ۳۰۰ GB دیگر پیش‌نیاز کپی Windows نیست و فقط در صورت نیاز واقعی فضای نصب native/داده‌های بعدی دوباره ارزیابی می‌شود.
- فایل‌های بازی native در مسیر پیش‌فرض اسکریپت فعلی `/home/steam/cs2` و Steam Linux Runtime در `/home/steam/steamrt` قرار می‌گیرند؛ مقصد نهایی باید از روی نسخهٔ فعلی اسکریپت تأیید شود.

### ۱۲.۸. گام بعد از Clone

1. وارد `~/projects/cs2-kus-addons` شو و مسیر، branch، آخرین commit و working tree را با `pwd`, `git status --short --branch` و `git log -1 --oneline` بررسی کن.
2. Syntax اسکریپت‌های Linux را با `bash -n` بررسی کن.
3. قبل از هر نصب، در VMware Snapshot بگیر و مطمئن شو CS2 فعال نیست.
4. برای خط مبنای نصب از `sudo -E env RUN_PLUGIN_UPDATER=0 bash ./linux/setup.sh` استفاده کن؛ این دستور فقط پس از بازبینی نسخهٔ جاری اسکریپت اجرا شود. از `linux/install.sh` و `linux/update.sh` برای اولین نصب کنترل‌شده استفاده نکن.
5. پس از نصب، وجود فایل‌های native Linux و payload را بررسی کن؛ سپس یک Instance بساز و فقط از `watchdog.sh` آن را اجرا کن.

در حال حاضر کاربر نصب Git و Clone را گزارش کرده است؛ خروجی branch/status/log، اجرای Syntax، نصب CS2 بومی Linux، اجرای Instance و بررسی واقعی پلاگین‌ها هنوز در این سند تأیید نشده‌اند.

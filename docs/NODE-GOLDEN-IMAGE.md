# FragCity — Debian Node Golden Image & Cloning Policy

> **وضعیت:** طرح تأییدشده برای بررسی در PoC؛ هنوز روی Debian فعلی اجرا یا اعتبارسنجی نشده است. این سند مجوز ساخت یا تکثیر نود عملیاتی پیش از قبولی آزمون‌های پایه نیست.

## 1. هدف

هدف این است که پس از تکمیل و تست یک Debian Node مرجع، برای ساخت نودهای بعدی مجبور نباشیم همهٔ مراحل نصب را دستی از ابتدا تکرار کنیم. یک **Golden Image/Template نسخه‌بندی‌شده** از لایهٔ مشترک تهیه می‌کنیم و برای هر نود جدید فقط تنظیمات مختص همان نود را اعمال می‌کنیم.

Golden Image به معنی «کپی بدون تغییر و آمادهٔ Production» نیست. هر Clone باید هویت یکتا، تنظیمات شبکه و پیکربندی مخصوص خودش را بگیرد و بعد آزمون سلامت را بگذراند.

## 2. دو روش استقرار که نباید با هم اشتباه شوند

### A. ساخت VM جدید در VMware

فایل VMDK دیسک مجازی است؛ حتی اگر گزینهٔ **single file** برای آن انتخاب شده باشد، لزوماً همهٔ فایل‌های VM را شامل نمی‌شود.

برای Clone مطمئن در VMware:
1. VM اصلی را کاملاً **Shut down** کن؛ در حالت Running یا Suspended از فایل‌های آن کپی نگیر.
2. از **کل پوشهٔ VM** کپی/Clone بگیر، نه فقط VMDK. فایل پیکربندی VM (معمولاً `.vmx`)، دیسک(ها) و هر فایل وابسته‌ای که واقعاً استفاده می‌شود باید حفظ شود. اگر snapshot یا دیسک وابسته وجود دارد، پیش از کپی وضعیت زنجیرهٔ دیسک‌ها را بررسی کن.
3. Clone را با هویت مستقل اجرا کن. وقتی VMware می‌پرسد VM را «Moved» کرده‌ای یا «Copied»، برای اجرای هم‌زمان منبع و Clone، گزینهٔ **Copied It** را انتخاب کن تا شناسه‌های VM و MAC جدید ایجاد شوند.
4. پس از Boot، hostname، شبکه/IP و هویت سیستم‌عامل را طبق تنظیمات نود جدید یکتا کن و سپس سرویس‌های مختص نود را پیکربندی کن.

**فقط کپی‌کردن یک فایل VMDK به سرور فیزیکی، روش نصب Debian روی سخت‌افزار واقعی نیست.**

### B. سرور فیزیکی (Bare Metal) یا محیط غیر VMware

برای نصب مستقیم روی سخت‌افزار، VMDK را به‌عنوان روش استقرار نهایی فرض نمی‌کنیم. به‌جای آن، همان مراحل مشترک را در یک **Provisioning script** قابل تکرار یا ابزار مدیریت پیکربندی مانند Ansible نگه می‌داریم. این راهکار باید از روی سیستم تمیز، نصب و تنظیمات را با ورودی‌های مختص نود بازسازی کند.

بنابراین هدف بلندمدت دو خروجی مکمل دارد:
- **VMware:** Golden VM Template برای Clone سریع در همان محیط مجازی‌سازی.
- **Bare Metal/محیط دیگر:** Runbook و Provisioning خودکار برای بازسازی قابل تکرار.

## 3. چه چیزهایی می‌توانند در Template باشند؟

فقط اجزای مشترکی که نصب و سلامت آن‌ها روی نود مرجع تست شده‌اند:

- نسخهٔ مشخص و پشتیبانی‌شدهٔ Debian و بسته‌های پایهٔ موردنیاز.
- ابزارهای عمومی مدیریت و عیب‌یابی، گواهی‌های CA و Git.
- Clone ریپوی `larnzs/cs2-kus-addons` روی شاخهٔ `integration/kus-monorepo`، همراه ثبت commit دقیق و اسکریپت‌های تأییدشده؛ نصب/آپدیت واقعی باید طبق runbook انجام شود.
- SteamCMD و اجزای Linux runtime لازم برای CS2، پس از تست عملی.
- Docker و اجزای Pterodactyl/Wings تنها پس از انتخاب نسخه و قبولی آزمون نصب و امنیت آن‌ها.
- در صورت تصمیم بعدی، یک CS2 Base Game مشترکِ نصب‌شده برای همان Node؛ این بخش **اختیاری و نیازمند آزمون Update** است. وجود Base داخل Image جایگزین چرخهٔ مرکزی و هماهنگ‌شدهٔ Update بازی نمی‌شود.
- فایل‌های مستندات، health check و اسکریپت bootstrap که secret واقعی داخل آن‌ها نباشد.

نسخهٔ Debian، commit ریپو، نسخهٔ بسته‌ها، نسخهٔ Panel/Wings/Docker و زمان تهیهٔ Image باید در manifest متنی ثبت شوند تا بعداً معلوم باشد Node از چه خط مبنایی ساخته شده است.

## 4. چه چیزهایی نباید بین Cloneها مشترک باقی بمانند؟

موارد زیر باید در مرحلهٔ آماده‌سازی Template پاک‌سازی شوند یا برای هر نود از نو تولید/تنظیم شوند:

- hostname و تنظیمات شبکه/IP/route.
- شناسهٔ ماشین لینوکس، از جمله `/etc/machine-id`.
- کلیدهای SSH میزبان در `/etc/ssh/ssh_host_*`؛ Clone جدید نباید هویت SSH نود مرجع را به ارث ببرد.
- پیکربندی نود در Pterodactyl/Wings، شامل UUID و credential/token مستقل آن نود، آدرس Panel، تنظیمات TLS و مسیرهای داده.
- گواهی‌ها و private keyهای TLS مختص سرویس، در صورتی که برای هر نود صادر می‌شوند.
- credentialهای دیتابیس/API، tokenها و هر secret دیگر.
- دیتابیس محلی و داده‌های وابسته به یک نود، logهای خصوصی، backupها، sessionها و دادهٔ مشتریان.
- تخصیص‌های شبکه/پورت و ظرفیت‌های مختص سخت‌افزار/VM مقصد.

**قانون مهم:** توکن Wings یا secret یک نود را در Golden Image مشترک قرار نمی‌دهیم و یک `config.yml` آمادهٔ نود موجود را به Clone جدید منتقل نمی‌کنیم. نود جدید باید در Panel ثبت شود و پیکربندی مختص همان Node را بگیرد. نحوهٔ تولید/جای‌گذاری secret باید کنترل‌شده باشد و secret نباید وارد Git یا log شود.

## 5. الگوی پیشنهادی برای افزودن نود

هر نود از دو بخش تشکیل می‌شود:

1. **لایهٔ مشترک:** از Template نسخه‌بندی‌شده یا Provisioning تکرارپذیر.
2. **تنظیمات مختص نود:** یک فایل ورودی محلی مانند `node.env` یا فایل config خارج از Git، شامل مقادیر غیرمحرمانه‌ای مثل نام نود، محدودهٔ پورت و ظرفیت‌ها؛ secretها جداگانه و امن تزریق شوند.

Bootstrap باید دست‌کم این کارها را انجام دهد:
- هویت سیستم‌عامل، hostname و تنظیمات شبکهٔ نود جدید را یکتا/اعمال کند.
- هویت SSH را با رویهٔ امن تولید کند.
- Node تازه را در Panel ثبت یا با پیکربندی تولیدشدهٔ همان Node آماده کند.
- تنظیمات خاص Wings، مسیرهای داده، آدرس Panel، TLS، منابع و پورت‌ها را اعمال کند.
- وجود secretها و مجوز فایل‌ها را اعتبارسنجی کند؛ secret گم‌شده یا config ناقص باید باعث توقف امن شود، نه اجرای نود با credential پیش‌فرض.
- نسخه‌ها و نتیجهٔ health check را ثبت کند.

نام فایل و قرارداد دقیق تنظیمات بعد از دیدن وضعیت واقعی Debian، نسخه‌های نهایی و شیوهٔ Provisioning انتخاب خواهد شد؛ هنوز قرارداد نهایی `node.env` تصویب نشده است.

## 6. ترتیب صحیح تهیهٔ Golden Image

Golden Image را **بعد از تست موفق پایه** می‌سازیم، نه قبل از آن. ترتیب پیشنهادی:

1. وضعیت واقعی Debian فعلی، فضای ذخیره‌سازی، شبکه و نسخهٔ ابزارها ثبت شود.
2. نصب/Update لایهٔ Linux ریپوی KUS با بازبینی اسکریپت‌ها و بدون اجرای ناخواستهٔ server یا plugin updater انجام و بررسی شود.
3. اجرای یک CS2 Instance، لاگ‌ها، توقف/شروع و Update پایه اعتبارسنجی شود.
4. Panel/Wings و اتصال Node آزمایشی نصب و آزموده شود.
5. دو Instance روی یک Base مشترک ساخته شوند؛ جداسازی فضای خصوصی، پورت‌ها، File Manager و حفاظت کانفیگ بررسی شود.
6. چرخهٔ هماهنگ Update Base و updater انتخابی پلاگین/Runtime در برابر checksum مسیرهای محافظت‌شده آزموده شود.
7. اتصال موردنیاز پلاگین‌ها به MySQL/MariaDB محلی و روش Backup/Restore ارزیابی شود.
8. از محیطی که همهٔ آزمون‌های لازم آن قبول شده‌اند، VM را خاموش کن؛ secretها و هویت‌های مختص نود را پاک/بازنشانی کن و Template نسخه‌بندی‌شده بساز.
9. از Template یک Clone آزمایشی مستقل بساز و ثابت کن هویت OS/SSH/شبکه و config نودها تکراری نیست، Wings با Panel هماهنگ است و یک Instance آزمایشی به‌درستی کار می‌کند.
10. نتیجه و نسخه‌ها را در [Testing Bench](TESTING-BENCH.md) ثبت کن. تا قبولی این آزمون‌ها Template فقط آزمایشی است.

## 7. مدیریت نسخه و نگهداری

- هر Golden Image شناسه/نسخهٔ روشن داشته باشد؛ برای مثال `fragcity-debian-cs2-v1`، پس از نهایی‌شدن قرارداد نسخه‌گذاری.
- Image اصلی به‌عنوان مرجع نگهداری شود؛ تغییرات هر نود را به‌صورت تصادفی به Template اصلی برنگردان.
- برای ارتقای سیستم‌عامل یا ابزارهای مشترک، Template جدید بساز، آزمون‌ها را تکرار کن و نسخهٔ جدید منتشر کن.
- نودهای موجود را با overwrite کردن دیسک از روی Image جدید ارتقا نده؛ ارتقا باید از مسیر کنترل‌شده، همراه backup و rollback انجام شود.
- Template هرگز نباید جایگزین backup داده‌های مشتری، دیتابیس یا تنظیمات مختص نود شود.

## 8. وضعیت و محدودیت‌های فعلی

- این سند برنامهٔ معماری و runbook اولیه است؛ **Golden Image ساخته نشده و Clone آزمایشی صورت نگرفته است**.
- نصب و صحت Pterodactyl/Wings، چرخهٔ Base مشترک، overlay/mount، bootstrap نود، و اتصال DB باید روی Debian واقعی آزمایش شوند.
- تهیهٔ Template شامل اجرای هیچ فرمانی روی Debian فعلی نیست.
- ریپوی `cs2-kus-addons` در این تغییر مستنداتی دست‌کاری نمی‌شود.
- معیار پذیرش بعدی: بتوان از یک خط مبنای تأییدشده نود جدید ساخت، مقادیر مختص نود را بدون ویرایش کد برنامه اعمال کرد و آزمون‌های سلامت/جداسازی را تکرارپذیر گذراند.

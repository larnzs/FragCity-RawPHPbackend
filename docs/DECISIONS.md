# FragCity — Architecture Decision Records

این فایل تصمیم‌های تأییدشده را از پیشنهادهای موقت و سؤال‌های باز جدا می‌کند.

## ADR-001 — استفادهٔ حداکثری از محصولات متن‌باز

**وضعیت:** تأییدشده به‌عنوان اصل توسعه  
**تصمیم:** قابلیت‌های عمومی فروش، مدیریت بازی و مدیریت نودها را از محصولات تخصصی بالغ بگیریم. کد اختصاصی فقط برای شکاف‌های واقعی FragCity نوشته شود.  
**اثر:** Instance Maker و RCON فعلی به‌عنوان پیاده‌سازی نهایی فرض نمی‌شوند؛ پنل منتخب باید در PoC ثابت کند چه چیزهایی را پوشش می‌دهد.

## ADR-002 — مسیر مرجع PoC

**وضعیت:** مسیر آزمایشی پیشنهادی؛ انتخاب تولیدی Pending  
**تصمیم:** Paymenter + Pterodactyl Panel/Wings مسیر A باشد؛ GameAP مسیر B مقایسه‌ای باقی بماند.  
**دلیل:** integration آماده Paymenter/Pterodactyl و کاهش کد provisioning سفارشی.  
**شرط ادامه:** موفقیت ساخت CS2، اتصال فروش، کیف پول، expiry، جداسازی مشتری و Backup/Restore.

## ADR-003 — مدل تجاری بستهٔ مدت‌دار

**وضعیت:** تأییدشده توسط کاربر  
**تصمیم:** قیمت ثابت هر بسته از کیف پول هنگام خرید یک‌بار کسر می‌شود؛ اعتبار ۱/۳/۷/۱۵/۳۰ روزه است؛ تایمر پس از خرید موفق شروع می‌شود و در خاموشی سرور pause نمی‌شود.  
**اثر:** زمان انقضا باید صریح ذخیره شود (`expires_at`)؛ این usage metering بر اساس uptime نیست.  
**موارد باز:** تعریف دقیق ۱ روز، تمدید، مهلت نگهداری و رفتار پس از انقضا.

## ADR-004 — Remote MariaDB از هاست فعلی

**وضعیت:** ردشده برای مسیر فعلی  
**تصمیم:** اتصال مستقیم از Debian به MariaDB cPanel روی TCP/3306 در برنامهٔ فعلی استفاده نشود.  
**دلیل:** تست اتصال timeout شده و ارائه‌دهنده اعلام کرده است دسترسی مناسب Remote DB در هاست فعلی در دسترس نیست/پورت مورد نیاز بسته است.  
**جایگزین:** درخواست HTTPS از نود به API سایت؛ PHP به دیتابیس از داخل هاست متصل شود. این روش نیازمند اصلاح احراز هویت و قراردادهای API موجود است.

## ADR-005 — محافظت از cs2-kus-addons

**وضعیت:** تأییدشده  
**تصمیم:** ریپوی `larnzs/cs2-kus-addons` و کانفیگ‌های آن در این پروژه تغییر نمی‌کنند مگر کاربر جداگانه درخواست صریح بدهد.  
**اثر:** نصب/به‌روزرسانی/اسکریپت تغییردهنده روی این ریپو برای این roadmap اجرا نمی‌شود.

## ADR-006 — مسئولیت پنل بازی

**وضعیت:** کاندید  
**تصمیم:** Pterodactyl یا GameAP باید مسئول provisioning و عملیات عادی instance باشند.  
**شرط:** PoC باید نشان دهد console، فایل‌ها، منابع، چرخهٔ عمر و Backup را پوشش می‌دهد. اگر gap باقی ماند، فقط همان بخش با کد محدود تکمیل می‌شود.

## ADR-007 — محل استقرار

**وضعیت:** جهت‌گیری تأییدشده؛ مکان نهایی Pending  
**تصمیم:** cPanel فعلی می‌تواند سایت عمومی و دیتابیس خودش را فعلاً میزبانی کند. Panel/Wings و سرویس‌های دائمی روی محیطی قرار می‌گیرند که الزامات شبکه و اجرای workerها را پشتیبانی کند.  
**اثر:** هاست اشتراکی را محل پیش‌فرض اجرای Wings یا queue worker فرض نمی‌کنیم.

## سؤال‌های باز برای تصمیم جلسه/PoC

1. Paymenter آیا دقیقاً به Wallet فعلی FragCity متصل می‌شود یا فقط سفارش/محصول را مدیریت خواهد کرد؟
2. تمدید قبل از انقضا زمان باقی‌مانده را افزایش دهد یا تاریخ را از لحظهٔ خرید بازتنظیم کند؟
3. در انقضا سرور Suspend شود یا Stop؛ داده تا چند روز حفظ شود؟
4. کدام درگاه پرداخت، واحد پول، refund و reconciliation نیاز است؟
5. آیا سایت PHP فعلی می‌ماند و Paymenter در زیر دامنه/سامانه جدا نصب می‌شود؟
6. کدام خانواده‌های دادهٔ پلاگین باید بین سرورها مشترک باشند و کدام‌ها مختص هر سرور/مشتری هستند؟
7. ظرفیت و هزینهٔ قابل قبول برای محیط Panel/Billing جدا چیست؟

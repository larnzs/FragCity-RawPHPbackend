# FragCity — Architecture Decision Records

این فایل تصمیم‌های تأییدشده را از پیشنهادهای موقت و سؤال‌های باز جدا می‌کند.

## ADR-001 — استفادهٔ حداکثری از محصولات متن‌باز

**وضعیت:** تأییدشده به‌عنوان اصل توسعه  
**تصمیم:** قابلیت‌های عمومی فروش، مدیریت بازی و مدیریت نودها را از محصولات تخصصی بالغ بگیریم. کد اختصاصی فقط برای شکاف‌های واقعی FragCity نوشته شود.  
**اثر:** Instance Maker و RCON فعلی به‌عنوان پیاده‌سازی نهایی فرض نمی‌شوند؛ پنل منتخب باید در PoC ثابت کند چه چیزهایی را پوشش می‌دهد.

## ADR-002 — مسیر مرجع PoC

**وضعیت:** مسیر آزمایشی پیشنهادی؛ انتخاب تولیدی Pending  
**تصمیم:** Paymenter + Pterodactyl Panel/Wings مسیر A باشد؛ GameAP مسیر B مقایسه‌ای باقی بماند.  
**دلیل:** integration آماده Paymenter/Pterodactyl و کاهش کد provisioning سفارشی.  
**شرط ادامه:** موفقیت ساخت CS2، اتصال فروش، کیف پول، expiry، جداسازی مشتری و Backup/Restore.

## ADR-003 — مدل تجاری بستهٔ مدت‌دار

**وضعیت:** تأییدشده توسط کاربر  
**تصمیم:** قیمت ثابت هر بسته از کیف پول هنگام خرید یک‌بار کسر می‌شود؛ اعتبار ۱/۳/۷/۱۵/۳۰ روزه است؛ تایمر پس از خرید موفق شروع می‌شود و در خاموشی سرور pause نمی‌شود.  
**اثر:** زمان انقضا باید صریح ذخیره شود (`expires_at`)؛ این usage metering بر اساس uptime نیست.  
**موارد باز:** تعریف دقیق ۱ روز، تمدید، مهلت نگهداری و رفتار پس از انقضا.

## ADR-004 — Remote MariaDB از هاست فعلی

**وضعیت:** ردشده برای مسیر فعلی  
**تصمیم:** اتصال مستقیم از Debian به MariaDB cPanel روی TCP/3306 در برنامهٔ فعلی استفاده نشود.  
**دلیل:** تست اتصال timeout شده و ارائه‌دهنده اعلام کرده است دسترسی مناسب Remote DB در هاست فعلی در دسترس نیست/پورت مورد نیاز بسته است.  
**جایگزین:** درخواست HTTPS از نود به API سایت؛ PHP به دیتابیس از داخل هاست متصل شود. این روش نیازمند اصلاح احراز هویت و قراردادهای API موجود است.

## ADR-005 — محافظت از cs2-kus-addons

**وضعیت:** تأییدشده  
**تصمیم:** ریپوی `larnzs/cs2-kus-addons` و کانفیگ‌های آن در این پروژه تغییر نمی‌کنند مگر کاربر جداگانه درخواست صریح بدهد.  
**اثر:** نصب/به‌روزرسانی/اسکریپت تغییردهنده روی این ریپو برای این roadmap اجرا نمی‌شود.

## ADR-006 — مسئولیت پنل بازی

**وضعیت:** کاندید  
**تصمیم:** Pterodactyl یا GameAP باید مسئول provisioning و عملیات عادی instance باشند.  
**شرط:** PoC باید نشان دهد console، فایل‌ها، منابع، چرخهٔ عمر و Backup را پوشش می‌دهد. اگر gap باقی ماند، فقط همان بخش با کد محدود تکمیل می‌شود.

## ADR-007 — محل استقرار

**وضعیت:** جهت‌گیری تأییدشده؛ مکان نهایی Pending  
**تصمیم:** cPanel فعلی می‌تواند سایت عمومی و دیتابیس خودش را فعلاً میزبانی کند. Panel/Wings و سرویس‌های دائمی روی محیطی قرار می‌گیرند که الزامات شبکه و اجرای workerها را پشتیبانی کند.  
**اثر:** هاست اشتراکی را محل پیش‌فرض اجرای Wings یا queue worker فرض نمی‌کنیم.

## سؤال‌های باز برای تصمیم جلسه/PoC

1. Paymenter آیا دقیقاً به Wallet فعلی FragCity متصل می‌شود یا فقط سفارش/محصول را مدیریت خواهد کرد؟
2. تمدید قبل از انقضا زمان باقی‌مانده را افزایش دهد یا تاریخ را از لحظهٔ خرید بازتنظیم کند؟
3. در انقضا سرور Suspend شود یا Stop؛ داده تا چند روز حفظ شود؟
4. کدام درگاه پرداخت، واحد پول، refund و reconciliation نیاز است؟
5. آیا سایت PHP فعلی می‌ماند و Paymenter در زیر دامنه/سامانه جدا نصب می‌شود؟
6. کدام خانواده‌های دادهٔ پلاگین باید بین سرورها مشترک باشند و کدام‌ها مختص هر سرور/مشتری هستند؟
7. ظرفیت و هزینهٔ قابل قبول برای محیط Panel/Billing جدا چیست؟



## ADR-008 — چند Instance و اشتراک فایل‌های پایهٔ CS2

**وضعیت:** جایگزین‌شده با ADR-010؛ این بخش سابقهٔ تصمیم قبلی را نگه می‌دارد.  
**تصمیم قبلی:** برای شروع PoC قرار بود هر سرور فایل‌های مستقل کامل داشته باشد و سپس K4ryuu/CS2-Egg VPK Sync بررسی شود. این دیگر هدف معماری فعلی FragCity نیست.  
**یادداشت:** مدل shared base اکنون در ADR-010 ثبت شده است؛ روش فنی اجرا همچنان باید در PoC آزموده شود.

## ADR-009 — تفکیک Test Bench و candidateها بر اساس سیستم‌عامل

**وضعیت:** ساختار مستندات تأییدشده؛ انتخاب ابزار/Production هنوز Pending.  
**تصمیم:** بررسی چند Instance CS2 پروژه‌ای مستقل است و باید candidateهای Linux-native، Windows-native و Cross-platform را در لاین‌های جداگانه آزمایش کند. Testing Bench مرجع وضعیت، معیار قبولی، شواهد و نتیجه است؛ Probably and Suggestions فقط فرضیه و توصیهٔ اولیه را نگه می‌دارد.  
**دلیل:** اجرای موفق روی یک OS، امکان Shared Base یا صحت isolation را برای OS دیگر ثابت نمی‌کند. همین‌طور README به‌تنهایی تضمین اجرای صحیح یا مجوز استفادهٔ تجاری نیست.  
**شرط:** هیچ candidate قبل از Static Review، licence/security gate، آزمون دو Instance، backup/restore و ثبت نتیجهٔ قابل تکرار به Production ارتقا پیدا نمی‌کند. مدل shared base انتخاب معماری فعلی FragCity برای PoC است؛ ابزارهای ثالث فقط در صورت نیاز، پس از بازبینی و آزمون مستقل مقایسه می‌شوند.  
**مرجع:** [Testing Bench](TESTING-BENCH.md)، [Probably and Suggestions](PROBABLY-AND-SUGGESTIONS.md)، [CS2 Multi-Instance](CS2-MULTI-INSTANCE.md).


## ADR-010 — بازی پایهٔ مشترک و فایل‌های اختصاصی Instance

**وضعیت:** جهت معماری تأییدشده برای PoC؛ پیاده‌سازی و Production هنوز آزمون نشده است.  
**تصمیم:** هر Node لینوکسی یک CS2 Base Game مرکزی دارد که SteamCMD فقط همان را نصب/به‌روزرسانی می‌کند. همهٔ Instanceهای تحت این Base از فایل‌های مشترک بازی استفاده می‌کنند؛ برای هر سرور نسخهٔ جداگانه‌ای از کل بازی نصب نمی‌شود.

**فایل‌های اختصاصی هر Instance:** پوشه‌های game/csgo/addons/ و game/csgo/cfg/ و فایل‌های متنی مشخصی که تنظیمات GameMode را تعریف می‌کنند. فهرست دقیق فایل‌های GameMode باید در طراحی فنی بعدی ثبت شود. بقیهٔ فایل‌های Base به‌عنوان فایل‌های مشترک و غیرقابل‌تغییر از سوی Instanceها در نظر گرفته می‌شوند؛ تنها فرایند مرکزی Update مجاز است Base را جایگزین کند.

**اسکریپت Pterodactyl:** هنگام Provisioning اولیه، baseline کامل payload شامل `addons/`، `cfg/` و فایل‌های متنی تعیین‌شدهٔ GameMode به مسیر خصوصی هر Instance کپی می‌شود. پیش از Startهای بعدی، updater فقط پلاگین‌ها و Runtimeهای مدیریت‌شده را به‌روزرسانی می‌کند؛ تنظیمات محافظت‌شده طبق ADR-014 بازنویسی نمی‌شوند. این اسکریپت نباید SteamCMD را اجرا کند، بازی پایه را نصب/به‌روزرسانی کند یا جایگزین چرخهٔ عمر Wings/Pterodactyl شود.

**سیاست Update بازی پایه:** به‌محض تشخیص انتشار Update جدید CS2، چرخهٔ Update هماهنگ‌شده باید خودکار آغاز شود. تمام Instanceهایی که از Base مشترک استفاده می‌کنند متوقف می‌شوند؛ سپس SteamCMD یک‌بار روی Base مرکزی اجرا می‌شود. هیچ Instance نباید هنگام Update یا روی فایل‌های نیمه‌به‌روزشده Start/Restart شود. پس از تأیید موفقیت Update، Instanceهایی که پیش از عملیات در حال اجرا بودند می‌توانند دوباره Start شوند؛ در صورت شکست، آن‌ها باید متوقف بمانند تا مسیر بازیابی اجرا شود.

**موارد باز برای پیاده‌سازی:** جزئیات فنی تشخیص Update جدید، قفل عملیات و جلوگیری از Start هم‌زمان، روش mount/link/overlay یا مسیر فیزیکی فایل‌های مشترک، اعتبارسنجی و rollback، و جزئیات deploy فایل‌های اختصاصی. هیچ ابزار ثالثی مانند VPK Sync در این تصمیم به‌عنوان پیاده‌سازی منتخب تعیین نشده است.

**مرجع:** [CS2 Multi-Instance](CS2-MULTI-INSTANCE.md)، [Platform PoC](PLATFORM-POC.md)، [Testing Bench](TESTING-BENCH.md).


## ADR-011 — پکیج اولیهٔ Instance و پیکربندی اختصاصی بدون Preset

**وضعیت:** تصمیم معماری تأییدشده برای PoC؛ پیکربندی مودهای نهایی و Production هنوز انجام/تأیید نشده است.  
**تصمیم:** هنگام Provisioning، هر Instance یک baseline کامل و خصوصی از payload استاندارد FragCity دریافت می‌کند: کل `game/csgo/addons/`، کل `game/csgo/cfg/` و فایل‌های متنی تعیین‌شدهٔ GameMode. این کپی کامل، مرحلهٔ ساخت اولیه است. پیش از هر Start، updater محدودشده فقط پلاگین‌ها و Runtimeهای مدیریت‌شده را به‌روزرسانی می‌کند و مسیرهای محافظت‌شده را تغییر نمی‌دهد؛ جزئیات در ADR-014 آمده است. این مسیرها باید در Volume/لایهٔ اختصاصی هر Instance قرار بگیرند.

**بدون preset در مرحلهٔ نخست:** در زمان Provisioning هنوز پروفایل مود نهایی مثل Aim map pool + HS Only، Public Fun یا DM/FFA با تنظیمات اختصاصی انتخاب و اعمال نمی‌شود. تمام Instanceها ابتدا همان baseline کامل و سالم را می‌گیرند، اما از همان ابتدا port/allocation، تنظیمات عمومی و پوشه‌های payload آن‌ها جدا است. پس از قبولی آزمون ساخت، اجرا و جداسازی، هر Instance جداگانه کانفیگ می‌شود.

**پیکربندی‌های بعدی:** تنظیمات مود می‌توانند در فایل‌های اختصاصی `cfg/`، فایل‌های GameMode و تنظیمات افزونه‌ها مانند `addons/counterstrikesharp/configs/plugins/` اعمال شوند. تغییر یک Instance نباید تنظیمات یا رفتار Instance دیگر را عوض کند. نمونه‌های مود در این ADR فقط مثال‌اند؛ به‌معنی تعریف محصول یا preset خودکار در مرحلهٔ اول نیستند.

**مرز اسکریپت Deploy:** اسکریپت Provisioning/Deploy فقط payload اختصاصی Instance را قرار می‌دهد و پوشه‌های مستقل را آماده می‌کند؛ SteamCMD اجرا نمی‌کند، Base Game را نصب/Update نمی‌کند و خود سرور را Start نمی‌کند.

**مرجع:** [CS2 Multi-Instance](CS2-MULTI-INSTANCE.md)، [Platform PoC](PLATFORM-POC.md)، [Testing Bench](TESTING-BENCH.md).

## ADR-012 — استفاده از File Manager داخلی Pterodactyl

**وضعیت:** جهت PoC تأییدشده؛ نحوهٔ اتصال آن به سایت FragCity و پنل C# موجود هنوز Pending است.  
**تصمیم:** قابلیت پایهٔ مرور، مشاهده و ویرایش فایل‌های هر سرور از طریق File Manager خود Pterodactyl ارزیابی می‌شود تا همان قابلیت از ابتدا در FragCity دوباره ساخته نشود. Pterodactyl مجوزهای فایل و عملیات کنترل سرور را جداگانه ارائه می‌کند؛ برای Subuserها می‌توان مجوزهای لازم را محدود کرد.

**مرزها:** Pterodactyl یک رابط/پنل مشتری مستقل است و به‌صورت خودکار داخل سایت FragCity یا پنل C# فعلی embed نمی‌شود. لینک‌دهی یا SSO/Integration با سایت بعداً جداگانه بررسی می‌شود. این تصمیم به معنی حذف فوری پنل/برنامهٔ C# موجود نیست؛ ابتدا باید هم‌پوشانی‌ها و شکاف‌های واقعی آن مشخص شوند.

**امنیت فایل‌ها:** مشتری فقط باید به فایل‌های Instance واگذارشدهٔ خودش دسترسی داشته باشد. File Manager باید فایل‌های private مانند `addons/`، `cfg/` و فایل‌های GameMode را به شکل قابل ویرایش در دسترس قرار دهد، بدون اینکه امکان نوشتن در Base مشترک یا دسترسی به Instanceهای دیگر ایجاد شود. نمایش و عملکرد mount/overlay از طریق File Manager و SFTP بخشی از PoC است.

**مرجع قابلیت‌ها:** [Pterodactyl permission model](https://github.com/pterodactyl/panel/blob/1.0-develop/app/Models/Permission.php)، [Client permissions API](https://docs.pterodactyl.io/v1/api/client-general/get-show-permissions).


## ADR-013 — همگام‌سازی payload خصوصی پیش از هر Start

**وضعیت:** سیاست Provisioning و به‌روزرسانی انتخابی تأیید شده است؛ روش mount/overlay و اعتبارسنجی عملی آن هنوز باید در PoC آزمایش شود.  
**منبع:** شاخهٔ `integration/kus-monorepo` در [`larnzs/cs2-kus-addons/game/csgo`](https://github.com/larnzs/cs2-kus-addons/tree/integration/kus-monorepo/game/csgo).

**رفتار هر Instance:** هر Instance در زمان Provisioning baseline کامل payload را در فضای خصوصی خود می‌گیرد. پیش از هر Start، pre-start updater فقط پلاگین‌ها، وابستگی‌ها و Runtimeهایی را که در سیاست updater مدیریت می‌شوند به‌روزرسانی می‌کند. این مرحله برای تمام Instanceها اجرا می‌شود، اما mirror یا کپی مجدد کامل `addons/`، `cfg/` و فایل‌های متنی انجام نمی‌دهد؛ فهرست مسیرهای محافظت‌شده در ADR-014 آمده است.

**جداسازی منابع:** فایل‌های اصلی CS2 از نصب مرکزی مشترک خوانده می‌شوند. فایل‌های payload و تنظیمات Instance از مسیر خصوصی همان Instance خوانده می‌شوند. هیچ فایل payload روی فایل‌های فیزیکی Base Game paste، copy یا merge نمی‌شود. پس از sync موفق، Pterodactyl/Wings باید Base و payload خصوصی را در نمای اجرایی جداشده به process ارائه کند؛ روش فنی mount/overlay هنوز باید در PoC انتخاب شود.

**ترتیب پیش از Start:** (۱) جلوگیری از اجرای هم‌زمان updater برای همان Instance، (۲) به‌روزرسانی انتخابی پلاگین‌ها و Runtimeهای مجاز در فضای خصوصی همان Instance، (۳) بررسی موفقیت عملیات و سالم‌بودن فایل‌های به‌روزشده، (۴) اطمینان از دست‌نخوردن مسیرهای محافظت‌شده، (۵) آماده‌کردن نمای اجرایی Base مشترک + لایهٔ خصوصی Instance، و (۶) واگذاری اجرای CS2 به Startup معمول Pterodactyl. در صورت شکست، Instance نباید با فایل‌های ناقص یا نیمه‌به‌روزشده اجرا شود.

**مرز اسکریپت:** pre-start updater خودش SteamCMD را اجرا نمی‌کند، Base Game را نصب/Update نمی‌کند و process بازی را مستقیماً اجرا نمی‌کند؛ فقط پس از پایان موفقیت‌آمیز آپدیت انتخابی و بررسی حفاظت کانفیگ‌ها، فرمان معمول Startup می‌تواند CS2 را اجرا کند.

**حفظ کانفیگ:** سیاست موجود ریپوی `cs2-kus-addons` مبناست: updater فایل‌های متنی تنظیمات/GameMode، درخت `cfg/` و درخت `addons/counterstrikesharp/configs/` را تغییر نمی‌دهد؛ فقط پلاگین‌ها و Runtimeهای تحت مدیریت را به‌روزرسانی می‌کند. همین حفاظت باید در updater خصوصی هر Instance رعایت و با checksum آزموده شود. تغییرات تازهٔ کانفیگ منبع خودکار روی Instanceهای موجود منتشر نمی‌شود و اگر روزی نیاز به مهاجرت عمدی تنظیمات باشد، باید عملیات جداگانه‌ای با حفظ overrideهای مشتری طراحی شود.

**مرجع:** ADR-010 (Base مشترک)، ADR-011 (payload خصوصی اولیه)، ADR-014 (updater انتخابی و حفاظت کانفیگ)، [CS2 Multi-Instance](CS2-MULTI-INSTANCE.md)، [Testing Bench](TESTING-BENCH.md).

## ADR-014 — به‌روزرسانی انتخابی و حفاظت از کانفیگ Instance

**وضعیت:** سیاست موردنظر تأیید شده؛ انتقال آن به pre-start updater پتروداکتیل باید در PoC پیاده‌سازی و آزمایش شود.

**تصمیم:** updater پیش از هر Start فقط پلاگین‌ها، فایل‌های اجرایی/وابستگی و Runtimeهای مدیریت‌شده را به‌روزرسانی می‌کند. این کار mirror کامل یا replace عمومی درخت `addons/` نیست؛ updater باید مسیرهای مجاز را صریحاً مشخص کند و از نوشتن فایل‌های تنظیماتی که داخل پکیج پلاگین‌ها قرار دارند هم جلوگیری کند.

**مسیرهای محافظت‌شده:**
- `game/csgo/cfg/`؛
- فایل‌های `.txt` تعیین‌شده که تنظیمات یا رفتار GameMode را تعریف می‌کنند؛
- `game/csgo/addons/counterstrikesharp/configs/` و تمام زیرشاخه‌های آن، از جمله تنظیمات پلاگین‌ها.

**حفاظت:** updater نباید فایل‌های محافظت‌شده را ایجاد، بازنویسی، حذف یا با نسخهٔ ریپو جایگزین کند. در Provisioning اولیه، baseline آن‌ها یک بار داخل فضای خصوصی Instance قرار می‌گیرد؛ بعد از آن، تغییر دستی مشتری باید با Restart و Update پلاگین‌ها باقی بماند. تغییر کانفیگ در ریپوی منبع به معنی انتشار خودکار روی Instanceهای موجود نیست.

**تفکیک مسیرها:** همهٔ عملیات per-instance روی فضای خصوصی همان Instance انجام می‌شود. هیچ payloadی در مسیر فیزیکی Base Game کپی یا merge نمی‌شود. Update خود بازی CS2 همچنان عملیات مرکزی و جداگانهٔ SteamCMD است.

**معیار پذیرش:** checksum فایل‌های محافظت‌شده قبل و بعد از چند اجرای updater یکسان بماند؛ فقط مسیرهای مجاز پلاگین/Runtime تغییر کنند؛ Instance دوم از تغییرات Instance اول اثر نگیرد؛ و شکست updater مانع Start روی payload ناقص شود.


## ADR-015 — Linux میزبان مرجع؛ Windows فقط محیط تست دستی

**وضعیت:** تصمیم تأییدشده برای مسیر فعلی PoC.

**تصمیم اصلی:** محیط هدف برای نصب و Update بومی CS2، اجرای Instanceها، Pterodactyl Panel/Wings، Base Game مشترک، updaterهای Linux و آزمایش اتصال محلی پلاگین‌ها به MySQL/MariaDB، Linux native روی Debian است. قبولی معماری، جداسازی Instanceها و چرخهٔ عمر باید روی همین محیط ثابت شود.

**نقش Windows:** Windows native به‌عنوان محیط راحت توسعه و تست دستی حفظ می‌شود؛ کاربر می‌تواند سرور مستقل CS2 را اجرا کند، لاگ‌ها و بارگذاری پلاگین‌ها را بررسی کند و تنظیمات پلاگین/کانفیگ را به‌صورت دستی آزمایش و تنظیم کند. این محیط میزبان نهایی Pterodactyl/Wings یا اثبات قبولی Node لینوکس محسوب نمی‌شود.

**مرز اعتبار تست:** موفقیت تست روی Windows تنها همان سناریوی Windows را تأیید می‌کند؛ سازگاری Linux باید جداگانه روی Debian اثبات شود. فایل‌های بازی یا کانفیگ‌های Windows به‌صورت خودکار یا با کپی کامل به Runtime لینوکس منتقل نمی‌شوند؛ تغییرات لازم برای Linux باید در مسیر خصوصی Instance و با روش کنترل‌شده اعمال و اعتبارسنجی شوند.

**ابزارهای مدیریت Windows و cross-platform:** بررسی WindowsGSH، ابزارهای مشابه Windows و مدیرهای عمومی cross-platform از مسیر اصلی PoC خارج و در حالت Deferred می‌ماند، مگر آنکه مسیر Linux/Pterodactyl یک مانع مشخص داشته باشد که بررسی جایگزین را توجیه کند. WSL2 نیز جایگزین تست native Debian نیست.

**دامنهٔ فعلی:** این تصمیم فقط لایهٔ Linux/CS2/Instance/MySQL آزمایشگاهی را پوشش می‌دهد؛ سایت، Billing و اتصال به سامانه‌های فروش تا عبور از مراحل سرور و دیتابیس وارد اجرا نمی‌شوند.

**مرجع:** [Platform PoC](PLATFORM-POC.md)، [CS2 Multi-Instance](CS2-MULTI-INSTANCE.md)، [Testing Bench](TESTING-BENCH.md)، [Roadmap](ROADMAP.md).


## ADR-016 — محیط یکپارچهٔ آزمایشی Pterodactyl روی fc-node-01

**وضعیت:** تصمیم تأییدشده برای PoC؛ Production همچنان Pending.

**تصمیم:** در مرحلهٔ فعلی، Pterodactyl Panel، دیتابیس محلی Panel، Redis و سپس Wings/Docker روی همان Debian 13 VM با hostname برابر fc-node-01 آزمایش شوند. هدف، یادگیری و اثبات اجرای صحیح سرورهای بازی پیش از ادغام فروش و سایت است.

**مرز سایت و دیتابیس:** Flute CMS جداگانه توسعه داده می‌شود و در این مرحله روی Panel نصب یا merge نمی‌شود. MariaDB سایت فعلی cPanel با دیتابیس Pterodactyl یکی نیست و نود به آن اتصال مستقیم نخواهد داشت. اتصال آیندهٔ سایت به Panel از طریق API امن HTTPS بررسی می‌شود.

**نسخهٔ کاندید:** Pterodactyl Panel 1.x stable و Wings 1.x stable؛ قبل از دانلود، release و security advisory جاری دوباره بررسی شود. از نسخهٔ Open Beta برای این مسیر استفاده نمی‌شود مگر تصمیم جداگانه ثبت شود.

**محدودیت منابع ثبت‌شده:** ۴ vCPU، حدود ۵٫۶ GiB RAM و ۲۸ GiB فضای آزاد / در snapshot. این اندازه‌ها ظرفیت چند سرور CS2 را ثابت نمی‌کنند. قبل از ایجاد game container باید فضای مصرف‌شدهٔ نصب native و احتمال دانلود مجدد Base Game بررسی شود.

**معیار خروج:** Panel با دیتابیس مستقل بالا بیاید؛ سپس Wings به Panel متصل شود و یک CS2 server از داخل Panel با چرخهٔ Start/Stop/Restart قابل تکرار اجرا شود. ساخت دو Instance، isolation، File Manager، Backup/Restore و معماری Base Game مشترک پس از قبولی تست نخستین سرور آزمایش می‌شوند.

**شرط بازنگری:** اگر منابع، شبکه، ذخیره‌سازی یا محدودیت‌های VMware مانع اجرای پایدار شدند، پیش از Production محل Panel و Nodeها دوباره تفکیک و تصمیم ثبت شود.

**مرجع:** [Pterodactyl PoC](PTERODACTYL-POC.md)، [Debian PoC Log](DEBIAN-POC.md)، [Roadmap](ROADMAP.md).

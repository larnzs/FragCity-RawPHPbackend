# FragCity — Documentation Audit & Beginner-Friendly Guide

> بازبینی مستندات: ۱۷ اکتبر ۲۰۲۶  
> محدوده: README و ۱۸ سند Markdown در `docs/` (در مجموع ۱۹ فایل)  
> وضعیت: مسیرهای داخلی و تعادل code fenceها دوباره بررسی شدند؛ گام اجرایی بعدی برای نصب Panel آماده شده اما هنوز روی Debian اجرا نشده است.

## ۱. هدف این سند

این گزارش ثبت می‌کند مستندات FragCity چگونه بازبینی شده‌اند، چه ایرادهایی اصلاح شده و از این به بعد آموزش‌ها چه استانداردی باید داشته باشند. این سند جایگزین راهنماهای تخصصی نیست؛ به تو کمک می‌کند بفهمی برای هر کار باید سراغ کدام فایل بروی و چه چیزی را می‌توان تأییدشده دانست.

## ۲. نتیجهٔ بررسی کلی

- در بررسی اولیه، README و ۱۷ سند داخل `docs/` بررسی شدند. پس از افزودن همین گزارش، کل مجموعه ۱۹ فایل Markdown (README و ۱۸ سند زیر `docs/`) دوباره بررسی شد.
- مسیرهای داخلی Markdown با فهرست فایل‌های مخزن تطبیق داده شدند؛ هیچ پیوند داخلی شکسته‌ای پیدا نشد.
- همهٔ ۱۹ فایل از نظر باز و بسته‌شدن fenceهای Markdown (بلوک‌های کد با backtick یا tilde) نیز بررسی شدند؛ بلوک نامتوازن گزارش نشد.
- وضعیت نصب واقعی با آخرین لاگ ترمینال مقایسه شد: PHP 8.3.35، افزونه‌های بررسی‌شده، MariaDB 11.8.6، Redis 8.0.2، Nginx 1.26.3 و Composer 2.10.3 تأیید شده‌اند. سرویس‌های Nginx، MariaDB، Redis و PHP-FPM فعال گزارش شده‌اند.
- خطای اولیهٔ `nginx -v: command not found` با بررسی `sudo /usr/sbin/nginx -v` روشن شد؛ باینری نسخهٔ 1.26.3 را گزارش کرد. مشکل از PATH کاربر بود، نه از فعال نبودن سرویس.
- محدودیت دیسک صریح باقی می‌ماند: حدود 28 GiB آزاد در برابر نصب native CS2 حدود 70 GiB. ساخت CS2 container تا بررسی/حل Storage مسدود است.
- دریافت و استخراج Panel v1.15.1 هنوز انجام نشده است؛ فرمان مرحلهٔ بعد در [Pterodactyl PoC، بخش ۱۱](PTERODACTYL-POC.md) آماده شده است.
- در بازبینی نهایی یک ایراد واقعی در Runbook پیدا شد: بخش‌های ۱۰/۱۱ چند بار تکرار شده بودند و یک فرمان grep برای بررسی extensionهای PHP علامت پایان/quote نداشت. Runbook از نقطهٔ تکرار بازسازی شد؛ حالا بخش ۱۰ و ۱۱ هر کدام فقط یک بار وجود دارند و فرمان grep کامل است.
- مقدمهٔ قدیمی Debian که می‌گفت هیچ مرحله‌ای انجام‌شده نیست، به‌عنوان توضیح تاریخی روشن شد تا با وضعیت اجرایی جدید تناقض نداشته باشد.
- راهنمای Flute در README اکنون قبل از تغییر Virtual Host، backup بیرون از `sites-enabled` و مسیر rollback در صورت شکست Restart All را هم توضیح می‌دهد.

## ۳. اصلاحاتی که در این دور انجام شدند

1. وضعیت قدیمی Composer و Nginx در راهنمای فعلی با نتیجهٔ واقعی نصب همگام شد. snapshotهای قبلی حذف نشدند؛ فقط توضیح داده شد که وضعیت آن‌ها مربوط به زمان قبل از نصب است.
2. چک‌لیست‌های P2.1 و P2.2 به‌روزرسانی شدند تا موارد واقعاً اجراشده تیک بخورند و دریافت Panel، DB، `.env`، APP_KEY، migrations، Nginx، cron و queue worker همچنان Pending بمانند.
3. README به‌عنوان نقطهٔ ورود و نقشهٔ راه تعریف شد؛ فرمان‌ها و توضیحات آن‌ها در یک Runbook مرجع نگه داشته می‌شوند تا در چند فایل کپی نشوند و ناهمگرا نگردند.
4. تکرار ناخواستهٔ بخش‌های Composer/Panel در Runbook حذف شد و فرمان بررسی extensionهای PHP از نظر syntax اصلاح شد.
5. در آموزش Nginx/Flute برای مبتدی‌ها، backup فایل اصلی و مسیر بازگشت در صورت شکست restart افزوده شد.
4. گام بعدی به یک مرحلهٔ محدود تبدیل شد: دریافت asset رسمی release ثابت v1.15.1، بررسی خوانایی archive، استخراج آن و تأیید وجود فایل‌های پایه. این گام هنوز اجرا نشده است.
5. استاندارد status روشن‌تر شد: تیک فقط وقتی زده می‌شود که لاگ یا خروجی آن را ثابت کند؛ برنامهٔ مرحلهٔ بعد با موفقیت واقعی اشتباه گرفته نمی‌شود.
6. لینک‌های داخلی Markdown بررسی شدند و در این بازبینی مسیر شکسته‌ای گزارش نشد.
7. در ممیزی دقیق‌ترِ فرمان‌ها، یک ایراد جدا از ساختار Markdown کشف شد: نقل‌قول بسته‌شدن الگوی `grep` در فرمان تأیید افزونه‌های PHP جا افتاده بود. این مورد در [Pterodactyl PoC، بخش ۹](PTERODACTYL-POC.md) اصلاح و علت آن مستند شد. تراز بودن code fenceها به‌تنهایی صحت نحو Bash را ثابت نمی‌کند؛ فرمان‌های آینده باید علاوه بر بازبینی متن، در صورت امکان با `bash -n` نیز بررسی شوند.

## ۵. استاندارد اجباری برای راهنمای مبتدی‌پسند

هر سندی که به کاربر می‌گوید فرمان اجرا کند یا فایل تنظیمات بسازد، باید تا حد مرتبط این بخش‌ها را داشته باشد:

1. **هدف:** این گام دقیقاً چه خروجی‌ای می‌سازد و چرا لازم است؟
2. **محل اجرا:** فرمان باید در Windows، PowerShell، Debian VM یا مسیر مشخص پروژه اجرا شود؟
3. **پیش‌نیاز:** چه نسخه، فایل، سرویس یا مجوزی باید حاضر باشد؟
4. **فرمان کامل:** فرمان باید قابل کپی باشد و محل تغییر مقادیر placeholder مشخص شود.
5. **توضیح ساده:** گزینه‌ها و مسیرهای اصلی فرمان چه کاری انجام می‌دهند؟
6. **خروجی مورد انتظار:** چه پیام، نسخه، فایل یا وضعیت سرویسی نشان می‌دهد کار موفق بوده؟
7. **رفتار در خطا:** کجا باید توقف کرد؟ چه چیزی را نباید حذف یا دوباره اجرا کرد؟
8. **امنیت و بازگشت:** secrets کجا ذخیره نمی‌شوند؟ آیا مرحله فایل یا دیتابیس موجود را بازنویسی می‌کند؟
9. **ثبت نتیجه:** پس از اجرای واقعی، نسخه، تاریخ و خروجی خلاصه باید در Runbook و لاگ ثبت شود.

اگر یک بخش مرجع معماری، نیازمندی یا تصمیم‌نامه است و قرار نیست فرمان اجرا شود، نباید صرفاً برای تبدیل‌کردن آن به tutorial مراحل ساختگی اضافه شود؛ باید هدف، وضعیت، اصطلاحات و ارتباطش با راهنمای اجرایی شفاف باشد.

## ۶. قواعدی که در ادامه رعایت می‌شوند

- فقط مرحلهٔ بعدی اجرا می‌شود؛ هیچ مرحله‌ای صرفاً برای کوتاه‌کردن مسیر یک‌جا رد نمی‌شود.
- هیچ secret، رمز دیتابیس، `APP_KEY` یا token در README، مستند عمومی یا Git قرار نمی‌گیرد.
- snapshot تاریخی پاک نمی‌شود؛ اگر وضعیت عوض شد، یک نتیجهٔ جدید با تاریخ اضافه می‌شود.
- نسخهٔ هر release نصب‌شده یا کاندید باید با صفحهٔ رسمی آن پروژه تطبیق داده شود.
- موفقیت نصب dependencyها به معنی نصب Panel، موفقیت Panel به معنی اتصال Wings، و اجرای native CS2 به معنی موفقیت container تلقی نمی‌شود.
- هیچ ادعایی دربارهٔ اجرای واقعی نوشته نمی‌شود مگر خروجی یا شواهد آن در دسترس باشد.
- تغییرات این دور فقط مستندات `FragCity-RawPHPbackend` را هدف گرفته‌اند؛ `cs2-kus-addons` در این بازبینی تغییر نکرده است.

## ۷. محدوده و محدودیت ممیزی

این دور، ساختار مستندات، مسیرهای Markdown داخلی، تعادل code fenceها، ارتباط README با راهنماها، خطاهای آشکار در فرمان‌های اصلی Runbook و سازگاری ادعاهای جاری با لاگ نصب اخیر را بررسی کرد. در بلوک بررسی PHP یک خطای نقل‌قول پیدا و اصلاح شد؛ با این حال تمام بلوک‌های shell در یک محیط clean-room به‌صورت خودکار اجرا نشده‌اند. این ممیزی جایگزین اجرای تمام سناریوهای نرم‌افزار، آزمون امنیتی پویا یا بررسی سطر‌به‌سطر تمام فایل‌های PHP نیست. نصب Panel، تنظیم Nginx، دیتابیس Panel، Wings و اجرای سرور CS2 هنوز باید جداگانه اجرا و با خروجی واقعی تأیید شوند.

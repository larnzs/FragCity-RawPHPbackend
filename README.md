> **هدف:** ثبت تصمیم‌های فعلی پیش از ورود به طراحی جزئیات، انتخاب نهایی فناوری‌ها و پیاده‌سازی. این سند در پارت‌های بعدی تکمیل می‌شود؛ تصمیم‌های باز نباید بدون بررسی به‌عنوان تصمیم قطعی در نظر گرفته شوند.

## ۱. چشم‌انداز

FragCity قرار است بستری برای معرفی، مدیریت و در آینده ارائه سرورهای بازی CS2 به مشتریان باشد. معماری باید از همان ابتدا ماژولار طراحی شود تا بتوان با یک سیستم شروع کرد و سپس با اضافه‌شدن دو، چهار یا تعداد بیشتری سیستم فیزیکی، ظرفیت را افزایش داد؛ بدون آنکه برای هر سیستم جدید مجبور به بازنویسی سایت یا ساخت منطق اختصاصی جدید شویم.

**اصل کلیدی:** افزودن یک نود جدید باید عمدتاً از طریق یک فرایند نصب تکرارپذیر و تنظیمات همان نود انجام شود، نه با تغییر کد اصلی سایت.

این موضوع به معنی «فقط کپی‌کردن یک فایل و تمام‌شدن خودکار راه‌اندازی» نیست؛ ابزارهای نصب، ثبت نود، بررسی سلامت و تنظیمات استاندارد نیز باید یک‌بار طراحی شوند تا راه‌اندازی سیستم‌های بعدی از همان الگو پیروی کند.

## ۲. تصمیم‌های پایه این پارت

- **ویندوز میزبان فعلی** برای تست، توسعه و اجرای سرورهای موقتی خودمان باقی می‌ماند.
- **سرورهای مشتریان** روی لینوکس اجرا می‌شوند؛ در شروع، لینوکس داخل ماشین مجازی VMware روی سیستم فعلی اجرا خواهد شد.
- **Pterodactyl** گزینه اصلی مدیریت سرورهای مشتریان است؛ به‌جای بازسازی تمام قابلیت‌های مدیریت سرور در برنامه C#، از پنل و سرویس نود آن استفاده می‌کنیم.
- یک **Pterodactyl Panel مرکزی** می‌تواند چندین نود را مدیریت کند. روی هر نود لینوکسی، Wings سرورهای بازی را با Docker اجرا و مدیریت می‌کند.
- سایت FragCity و زیرساخت اجرای سرورها مسئولیت‌های جدا دارند. سایت نباید خودش مستقیماً فرایندهای سیستم‌عامل را برای اجرای سرورهای مشتری مدیریت کند.
- ریپوی موجود larnzs/cs2-kus-addons زیرساخت فعلی افزونه‌ها و کانفیگ‌های CS2 باقی می‌ماند. در این پارت نیازی به تغییر آن نیست.
- تعداد سرورها و منابع اختصاص‌یافته، بر اساس اندازه‌گیری واقعی و آزمایش مرحله‌ای تعیین می‌شود؛ نه صرفاً بر اساس برآورد اولیه رم.

## ۳. معماری منطقی پیشنهادی

~~~text
بازیکنان
   │
   ├── اتصال مستقیم به IP و پورت سرور بازی
   │
   ▼
سرورهای CS2 در نودهای لینوکسی
   ▲
   │ مدیریت اجرا، توقف، فایل‌ها و منابع
   │
Pterodactyl Wings + Docker (روی هر نود)
   ▲
   │ ارتباط مدیریتی
   │
Pterodactyl Panel (پنل مرکزی)
   ▲
   │ API و یکپارچه‌سازی کنترل‌شده
   │
هسته FragCity / وب‌سایت
   ├── کاربران و دسترسی‌ها
   ├── مالکیت سرورها و پلن‌ها
   └── سفارش‌ها و منطق کسب‌وکار (در پارت‌های بعدی طراحی می‌شود)
~~~

این نمودار مرز مسئولیت‌ها را مشخص می‌کند، نه پیاده‌سازی نهایی تمام سرویس‌ها.

### تفکیک مسئولیت‌ها

**سایت و هسته FragCity**
- مدیریت کاربران، مالکیت و ارتباط سرور با مشتری.
- نگهداری منطق کسب‌وکار و ارائه API برای رابط کاربری و بخش‌های دیگر.
- ارتباط با سامانه مدیریت سرورها از طریق رابط‌های مشخص؛ نه اجرای مستقیم فرایندهای سیستم‌عامل.

**Pterodactyl Panel**
- مدیریت نودها، سرورها و عملیات مدیریتی از طریق یک نقطه مرکزی.
- ارائه API برای یکپارچه‌سازی با FragCity.

**Wings و Docker**
- اجرا و مدیریت سرورهای بازی روی نود لینوکسی.
- کمک به جداسازی محیط هر سرور و اعمال محدودیت‌های RAM و CPU.

**سرور CS2**
- بازیکنان مستقیماً به پورت بازی متصل می‌شوند؛ پنل وب مسیر عبور ترافیک بازی نیست.
- افزونه‌ها و کانفیگ‌های فعلی KUS تا وقتی نیاز مشخصی برای تغییر وجود ندارد، حفظ می‌شوند.

## ۴. ماژولار بودن و اضافه‌کردن سیستم‌های فیزیکی جدید

معماری باید از ابتدا مفهوم **نود (Node)** را مستقل از یک کامپیوتر مشخص بشناسد. یک نود یعنی ماشینی که سرویس اجرای سرورها روی آن نصب و مدیریت می‌شود؛ ممکن است در شروع یک ماشین مجازی باشد و در آینده یک سیستم فیزیکی مستقل.

### الگوی توسعه نودها

1. سایت و هسته FragCity نباید به IP، مسیر نصب یا پورت ثابت یک سیستم خاص وابسته باشند.
2. هر نود باید شناسه، نام، وضعیت، آدرس‌های شبکه و ظرفیت خودش را داشته باشد.
3. نصب وابستگی‌ها و سرویس‌های لازم باید به‌صورت خودکار و تکرارپذیر انجام شود.
4. اطلاعات مختص هر نود از تنظیمات همان نود خوانده شود؛ منطق عمومی در اسکریپت‌ها یا کد اصلی مشترک بماند.
5. اضافه‌کردن یک نود جدید نباید نیازمند تغییرات اختصاصی در کد سمت سایت باشد؛ سایت باید بتواند نود جدید را از مسیر استاندارد شناسایی و مدیریت کند.
6. ظرفیت هر نود باید مستقل قابل تنظیم باشد تا با سخت‌افزار متفاوت، محدودیت منابع متفاوت تعریف شود.
7. خرابی یا آفلاین‌شدن یک نود نباید باعث از دست‌رفتن اطلاعات مالکیت، سفارش یا مشخصات سرورهای سایر نودها شود.
8. عملیات نصب و به‌روزرسانی باید تا حد ممکن تکرارپذیر و قابل بررسی باشند و اطلاعات حساس را در خروجی عمومی یا مخزن کد قرار ندهند.

### طرح تنظیمات

در زمان پیاده‌سازی، تنظیمات را به دو سطح جدا می‌کنیم:

- **تنظیمات عمومی محیط:** آدرس سرویس‌های مرکزی و تنظیمات مشترک محیط.
- **تنظیمات هر نود:** شناسه و نام نود، آدرس‌های شبکه، محدوده پورت‌های اختصاص‌یافته، محدودیت منابع، برچسب‌ها و ظرفیت هدف.

توکن‌ها، رمزها، کلیدهای API و سایر اطلاعات محرمانه باید خارج از تنظیمات قابل انتشار و خارج از Git نگهداری شوند. فایل تنظیمات Wings نیز باید با روش معتبر خود Pterodactyl تولید و مدیریت شود؛ قرار نیست اطلاعات محرمانه پنل را داخل README یا کد سمت مرورگر قرار دهیم.

**هدف نهایی این بخش:** خرید سیستم جدید باید به معنی اجرای همان فرایند استاندارد نصب، واردکردن تنظیمات مخصوص نود، ثبت آن در پنل مرکزی و بررسی سلامت باشد؛ نه ساخت نسخه‌ای جداگانه از FragCity برای هر کامپیوتر.

## ۵. سخت‌افزار فعلی و ظرفیت شروع

### مشخصات فعلی

| بخش | وضعیت |
|---|---|
| پردازنده | AMD Ryzen 5 8400F، دارای ۶ هسته و ۱۲ رشته |
| رم | ۱۶ گیگابایت DDR5 با سرعت ۵۶۰۰ مگاهرتز |
| میزبان فعلی | Windows |
| نود اولیه مشتریان | ماشین مجازی Linux روی VMware |
| اتصال اینترنت | IP ثابت، اینترنت و Port Forwarding در دسترس هستند |
| سرور و افزونه‌ها | سرورهای فعلی KUS روی ویندوز تست شده‌اند؛ مسیر لینوکسی نیز طبق تست‌های انجام‌شده کار می‌کند |

### رویکرد ظرفیت

- **هدف اولیه:** رسیدن به ۵ سرور پایدار.
- پس از اندازه‌گیری، ظرفیت را مرحله‌ای افزایش می‌دهیم.
- **۸ تا ۱۰ سرور هدف کششی است، نه تضمین فعلی.** امکان اجرای هم‌زمان به گیم‌مود، مپ، تعداد بازیکن، افزونه‌ها، مصرف واقعی RAM، بار CPU و منابعی که برای ویندوز و خود VM مصرف می‌شوند بستگی دارد.

برآورد ۵۰۰ مگابایت تا ۱ گیگابایت رم به‌ازای هر سرور، صرفاً تخمین شروع است. باید مصرف واقعی در حالت خالی و در زمان بازی اندازه‌گیری شود.

### برنامه سنجش

ظرفیت را مرحله‌ای و با ثبت داده بررسی می‌کنیم:

1. اجرای یک سرور و ثبت مصرف پایه.
2. اجرای سه سرور و بررسی مصرف RAM، CPU و پایداری.
3. اجرای پنج سرور و آزمایش با بار نزدیک به استفاده واقعی.
4. فقط در صورت وجود حاشیه کافی، افزایش تعداد سرورها.

هنگام این تست‌ها باید مصرف خود ویندوز، حافظه اختصاص‌یافته به VM، سیستم لینوکس، Docker و سرویس‌های مدیریتی نیز محاسبه شود. پرشدن RAM یا فشار بیش از حد CPU می‌تواند باعث افت کیفیت یا ناپایداری شود؛ بنابراین محدودیت منابع باید واقعی و متناسب با نود تنظیم شود.

## ۶. لینوکس و امنیت پایه

هدف، استفاده از سیستم‌عاملی سبک و بدون محیط گرافیکی است تا منابع اضافه صرف سرویس‌های غیرضروری نشود.

- **انتخاب اولیه برای آزمایش: Debian Minimal.** نسخه دقیق نهایی پس از نصب آزمایشی و تأیید سازگاری Pterodactyl، Docker، سرور CS2 و افزونه‌ها تثبیت می‌شود. مستندات فعلی Pterodactyl نسخه‌های Debian 12 و 13 را برای نصب Panel و نسخه‌های 11 تا 13 را برای Wings فهرست کرده‌اند.
- نودهای مشتریان باید از طریق Docker و محدودیت‌های منابع مدیریت شوند؛ کانتینر به‌تنهایی تضمین امنیت کامل نیست.
- سرویس‌های مدیریتی و پورت‌های بازی باید جداگانه برنامه‌ریزی شوند.
- دسترسی مدیریتی غیرضروری نباید بی‌دلیل در اینترنت عمومی باز باشد.
- روش تهیه نسخه پشتیبان، ثبت رویدادها، به‌روزرسانی امن و بازیابی پس از خرابی در پارت‌های بعدی مشخص خواهد شد.

## ۷. شبکه و پورت‌ها

IP ثابت، اینترنت و Port Forwarding فعلی در دسترس هستند. برای نود لینوکسی داخل VMware، حالت **Bridged** گزینه اولیه برای آزمایش است تا VM در شبکه محلی آدرس مستقل داشته باشد و مسیر هدایت پورت‌ها ساده‌تر شود.

در طراحی نهایی باید این موارد مستقل از کد سایت و برای هر نود قابل تنظیم باشند:
- آدرس مدیریتی نود و آدرس قابل دسترسی بازیکنان.
- محدوده پورت‌های اختصاص‌یافته به سرورهای بازی.
- پورت‌ها و مسیرهای ارتباطی مورد نیاز Panel و Wings.
- قوانین فایروال و دسترسی‌های مدیریتی.

جزئیات واقعی آدرس‌دهی و تخصیص پورت در مرحله نصب نود و تست شبکه تعیین می‌شوند؛ این README جایگزین تنظیمات اجرایی نیست.

## ۸. حفظ زیرساخت فعلی KUS

ریپوی larnzs/cs2-kus-addons و کانفیگ‌های فعلی، زیرساخت بازی موجود هستند و در این مرحله تغییر نمی‌کنند.

هنگام پیاده‌سازی باید:
- نصب و اجرای سرور روی Linux با ساختار نودهای Pterodactyl هماهنگ شود.
- روش به‌روزرسانی افزونه‌ها و فایل‌های بازی تا حد ممکن با فرایند فعلی سازگار بماند.
- فایل‌های شخصی، کانفیگ‌ها و تنظیمات موجود بدون نیاز مشخص و بررسی اثر تغییر، حذف یا بازنویسی نشوند.
- تست Windows و Linux به‌عنوان دو محیط جدا در نظر گرفته شود؛ تأیید یک محیط به‌تنهایی جایگزین تست محیط دیگر نیست.

## ۹. مواردی که در پارت ۱ هنوز تعیین تکلیف نشده‌اند

این موارد عمداً باز می‌مانند تا قبل از تصمیم‌گیری، معماری موجود و گزینه‌ها به‌صورت جداگانه بررسی شوند:

- انتخاب نهایی فناوری هسته وب و نحوه توسعه یا نوسازی بخش PHP.
- نقش آینده برنامه C# و اینکه کدام مسئولیت‌ها باید حذف، حفظ یا به API منتقل شوند.
- مدل دقیق اتصال سایت به Pterodactyl و اینکه کدام عملیات از رابط اختصاصی FragCity انجام شوند.
- مدل داده و مرجع اصلی اطلاعات کاربران، سفارش‌ها، مالکیت سرورها و وضعیت اجرای آن‌ها.
- سیاست بکاپ، مانیتورینگ، به‌روزرسانی و بازیابی.
- نحوه مهاجرت از پیاده‌سازی موجود، بدون قطع سرویس یا از دست‌رفتن کانفیگ‌ها.
- ظرفیت نهایی سرورها برای سخت‌افزار فعلی و معیارهای لازم برای اضافه‌کردن نود جدید.

## ۱۰. خروجی مورد انتظار پارت ۱

در پایان این پارت، تصمیم پایه این است:

> FragCity به‌صورت یک سامانه مرکزی و ماژولار ساخته می‌شود که مدیریت کسب‌وکار را از اجرای سرورهای بازی جدا نگه می‌دارد. ویندوز فعلی برای تست و سرورهای موقت باقی می‌ماند؛ سرورهای مشتریان از طریق نودهای لینوکسی و Pterodactyl مدیریت می‌شوند. معماری از روز اول برای چند نود طراحی خواهد شد، به‌طوری که افزودن سیستم‌های فیزیکی جدید از فرایند نصب استاندارد و تنظیمات اختصاصی نود پیروی کند، نه از تغییر کد اصلی سایت.

**پارت بعدی:** بررسی معماری سایت و هسته FragCity، ارتباط با Pterodactyl و تعیین نقش واقعی برنامه C#؛ بدون شروع بازنویسی یا تغییر ریپوها تا زمانی که تصمیم‌ها مستند و روشن شوند.

# پارت ۲ — آماده‌سازی Debian و VMware و آزمایش نخستین سرور CS2

> **وضعیت:** برنامه اجرایی آماده است؛ تا وقتی نصب و آزمایش روی سیستم واقعی انجام نشده، هیچ‌کدام از مراحل این بخش «انجام‌شده» محسوب نمی‌شوند. پس از تست، نتیجه واقعی و تنظیمات نهایی در همین سند ثبت خواهد شد.

## ۱. هدف این پارت

در این مرحله قرار است روی کامپیوتر فعلی FragCity:

1. یک ماشین مجازی سبک Debian داخل VMware ساخته شود.
2. شبکه VM طوری تنظیم شود که لینوکس آدرس محلی مستقل داشته باشد.
3. ابزارهای پایه نصب و صحت سیستم‌عامل، شبکه، رم و فضای دیسک بررسی شوند.
4. نسخه Linux موجود سرور KUS به‌صورت محلی روی VM نصب شود.
5. ابتدا نصب و انتقال فایل‌ها بدون راه‌اندازی خودکار سرور انجام شود؛ سپس تنظیمات لازم بررسی و یک سرور CS2 به‌صورت آزمایشی اجرا شود.
6. RAM، CPU، پایداری و اتصال شبکه ثبت شوند تا مبنای تصمیم‌های ظرفیت‌سنجی باشند.

**در این پارت Pterodactyl نصب نمی‌شود.** ابتدا باید مطمئن شویم Debian و سرور CS2 با افزونه‌ها و تنظیمات موجود درست کار می‌کنند. اتصال این نصب آزمایشی به Pterodactyl در مرحله جداگانه بررسی می‌شود؛ ساختار اجرای مستقیم KUS و اجرای مدیریت‌شده داخل Docker یکسان فرض نمی‌شوند.

## ۲. نسخه Debian انتخاب‌شده برای آزمایش

نسخه منتخب برای نصب آزمایشی، **Debian 13.7 (Trixie)، معماری amd64** است. طبق صفحه رسمی Debian، نسخه 13.7 در ۱۲ سپتامبر ۲۰۲۶ منتشر شده و نسخه پایدار جاری در زمان تدوین این پارت است. در روز نصب، صفحه رسمی را دوباره بررسی می‌کنیم؛ اگر نسخه پایدار 13.x جدیدتری منتشر شده باشد، آخرین ISO پایدار را ترجیح می‌دهیم.

- [صفحه رسمی دانلود Debian](https://www.debian.org/distrib/)
- [Debian netinst — نصب شبکه‌ای](https://www.debian.org/distrib/netinst)
- [فهرست انتشارهای Debian](https://www.debian.org/releases/index.en.html)

### فایل ISO

فایل **64-bit PC netinst ISO (amd64)** را دانلود کن. با توجه به اینکه VM در زمان نصب اینترنت خواهد داشت، netinst انتخاب مناسبی برای نصب بدون محیط گرافیکی است. به ISO نسخه Live نیازی نداریم.

## ۳. تنظیمات اولیه ماشین مجازی

این مقادیر برای **مرحله نصب و آزمایش یک سرور CS2** پیشنهاد شده‌اند؛ تنظیمات نهایی ظرفیت چند سرور بعد از اندازه‌گیری تعیین می‌شوند.

| گزینه | مقدار اولیه | توضیح |
|---|---|---|
| نام VM | **FragCity-Debian-Node01** | نام واضح برای اولین نود آزمایشی |
| سیستم‌عامل مهمان | Debian 13، 64-bit | در صورت نبودن نسخه دقیق، نزدیک‌ترین گزینه Debian 64-bit |
| vCPU | ۴ هسته مجازی | یک پردازنده مجازی با ۴ هسته، در صورت امکان |
| RAM | ۶ گیگابایت (۶۱۴۴ مگابایت) | برای نصب و تست یک سرور؛ تضمین‌کننده اجرای ۵ تا ۱۰ سرور نیست |
| دیسک | ۱۰۰ گیگابایت، Thin Provision | فضای میزبانی واقعی باید کافی باشد؛ Thin بودن جلوی مصرف واقعی فضای فایل‌های بازی را نمی‌گیرد |
| نوع شبکه | Bridged | VM در شبکه محلی IP مستقل می‌گیرد |
| محیط گرافیکی | نصب نشود | منابع فقط به سرویس‌های لازم اختصاص داده شوند |
| فایل‌های VM | روی SSD | عملکرد و زمان بارگذاری بهتر از دیسک کندتر |

### احتیاط درباره منابع

سیستم میزبان ۱۶ گیگابایت رم دارد؛ بنابراین هنگام روشن بودن VM بخشی از حافظه همچنان برای Windows و برنامه‌های ضروری میزبان لازم است. فعلاً ۶ گیگابایت به VM اختصاص داده می‌شود و تا قبل از سنجش مصرف واقعی، افزایش رم یا تعداد سرورها را قطعی نمی‌دانیم. قابلیت رزرو تمام حافظه VM در VMware فعال نشود.

پیش از ساخت دیسک، فضای واقعی خالی میزبان بررسی شود. Thin Provision به این معنی نیست که فایل‌های CS2 و به‌روزرسانی‌ها فضای فیزیکی مصرف نمی‌کنند.

## ۴. مراحل نصب Debian

در نصب‌کننده Debian از این مقادیر استفاده شود:

| گزینه | مقدار پیشنهادی |
|---|---|
| Hostname | **fc-node-01** |
| Domain name | خالی، مگر اینکه دامنه داخلی مشخصی وجود داشته باشد |
| کاربر مدیریتی | یک کاربر معمولی، مثلاً **fragcityadmin** |
| حساب root | می‌توان فیلد رمز root را خالی گذاشت تا حساب root مستقیم غیرفعال شود و کاربر اولیه از sudo استفاده کند |
| پارتیشن‌بندی | استفاده از کل دیسک مجازی VM؛ دیسک میزبان Windows انتخاب یا تغییر داده نشود |
| SSH server | نصب شود |
| محیط دسکتاپ | انتخاب نشود |
| Standard system utilities | انتخاب شود |

این پارتیشن‌بندی فقط روی دیسک مجازی انجام می‌شود. هنگام نصب، نام دیسک و خلاصه تغییرات را کنترل کن تا هیچ دیسک فیزیکی میزبان انتخاب نشود.

## ۵. به‌روزرسانی اولیه و ابزارهای پایه

پس از اولین بوت و ورود با کاربر مدیریتی:

~~~bash
sudo apt update
sudo apt full-upgrade -y
sudo apt install -y git curl ca-certificates nano htop tmux jq rsync unzip tar xz-utils dnsutils netcat-openbsd openssh-server
sudo systemctl enable --now ssh
sudo reboot
~~~

پس از راه‌اندازی مجدد، بررسی اولیه انجام شود:

~~~bash
cat /etc/os-release
uname -m
ip -br address
ip route
free -h
df -h /
nproc
systemctl status ssh --no-pager
~~~

انتظار می‌رود نسخه سیستم Debian 13.x و معماری x86_64 باشد؛ رابط شبکه باید آدرس معتبر محلی و مسیر پیش‌فرض داشته باشد. مقدار واقعی RAM، فضای آزاد و تعداد CPU قابل مشاهده نیز ثبت شود.

## ۶. شبکه VMware و مسیریابی

**Bridged** حالت اولیه شبکه است تا VM یک آدرس IP محلی مستقل داشته باشد. پس از نصب:

- آدرس IP ماشین مجازی با دستور **ip -br address** مشخص شود.
- بررسی شود که دستور **ip route** مسیر پیش‌فرض معتبری نشان می‌دهد.
- اتصال اینترنت از داخل Debian آزمایش شود.
- ترجیحاً برای MAC ماشین مجازی در روتر DHCP reservation تعریف شود تا آدرس داخلی نود مرتب عوض نشود.
- Port Forwarding سرور آزمایشی باید به IP خود VM اشاره کند، نه به IP محلی Windows میزبان.
- پورت‌های مدیریتی SSH و پنل‌های مدیریتی را بدون نیاز و بررسی امنیتی به اینترنت عمومی باز نکنیم.
- اگر Windows و VM قرار است هم‌زمان سرورهایی با یک پورت مشابه اجرا کنند، مقصد و قواعد هدایت پورت باید جداگانه بررسی شوند.

پورت‌های نهایی و قواعد فایروال هنوز در این مرحله تثبیت نشده‌اند و پس از مشاهده IP واقعی VM تعیین می‌شوند.

## ۷. دریافت و آماده‌سازی نسخه Linux ریپوی KUS

ریپوی **larnzs/cs2-kus-addons** و شاخه **integration/kus-monorepo** زیرساخت موجود سرور بازی هستند. برای نصب آزمایشی می‌توان نسخه مخزن را روی VM کلون کرد و از ورودی‌های Linux موجود استفاده کرد؛ **این کار مجوز ویرایش، commit یا push کردن تغییرات به ریپو نیست.**

مسیرهای موجود برای مطالعه قبل از اجرا:

- [راهنمای Linux](https://github.com/larnzs/cs2-kus-addons/blob/integration/kus-monorepo/linux/README.md)
- [اسکریپت نصب Linux](https://github.com/larnzs/cs2-kus-addons/blob/integration/kus-monorepo/linux/install.sh)
- [اسکریپت به‌روزرسانی Linux](https://github.com/larnzs/cs2-kus-addons/blob/integration/kus-monorepo/linux/update.sh)
- [اسکریپت اجرای Linux](https://github.com/larnzs/cs2-kus-addons/blob/integration/kus-monorepo/linux/run.sh)

به دلیل خصوصی بودن مخزن، دریافت آن باید با دسترسی مجاز GitHub انجام شود. احراز هویت و توکن‌ها را در دستورهای قابل ذخیره، لاگ یا فایل tracked قرار نده.

### هشدار مهم برای اجرای اسکریپت‌ها

**در تست اولیه، linux/update.sh اجرا نشود.** طبق نسخه‌ای که برای این پارت بررسی شد، این ورودی مسیر به‌روزرسانی افزونه‌ها را فعال می‌کند و فرایند نصبِ فراخوانی‌شده با RUN_PLUGIN_UPDATER=1 ممکن است تلاش کند تغییرات افزونه‌ها را به شاخه integration/kus-monorepo push کند. این رفتار برای یک تست محلی اولیه لازم نیست و با اصل عدم‌تغییر مخزن در این پارت سازگار نیست.

پیش از هر اجرا باید نسخه فعلی اسکریپت‌ها دوباره بررسی شود. برای نصب آزمایشی، مسیر مستقیم نصب با حالت **عدم شروع سرور** مدنظر است:

~~~bash
sudo env -u RUN_PLUGIN_UPDATER UPDATE_ONLY=1 bash ./linux/install.sh
~~~

این دستور صرفاً روی VM اجرا شود، از پوشه clone همان ریپو و پس از بررسی دستی اسکریپت. در نسخه‌ای که بررسی شده، حالت UPDATE_ONLY=1 اجازه نصب و به‌روزرسانی فایل‌های بازی و overlay کردن payload را می‌دهد اما از شروع CS2 در انتهای همان اسکریپت جلوگیری می‌کند. پاکسازی یا حذف فایل‌های موجود از سمت این فرایند مجاز نیست و کانفیگ‌های دستی باید محفوظ بمانند.

این اسکریپت ممکن است بسته‌های Debian را به‌روزرسانی کند و فایل‌های Steam Linux Runtime و CS2 را دانلود کند؛ برای همین فضای آزاد میزبان و VM باید کافی باشد.

> **قانون ثابت:** از طریق این فرایند هیچ commit، push یا تغییر محتوایی در ریپوی cs2-kus-addons ایجاد نمی‌کنیم. اگر در آینده تغییر در خود ریپو لازم شود، فقط پس از درخواست صریح کاربر بررسی خواهد شد.

## ۸. راه‌اندازی آزمایشی نخستین سرور

بعد از اتمام نصب با UPDATE_ONLY=1، هنوز نباید سرور را کورکورانه اجرا کرد. ابتدا باید موارد زیر بررسی شوند:

1. وجود فایل اجرایی CS2 و فایل‌های runtime لینوکس.
2. نتیجه overlay شدن payload و وجود افزونه‌های مورد انتظار.
3. سلامت فایل gameinfo.gi در runtime نصب‌شده.
4. مسیر و محتوای کانفیگ مورد استفاده سرور و مقادیر پورت، مپ، ظرفیت بازیکن و رمز RCON.
5. نحوه شروع از طریق ورودی Linux مناسب، بدون فعال شدن ناخواسته updater.
6. اطمینان از اینکه رمز RCON قوی، یکتا و خارج از Git است؛ رمز واقعی نباید در README ثبت شود.

پس از این بررسی‌ها، روش اجرای سرور برای همین VM و همین نسخه اسکریپت تثبیت می‌شود. فرمان شروع و مقادیر واقعی فقط بعد از بررسی فایل‌های فعلی و مشخص شدن تنظیمات مورد نیاز ثبت خواهند شد؛ این سند فعلاً موفقیت اجرای سرور را ادعا نمی‌کند.

## ۹. معیارهای پذیرش پارت ۲

پارت ۲ فقط زمانی تکمیل‌شده محسوب می‌شود که این موارد روی سیستم واقعی بررسی شده باشند:

- [ ] Debian 13.x پایدار نصب و نسخه دقیق آن ثبت شده باشد.
- [ ] VM بدون محیط دسکتاپ بوت شود و دسترسی کنسول/SSH کار کند.
- [ ] VM آدرس مستقل محلی، مسیر پیش‌فرض و اتصال اینترنت داشته باشد.
- [ ] فضای آزاد میزبان و VM برای فایل‌های بازی و آپدیت کافی باشد.
- [ ] payload موردنیاز Linux نصب شده باشد، بدون دستکاری مخزن GitHub.
- [ ] هیچ updater ناخواسته‌ای که commit یا push کند اجرا نشده باشد.
- [ ] اولین سرور CS2 روی Linux بالا بیاید و از شبکه قابل دسترسی باشد.
- [ ] مصرف RAM و CPU در حالت بدون بازیکن و طی تست واقعی ثبت شود.
- [ ] لاگ‌های شروع و هر خطای مهم بررسی و نتیجه ثبت شود.

اگر هر مورد شکست خورد، ابتدا همان مرحله عیب‌یابی می‌شود؛ قبل از اثبات پایداری یک سرور، نصب Pterodactyl یا افزایش تعداد سرورها را هم‌زمان وارد این آزمایش نمی‌کنیم.

## ۱۰. خروجی مورد انتظار پارت ۲

> هدف پارت ۲، آماده‌سازی یک Debian minimal روی VMware و اجرای آزمایشی یک سرور CS2 با Linux payload فعلی است. در این مرحله پارامترهای VM به‌صورت اولیه روی ۴ vCPU، رم ۶ گیگابایت، دیسک مجازی Thin با ظرفیت ۱۰۰ گیگابایت و شبکه Bridged پیشنهاد شده‌اند. انتخاب Debian 13.7 amd64 مبنای شروع است، ولی نسخه دقیق نصب‌شده باید از خروجی سیستم ثبت شود. این پارت تنها پس از آزمایش واقعی شبکه، نصب payload، اجرای سرور و ثبت مصرف منابع کامل خواهد شد.

**مرحله بعد پس از تست:** ثبت نتیجه واقعی و حل مشکلات احتمالی اجرای CS2؛ سپس تصمیم درباره نحوه انتقال نصب به معماری نودهای Pterodactyl، بدون بازنویسی یا تغییر شتاب‌زده زیرساخت موجود.

# FragCity — مستند پایه معماری و مسیر توسعه

> **وضعیت سند:** پارت ۱ ثبت شده؛ پارت ۲ در حال اجرا و فعلاً **Pending** است.  
> **هدف:** ثبت تصمیم‌های فعلی پیش از ورود به طراحی جزئیات، انتخاب نهایی فناوری‌ها و پیاده‌سازی. این سند در پارت‌های بعدی تکمیل می‌شود؛ تصمیم‌های باز نباید بدون بررسی به‌عنوان تصمیم قطعی در نظر گرفته شوند.

## ۱. چشم‌انداز

FragCity قرار است بستری برای معرفی، مدیریت و در آینده ارائه سرورهای بازی CS2 به مشتریان باشد. معماری باید از همان ابتدا ماژولار طراحی شود تا بتوان با یک سیستم شروع کرد و سپس با اضافه‌شدن دو، چهار یا تعداد بیشتری سیستم فیزیکی، ظرفیت را افزایش داد؛ بدون آنکه برای هر سیستم جدید مجبور به بازنویسی سایت یا ساخت منطق اختصاصی جدید شویم.

**اصل کلیدی:** افزودن یک نود جدید باید عمدتاً از طریق یک فرایند نصب تکرارپذیر و تنظیمات همان نود انجام شود، نه با تغییر کد اصلی سایت.

این موضوع به معنی «فقط کپی‌کردن یک فایل و تمام‌شدن خودکار راه‌اندازی» نیست؛ ابزارهای نصب، ثبت نود، بررسی سلامت و تنظیمات استاندارد نیز باید یک‌بار طراحی شوند تا راه‌اندازی سیستم‌های بعدی از همان الگو پیروی کند.

## ۲. تصمیم‌های پایه این پارت

- **ویندوز میزبان فعلی** برای تست، توسعه و اجرای سرورهای موقتی خودمان باقی می‌ماند.
- **سرورهای مشتریان** روی لینوکس اجرا می‌شوند؛ در شروع، لینوکس داخل ماشین مجازی VMware روی سیستم فعلی اجرا خواهد شد.
- **Pterodactyl** گزینه اصلی مدیریت سرورهای مشتریان است؛ به‌جای بازسازی تمام قابلیت‌های مدیریت سرور در برنامه C#، از پنل و سرویس نود آن استفاده می‌کنیم.
- یک **Pterodactyl Panel مرکزی** می‌تواند چندین نود را مدیریت کند. روی هر نود لینوکسی، Wings سرورهای بازی را با Docker اجرا و مدیریت می‌کند.
- سایت FragCity و زیرساخت اجرای سرورها مسئولیت‌های جدا دارند. سایت نباید خودش مستقیماً فرایندهای سیستم‌عامل را برای اجرای سرورهای مشتری مدیریت کند.
- ریپوی موجود larnzs/cs2-kus-addons زیرساخت فعلی افزونه‌ها و کانفیگ‌های CS2 باقی می‌ماند. در این پارت نیازی به تغییر آن نیست.
- تعداد سرورها و منابع اختصاص‌یافته، بر اساس اندازه‌گیری واقعی و آزمایش مرحله‌ای تعیین می‌شود؛ نه صرفاً بر اساس برآورد اولیه رم.

## ۳. معماری منطقی پیشنهادی

~~~text
بازیکنان
   │
   ├── اتصال مستقیم به IP و پورت سرور بازی
   │
   ▼
سرورهای CS2 در نودهای لینوکسی
   ▲
   │ مدیریت اجرا، توقف، فایل‌ها و منابع
   │
Pterodactyl Wings + Docker (روی هر نود)
   ▲
   │ ارتباط مدیریتی
   │
Pterodactyl Panel (پنل مرکزی)
   ▲
   │ API و یکپارچه‌سازی کنترل‌شده
   │
هسته FragCity / وب‌سایت
   ├── کاربران و دسترسی‌ها
   ├── مالکیت سرورها و پلن‌ها
   └── سفارش‌ها و منطق کسب‌وکار (در پارت‌های بعدی طراحی می‌شود)
~~~

این نمودار مرز مسئولیت‌ها را مشخص می‌کند، نه پیاده‌سازی نهایی تمام سرویس‌ها.

### تفکیک مسئولیت‌ها

**سایت و هسته FragCity**
- مدیریت کاربران، مالکیت و ارتباط سرور با مشتری.
- نگهداری منطق کسب‌وکار و ارائه API برای رابط کاربری و بخش‌های دیگر.
- ارتباط با سامانه مدیریت سرورها از طریق رابط‌های مشخص؛ نه اجرای مستقیم فرایندهای سیستم‌عامل.

**Pterodactyl Panel**
- مدیریت نودها، سرورها و عملیات مدیریتی از طریق یک نقطه مرکزی.
- ارائه API برای یکپارچه‌سازی با FragCity.

**Wings و Docker**
- اجرا و مدیریت سرورهای بازی روی نود لینوکسی.
- کمک به جداسازی محیط هر سرور و اعمال محدودیت‌های RAM و CPU.

**سرور CS2**
- بازیکنان مستقیماً به پورت بازی متصل می‌شوند؛ پنل وب مسیر عبور ترافیک بازی نیست.
- افزونه‌ها و کانفیگ‌های فعلی KUS تا وقتی نیاز مشخصی برای تغییر وجود ندارد، حفظ می‌شوند.

## ۴. ماژولار بودن و اضافه‌کردن سیستم‌های فیزیکی جدید

معماری باید از ابتدا مفهوم **نود (Node)** را مستقل از یک کامپیوتر مشخص بشناسد. یک نود یعنی ماشینی که سرویس اجرای سرورها روی آن نصب و مدیریت می‌شود؛ ممکن است در شروع یک ماشین مجازی باشد و در آینده یک سیستم فیزیکی مستقل.

### الگوی توسعه نودها

1. سایت و هسته FragCity نباید به IP، مسیر نصب یا پورت ثابت یک سیستم خاص وابسته باشند.
2. هر نود باید شناسه، نام، وضعیت، آدرس‌های شبکه و ظرفیت خودش را داشته باشد.
3. نصب وابستگی‌ها و سرویس‌های لازم باید به‌صورت خودکار و تکرارپذیر انجام شود.
4. اطلاعات مختص هر نود از تنظیمات همان نود خوانده شود؛ منطق عمومی در اسکریپت‌ها یا کد اصلی مشترک بماند.
5. اضافه‌کردن یک نود جدید نباید نیازمند تغییرات اختصاصی در کد سمت سایت باشد؛ سایت باید بتواند نود جدید را از مسیر استاندارد شناسایی و مدیریت کند.
6. ظرفیت هر نود باید مستقل قابل تنظیم باشد تا با سخت‌افزار متفاوت، محدودیت منابع متفاوت تعریف شود.
7. خرابی یا آفلاین‌شدن یک نود نباید باعث از دست‌رفتن اطلاعات مالکیت، سفارش یا مشخصات سرورهای سایر نودها شود.
8. عملیات نصب و به‌روزرسانی باید تا حد ممکن تکرارپذیر و قابل بررسی باشند و اطلاعات حساس را در خروجی عمومی یا مخزن کد قرار ندهند.

### طرح تنظیمات

در زمان پیاده‌سازی، تنظیمات را به دو سطح جدا می‌کنیم:

- **تنظیمات عمومی محیط:** آدرس سرویس‌های مرکزی و تنظیمات مشترک محیط.
- **تنظیمات هر نود:** شناسه و نام نود، آدرس‌های شبکه، محدوده پورت‌های اختصاص‌یافته، محدودیت منابع، برچسب‌ها و ظرفیت هدف.

توکن‌ها، رمزها، کلیدهای API و سایر اطلاعات محرمانه باید خارج از تنظیمات قابل انتشار و خارج از Git نگهداری شوند. فایل تنظیمات Wings نیز باید با روش معتبر خود Pterodactyl تولید و مدیریت شود؛ قرار نیست اطلاعات محرمانه پنل را داخل README یا کد سمت مرورگر قرار دهیم.

**هدف نهایی این بخش:** خرید سیستم جدید باید به معنی اجرای همان فرایند استاندارد نصب، واردکردن تنظیمات مخصوص نود، ثبت آن در پنل مرکزی و بررسی سلامت باشد؛ نه ساخت نسخه‌ای جداگانه از FragCity برای هر کامپیوتر.

## ۵. سخت‌افزار فعلی و ظرفیت شروع

### مشخصات فعلی

| بخش | وضعیت |
|---|---|
| پردازنده | AMD Ryzen 5 8400F، دارای ۶ هسته و ۱۲ رشته |
| رم | ۱۶ گیگابایت DDR5 با سرعت ۵۶۰۰ مگاهرتز |
| میزبان فعلی | Windows |
| نود اولیه مشتریان | ماشین مجازی Linux روی VMware |
| اتصال اینترنت | IP ثابت، اینترنت و Port Forwarding در دسترس هستند |
| سرور و افزونه‌ها | سرورهای فعلی KUS روی ویندوز تست شده‌اند؛ مسیر لینوکسی نیز طبق تست‌های انجام‌شده کار می‌کند |

### رویکرد ظرفیت

- **هدف اولیه:** رسیدن به ۵ سرور پایدار.
- پس از اندازه‌گیری، ظرفیت را مرحله‌ای افزایش می‌دهیم.
- **۸ تا ۱۰ سرور هدف کششی است، نه تضمین فعلی.** امکان اجرای هم‌زمان به گیم‌مود، مپ، تعداد بازیکن، افزونه‌ها، مصرف واقعی RAM، بار CPU و منابعی که برای ویندوز و خود VM مصرف می‌شوند بستگی دارد.

برآورد ۵۰۰ مگابایت تا ۱ گیگابایت رم به‌ازای هر سرور، صرفاً تخمین شروع است. باید مصرف واقعی در حالت خالی و در زمان بازی اندازه‌گیری شود.

### برنامه سنجش

ظرفیت را مرحله‌ای و با ثبت داده بررسی می‌کنیم:

1. اجرای یک سرور و ثبت مصرف پایه.
2. اجرای سه سرور و بررسی مصرف RAM، CPU و پایداری.
3. اجرای پنج سرور و آزمایش با بار نزدیک به استفاده واقعی.
4. فقط در صورت وجود حاشیه کافی، افزایش تعداد سرورها.

هنگام این تست‌ها باید مصرف خود ویندوز، حافظه اختصاص‌یافته به VM، سیستم لینوکس، Docker و سرویس‌های مدیریتی نیز محاسبه شود. پرشدن RAM یا فشار بیش از حد CPU می‌تواند باعث افت کیفیت یا ناپایداری شود؛ بنابراین محدودیت منابع باید واقعی و متناسب با نود تنظیم شود.

## ۶. لینوکس و امنیت پایه

هدف، استفاده از سیستم‌عاملی سبک و بدون محیط گرافیکی است تا منابع اضافه صرف سرویس‌های غیرضروری نشود.

- **انتخاب اولیه برای آزمایش: Debian Minimal.** نسخه دقیق نهایی پس از نصب آزمایشی و تأیید سازگاری Pterodactyl، Docker، سرور CS2 و افزونه‌ها تثبیت می‌شود. مستندات فعلی Pterodactyl نسخه‌های Debian 12 و 13 را برای نصب Panel و نسخه‌های 11 تا 13 را برای Wings فهرست کرده‌اند.
- نودهای مشتریان باید از طریق Docker و محدودیت‌های منابع مدیریت شوند؛ کانتینر به‌تنهایی تضمین امنیت کامل نیست.
- سرویس‌های مدیریتی و پورت‌های بازی باید جداگانه برنامه‌ریزی شوند.
- دسترسی مدیریتی غیرضروری نباید بی‌دلیل در اینترنت عمومی باز باشد.
- روش تهیه نسخه پشتیبان، ثبت رویدادها، به‌روزرسانی امن و بازیابی پس از خرابی در پارت‌های بعدی مشخص خواهد شد.

## ۷. شبکه و پورت‌ها

IP ثابت، اینترنت و Port Forwarding فعلی در دسترس هستند. برای نود لینوکسی داخل VMware، حالت **Bridged** گزینه اولیه برای آزمایش است تا VM در شبکه محلی آدرس مستقل داشته باشد و مسیر هدایت پورت‌ها ساده‌تر شود.

در طراحی نهایی باید این موارد مستقل از کد سایت و برای هر نود قابل تنظیم باشند:
- آدرس مدیریتی نود و آدرس قابل دسترسی بازیکنان.
- محدوده پورت‌های اختصاص‌یافته به سرورهای بازی.
- پورت‌ها و مسیرهای ارتباطی مورد نیاز Panel و Wings.
- قوانین فایروال و دسترسی‌های مدیریتی.

جزئیات واقعی آدرس‌دهی و تخصیص پورت در مرحله نصب نود و تست شبکه تعیین می‌شوند؛ این README جایگزین تنظیمات اجرایی نیست.

## ۸. حفظ زیرساخت فعلی KUS

ریپوی larnzs/cs2-kus-addons و کانفیگ‌های فعلی، زیرساخت بازی موجود هستند و در این مرحله تغییر نمی‌کنند.

هنگام پیاده‌سازی باید:
- نصب و اجرای سرور روی Linux با ساختار نودهای Pterodactyl هماهنگ شود.
- روش به‌روزرسانی افزونه‌ها و فایل‌های بازی تا حد ممکن با فرایند فعلی سازگار بماند.
- فایل‌های شخصی، کانفیگ‌ها و تنظیمات موجود بدون نیاز مشخص و بررسی اثر تغییر، حذف یا بازنویسی نشوند.
- تست Windows و Linux به‌عنوان دو محیط جدا در نظر گرفته شود؛ تأیید یک محیط به‌تنهایی جایگزین تست محیط دیگر نیست.

## ۹. مواردی که در پارت ۱ هنوز تعیین تکلیف نشده‌اند

این موارد عمداً باز می‌مانند تا قبل از تصمیم‌گیری، معماری موجود و گزینه‌ها به‌صورت جداگانه بررسی شوند:

- انتخاب نهایی فناوری هسته وب و نحوه توسعه یا نوسازی بخش PHP.
- نقش آینده برنامه C# و اینکه کدام مسئولیت‌ها باید حذف، حفظ یا به API منتقل شوند.
- مدل دقیق اتصال سایت به Pterodactyl و اینکه کدام عملیات از رابط اختصاصی FragCity انجام شوند.
- مدل داده و مرجع اصلی اطلاعات کاربران، سفارش‌ها، مالکیت سرورها و وضعیت اجرای آن‌ها.
- سیاست بکاپ، مانیتورینگ، به‌روزرسانی و بازیابی.
- نحوه مهاجرت از پیاده‌سازی موجود، بدون قطع سرویس یا از دست‌رفتن کانفیگ‌ها.
- ظرفیت نهایی سرورها برای سخت‌افزار فعلی و معیارهای لازم برای اضافه‌کردن نود جدید.

## ۱۰. خروجی مورد انتظار پارت ۱

در پایان این پارت، تصمیم پایه این است:

> FragCity به‌صورت یک سامانه مرکزی و ماژولار ساخته می‌شود که مدیریت کسب‌وکار را از اجرای سرورهای بازی جدا نگه می‌دارد. ویندوز فعلی برای تست و سرورهای موقت باقی می‌ماند؛ سرورهای مشتریان از طریق نودهای لینوکسی و Pterodactyl مدیریت می‌شوند. معماری از روز اول برای چند نود طراحی خواهد شد، به‌طوری که افزودن سیستم‌های فیزیکی جدید از فرایند نصب استاندارد و تنظیمات اختصاصی نود پیروی کند، نه از تغییر کد اصلی سایت.

**پارت بعدی:** بررسی معماری سایت و هسته FragCity، ارتباط با Pterodactyl و تعیین نقش واقعی برنامه C#؛ بدون شروع بازنویسی یا تغییر ریپوها تا زمانی که تصمیم‌ها مستند و روشن شوند.

# پارت ۲ — آماده‌سازی Debian و VMware و آزمایش نخستین سرور CS2

> **وضعیت:** برنامه اجرایی آماده است؛ تا وقتی نصب و آزمایش روی سیستم واقعی انجام نشده، هیچ‌کدام از مراحل این بخش «انجام‌شده» محسوب نمی‌شوند. پس از تست، نتیجه واقعی و تنظیمات نهایی در همین سند ثبت خواهد شد.

## ۱. هدف این پارت

در این مرحله قرار است روی کامپیوتر فعلی FragCity:

1. یک ماشین مجازی سبک Debian داخل VMware ساخته شود.
2. شبکه VM طوری تنظیم شود که لینوکس آدرس محلی مستقل داشته باشد.
3. ابزارهای پایه نصب و صحت سیستم‌عامل، شبکه، رم و فضای دیسک بررسی شوند.
4. نسخه Linux موجود سرور KUS به‌صورت محلی روی VM نصب شود.
5. ابتدا نصب و انتقال فایل‌ها بدون راه‌اندازی خودکار سرور انجام شود؛ سپس تنظیمات لازم بررسی و یک سرور CS2 به‌صورت آزمایشی اجرا شود.
6. RAM، CPU، پایداری و اتصال شبکه ثبت شوند تا مبنای تصمیم‌های ظرفیت‌سنجی باشند.

**در این پارت Pterodactyl نصب نمی‌شود.** ابتدا باید مطمئن شویم Debian و سرور CS2 با افزونه‌ها و تنظیمات موجود درست کار می‌کنند. اتصال این نصب آزمایشی به Pterodactyl در مرحله جداگانه بررسی می‌شود؛ ساختار اجرای مستقیم KUS و اجرای مدیریت‌شده داخل Docker یکسان فرض نمی‌شوند.

## ۲. نسخه Debian انتخاب‌شده برای آزمایش

نسخه منتخب برای نصب آزمایشی، **Debian 13.7 (Trixie)، معماری amd64** است. طبق صفحه رسمی Debian، نسخه 13.7 در ۱۲ سپتامبر ۲۰۲۶ منتشر شده و نسخه پایدار جاری در زمان تدوین این پارت است. در روز نصب، صفحه رسمی را دوباره بررسی می‌کنیم؛ اگر نسخه پایدار 13.x جدیدتری منتشر شده باشد، آخرین ISO پایدار را ترجیح می‌دهیم.

- [صفحه رسمی دانلود Debian](https://www.debian.org/distrib/)
- [Debian netinst — نصب شبکه‌ای](https://www.debian.org/distrib/netinst)
- [فهرست انتشارهای Debian](https://www.debian.org/releases/index.en.html)

### فایل ISO

فایل **64-bit PC netinst ISO (amd64)** را دانلود کن. با توجه به اینکه VM در زمان نصب اینترنت خواهد داشت، netinst انتخاب مناسبی برای نصب بدون محیط گرافیکی است. به ISO نسخه Live نیازی نداریم.

## ۳. تنظیمات اولیه ماشین مجازی

این مقادیر برای **مرحله نصب و آزمایش یک سرور CS2** پیشنهاد شده‌اند؛ تنظیمات نهایی ظرفیت چند سرور بعد از اندازه‌گیری تعیین می‌شوند.

| گزینه | مقدار اولیه | توضیح |
|---|---|---|
| نام VM | **FragCity-Debian-Node01** | نام واضح برای اولین نود آزمایشی |
| سیستم‌عامل مهمان | Debian 13، 64-bit | در صورت نبودن نسخه دقیق، نزدیک‌ترین گزینه Debian 64-bit |
| vCPU | ۴ هسته مجازی | یک پردازنده مجازی با ۴ هسته، در صورت امکان |
| RAM | ۶ گیگابایت (۶۱۴۴ مگابایت) | برای نصب و تست یک سرور؛ تضمین‌کننده اجرای ۵ تا ۱۰ سرور نیست |
| دیسک | هدف جدید: ۳۰۰ گیگابایت، Thin Provision | برای نگهداری کپی نصب فعلی ویندوز (حدود ۹۰ گیگابایت) به‌علاوه نصب و فایل‌های Linux؛ افزایش هنوز انجام نشده است |
| نوع شبکه | Bridged | VM در شبکه محلی IP مستقل می‌گیرد |
| محیط گرافیکی | فعلاً حفظ شود | برای یادگیری و راه‌اندازی اولیه؛ حذف احتمالی فقط در نودهای تولیدی آینده بررسی می‌شود |
| فایل‌های VM | روی SSD | عملکرد و زمان بارگذاری بهتر از دیسک کندتر |

### احتیاط درباره منابع

سیستم میزبان ۱۶ گیگابایت رم دارد؛ بنابراین هنگام روشن بودن VM بخشی از حافظه همچنان برای Windows و برنامه‌های ضروری میزبان لازم است. فعلاً ۶ گیگابایت به VM اختصاص داده می‌شود و تا قبل از سنجش مصرف واقعی، افزایش رم یا تعداد سرورها را قطعی نمی‌دانیم. قابلیت رزرو تمام حافظه VM در VMware فعال نشود.

پیش از ساخت دیسک، فضای واقعی خالی میزبان بررسی شود. Thin Provision به این معنی نیست که فایل‌های CS2 و به‌روزرسانی‌ها فضای فیزیکی مصرف نمی‌کنند.

## ۴. مراحل نصب Debian

در نصب‌کننده Debian از این مقادیر استفاده شود:

| گزینه | مقدار پیشنهادی |
|---|---|
| Hostname | **fc-node-01** |
| Domain name | خالی، مگر اینکه دامنه داخلی مشخصی وجود داشته باشد |
| کاربر مدیریتی | یک کاربر معمولی، مثلاً **fragcityadmin** |
| حساب root | می‌توان فیلد رمز root را خالی گذاشت تا حساب root مستقیم غیرفعال شود و کاربر اولیه از sudo استفاده کند |
| پارتیشن‌بندی | استفاده از کل دیسک مجازی VM؛ دیسک میزبان Windows انتخاب یا تغییر داده نشود |
| SSH server | نصب شود |
| محیط دسکتاپ | فعلاً حفظ شود |
| Standard system utilities | انتخاب شود |

این پارتیشن‌بندی فقط روی دیسک مجازی انجام می‌شود. هنگام نصب، نام دیسک و خلاصه تغییرات را کنترل کن تا هیچ دیسک فیزیکی میزبان انتخاب نشود. چون مدیر پروژه فعلاً با لینوکس تازه آشنا می‌شود، محیط گرافیکی نصب‌شده حذف نخواهد شد؛ در صورت ساخت نودهای تولیدی بعدی، می‌توان نصب بدون محیط گرافیکی را جداگانه بررسی کرد.

## ۵. به‌روزرسانی اولیه و ابزارهای پایه

پس از اولین بوت و ورود با کاربر مدیریتی:

~~~bash
sudo apt update
sudo apt full-upgrade -y
sudo apt install -y git curl ca-certificates nano htop tmux jq rsync unzip tar xz-utils dnsutils netcat-openbsd openssh-server
sudo systemctl enable --now ssh
sudo reboot
~~~

پس از راه‌اندازی مجدد، بررسی اولیه انجام شود:

~~~bash
cat /etc/os-release
uname -m
ip -br address
ip route
free -h
df -h /
nproc
systemctl status ssh --no-pager
~~~

انتظار می‌رود نسخه سیستم Debian 13.x و معماری x86_64 باشد؛ رابط شبکه باید آدرس معتبر محلی و مسیر پیش‌فرض داشته باشد. مقدار واقعی RAM، فضای آزاد و تعداد CPU قابل مشاهده نیز ثبت شود.

## ۶. شبکه VMware و مسیریابی

**Bridged** حالت اولیه شبکه است تا VM یک آدرس IP محلی مستقل داشته باشد. پس از نصب:

- آدرس IP ماشین مجازی با دستور **ip -br address** مشخص شود.
- بررسی شود که دستور **ip route** مسیر پیش‌فرض معتبری نشان می‌دهد.
- اتصال اینترنت از داخل Debian آزمایش شود.
- ترجیحاً برای MAC ماشین مجازی در روتر DHCP reservation تعریف شود تا آدرس داخلی نود مرتب عوض نشود.
- Port Forwarding سرور آزمایشی باید به IP خود VM اشاره کند، نه به IP محلی Windows میزبان.
- پورت‌های مدیریتی SSH و پنل‌های مدیریتی را بدون نیاز و بررسی امنیتی به اینترنت عمومی باز نکنیم.
- اگر Windows و VM قرار است هم‌زمان سرورهایی با یک پورت مشابه اجرا کنند، مقصد و قواعد هدایت پورت باید جداگانه بررسی شوند.

پورت‌های نهایی و قواعد فایروال هنوز در این مرحله تثبیت نشده‌اند و پس از مشاهده IP واقعی VM تعیین می‌شوند.

## ۷. دریافت و آماده‌سازی نسخه Linux ریپوی KUS

ریپوی **larnzs/cs2-kus-addons** و شاخه **integration/kus-monorepo** زیرساخت موجود سرور بازی هستند. برای نصب آزمایشی می‌توان نسخه مخزن را روی VM کلون کرد و از ورودی‌های Linux موجود استفاده کرد؛ **این کار مجوز ویرایش، commit یا push کردن تغییرات به ریپو نیست.**

مسیرهای موجود برای مطالعه قبل از اجرا:

- [راهنمای Linux](https://github.com/larnzs/cs2-kus-addons/blob/integration/kus-monorepo/linux/README.md)
- [اسکریپت نصب Linux](https://github.com/larnzs/cs2-kus-addons/blob/integration/kus-monorepo/linux/install.sh)
- [اسکریپت به‌روزرسانی Linux](https://github.com/larnzs/cs2-kus-addons/blob/integration/kus-monorepo/linux/update.sh)
- [اسکریپت اجرای Linux](https://github.com/larnzs/cs2-kus-addons/blob/integration/kus-monorepo/linux/run.sh)

به دلیل خصوصی بودن مخزن، دریافت آن باید با دسترسی مجاز GitHub انجام شود. احراز هویت و توکن‌ها را در دستورهای قابل ذخیره، لاگ یا فایل tracked قرار نده.

### هشدار مهم برای اجرای اسکریپت‌ها

**در تست اولیه، linux/update.sh اجرا نشود.** طبق نسخه‌ای که برای این پارت بررسی شد، این ورودی مسیر به‌روزرسانی افزونه‌ها را فعال می‌کند و فرایند نصبِ فراخوانی‌شده با RUN_PLUGIN_UPDATER=1 ممکن است تلاش کند تغییرات افزونه‌ها را به شاخه integration/kus-monorepo push کند. این رفتار برای یک تست محلی اولیه لازم نیست و با اصل عدم‌تغییر مخزن در این پارت سازگار نیست.

پیش از هر اجرا باید نسخه فعلی اسکریپت‌ها دوباره بررسی شود. برای نصب آزمایشی، مسیر مستقیم نصب با حالت **عدم شروع سرور** مدنظر است:

~~~bash
sudo env -u RUN_PLUGIN_UPDATER UPDATE_ONLY=1 bash ./linux/install.sh
~~~

این دستور صرفاً روی VM اجرا شود، از پوشه clone همان ریپو و پس از بررسی دستی اسکریپت. در نسخه‌ای که بررسی شده، حالت UPDATE_ONLY=1 اجازه نصب و به‌روزرسانی فایل‌های بازی و overlay کردن payload را می‌دهد اما از شروع CS2 در انتهای همان اسکریپت جلوگیری می‌کند. پاکسازی یا حذف فایل‌های موجود از سمت این فرایند مجاز نیست و کانفیگ‌های دستی باید محفوظ بمانند.

این اسکریپت ممکن است بسته‌های Debian را به‌روزرسانی کند و فایل‌های Steam Linux Runtime و CS2 را دانلود کند؛ برای همین فضای آزاد میزبان و VM باید کافی باشد.

> **قانون ثابت:** از طریق این فرایند هیچ commit، push یا تغییر محتوایی در ریپوی cs2-kus-addons ایجاد نمی‌کنیم. اگر در آینده تغییر در خود ریپو لازم شود، فقط پس از درخواست صریح کاربر بررسی خواهد شد.

## ۸. راه‌اندازی آزمایشی نخستین سرور

بعد از اتمام نصب با UPDATE_ONLY=1، هنوز نباید سرور را کورکورانه اجرا کرد. ابتدا باید موارد زیر بررسی شوند:

1. وجود فایل اجرایی CS2 و فایل‌های runtime لینوکس.
2. نتیجه overlay شدن payload و وجود افزونه‌های مورد انتظار.
3. سلامت فایل gameinfo.gi در runtime نصب‌شده.
4. مسیر و محتوای کانفیگ مورد استفاده سرور و مقادیر پورت، مپ، ظرفیت بازیکن و رمز RCON.
5. نحوه شروع از طریق ورودی Linux مناسب، بدون فعال شدن ناخواسته updater.
6. اطمینان از اینکه رمز RCON قوی، یکتا و خارج از Git است؛ رمز واقعی نباید در README ثبت شود.

پس از این بررسی‌ها، روش اجرای سرور برای همین VM و همین نسخه اسکریپت تثبیت می‌شود. فرمان شروع و مقادیر واقعی فقط بعد از بررسی فایل‌های فعلی و مشخص شدن تنظیمات مورد نیاز ثبت خواهند شد؛ این سند فعلاً موفقیت اجرای سرور را ادعا نمی‌کند.

## ۹. معیارهای پذیرش پارت ۲

پارت ۲ فقط زمانی تکمیل‌شده محسوب می‌شود که این موارد روی سیستم واقعی بررسی شده باشند:

- [ ] Debian 13.x پایدار نصب و نسخه دقیق آن ثبت شده باشد.
- [ ] VM به‌صورت پایدار بوت شود؛ محیط گرافیکی فعلاً حفظ شده باشد و دسترسی کنسول/SSH کار کند.
- [ ] VM آدرس مستقل محلی، مسیر پیش‌فرض و اتصال اینترنت داشته باشد.
- [ ] فضای آزاد میزبان و VM برای فایل‌های بازی و آپدیت کافی باشد.
- [ ] payload موردنیاز Linux نصب شده باشد، بدون دستکاری مخزن GitHub.
- [ ] هیچ updater ناخواسته‌ای که commit یا push کند اجرا نشده باشد.
- [ ] اولین سرور CS2 روی Linux بالا بیاید و از شبکه قابل دسترسی باشد.
- [ ] مصرف RAM و CPU در حالت بدون بازیکن و طی تست واقعی ثبت شود.
- [ ] لاگ‌های شروع و هر خطای مهم بررسی و نتیجه ثبت شود.

اگر هر مورد شکست خورد، ابتدا همان مرحله عیب‌یابی می‌شود؛ قبل از اثبات پایداری یک سرور، نصب Pterodactyl یا افزایش تعداد سرورها را هم‌زمان وارد این آزمایش نمی‌کنیم.

## ۱۰. خروجی مورد انتظار پارت ۲

> هدف پارت ۲، آماده‌سازی ماشین Debian 13.7 روی VMware و اجرای آزمایشی یک سرور CS2 با Linux payload فعلی است. برای مرحله فعلی، ۴ vCPU و ۶ گیگابایت RAM اختصاص داده شده‌اند؛ محیط گرافیکی حفظ می‌شود. به‌دلیل تصمیم به کپی‌کردن نصب فعلی ویندوز، ظرفیت دیسک مجازی ۳۰۰ گیگابایت Thin Provision هدف‌گذاری شده است، اما افزایش دیسک و کپی فایل‌ها هنوز انجام نشده‌اند. این پارت تنها پس از آزمایش واقعی شبکه، نصب payload، اجرای سرور و ثبت مصرف منابع کامل خواهد شد.

**مرحله بعد پس از تست:** ثبت نتیجه واقعی و حل مشکلات احتمالی اجرای CS2؛ سپس تصمیم درباره نحوه انتقال نصب به معماری نودهای Pterodactyl، بدون بازنویسی یا تغییر شتاب‌زده زیرساخت موجود.

3. هدف پیشنهادی اندازه دیسک مجازی به **۳۰۰ GB، از نوع Thin Provision** تغییر کرده است. این ظرفیت فعلاً هدف برنامه است و افزایش آن هنوز انجام نشده است.
4. فایل‌های منبع اصلی ویندوز نباید حذف یا جابه‌جا شوند. عملیات انتقال باید از اشتراک به یک مسیر محلی مجزا در Debian انجام شود و به‌صورت کپی باشد، نه انتقالی که منبع را پاک کند.
5. کپی نصب ویندوز به Debian به‌معنی قابل اجرا بودن فایل اجرایی ویندوز در Linux نیست. برای اجرای واقعی CS2 همچنان فایل‌های Linux و Steam Linux Runtime موردنیازند؛ کپی ویندوز صرفاً برای نگهداری و بررسی فایل‌های موجود و جلوگیری از دانلودهای غیرضروری است.

### مسیر اشتراک و نکته مالکیت Git

در پیکربندی فعلی، نام اشتراک VMware برابر **W** است و ریشه قابل مشاهده آن **/mnt/hgfs/W** است؛ این مسیر مستقیماً محتوای ریپوی KUS را نشان می‌دهد. مسیر **/mnt/hgfs/W/cs2-kus-addons** وجود ندارد و نباید به‌عنوان مسیر ریشه استفاده شود.

اجرای **git -C /mnt/hgfs/W rev-parse --show-toplevel** با پیام **detected dubious ownership** متوقف شد. این پیام به‌تنهایی نشان‌دهنده خرابی ریپو نیست و به نحوه گزارش مالکیت فایل‌ها از طریق Shared Folders مربوط می‌شود. برای بررسی فایل‌ها نیازی به اجرای Git روی این mount نیست؛ بنابراین فعلاً **safe.directory** به تنظیمات Git اضافه نشده است.

**برای حفاظت بیشتر از سورس:** قبل از عملیات کپی بعدی، Shared Folder بهتر است از تنظیمات VMware به حالت **Read-only** تغییر کند. VM باید بتواند فایل‌ها را بخواند و در فضای محلی خودش کپی کند، بدون اینکه بتواند سورس میزبان را تغییر دهد. این گزینه هنوز نیاز به تأیید در تنظیمات VMware دارد؛ صرف مشاهده فایل‌ها به معنی Read-only بودن اشتراک نیست.

### موارد Pending — هنوز انجام نشده‌اند

- [ ] بررسی فضای آزاد واقعی در درایوی که فایل‌های VMware روی آن قرار دارند؛ Thin Provision از پرشدن واقعی دیسک میزبان جلوگیری نمی‌کند.
- [ ] خاموش‌کردن VM و افزایش اندازه دیسک مجازی از مقدار فعلی به هدف **۳۰۰ GB** در VMware.
- [ ] پس از افزایش دیسک مجازی، بررسی ساختار واقعی دیسک با **lsblk -o NAME,SIZE,FSTYPE,TYPE,MOUNTPOINTS**، **lsblk -f**، **findmnt /** و **df -h /**.
- [ ] تنها پس از مشاهده خروجی دیسک، تعیین روش لازم برای بزرگ‌کردن پارتیشن و فایل‌سیستم Debian؛ افزایش ظرفیت مجازی VMware لزوماً فایل‌سیستم مهمان را خودکار بزرگ نمی‌کند.
- [ ] تأیید Read-only بودن Shared Folder و ادامه استفاده از ریشه **/mnt/hgfs/W** برای خواندن فایل‌های منبع.
- [ ] کپی غیرمخرب و کامل پوشه نصب ویندوز از **/mnt/hgfs/W/server** به مسیری محلی و جدا در VM؛ مسیر مقصد نهایی پس از بررسی اندازه دیسک مشخص شود.
- [ ] بررسی کپی محلی، اندازه فایل‌ها و وجود فایل‌های موردنیاز Linux. هیچ فایل اجرایی Windows نباید به‌عنوان فایل اجرایی Linux فرض شود.
- [ ] آماده‌سازی payload فعلی KUS برای نصب Linux، بدون اجرای updaterی که ممکن است به GitHub push کند.
- [ ] اجرای نخستین سرور CS2 روی Linux، بررسی لاگ‌ها و ثبت مصرف واقعی RAM و CPU.

### هشدارهای عملیاتی که پابرجا هستند

- در این مرحله **linux/update.sh** اجرا نشود؛ نسخه بررسی‌شده آن می‌تواند مسیر updater افزونه‌ها را فعال کند و آن فرایند برای push کردن تغییرات به شاخه مخزن تلاش کند.
- پیش از هر اجرای اسکریپت نصب Linux، محتوای همان نسخه باید دوباره بررسی شود؛ برای مرحله نصب فایل‌ها، حالت **UPDATE_ONLY=1** و غیرفعال‌کردن **RUN_PLUGIN_UPDATER** در نظر گرفته شده است، ولی نباید یک فرمان را بدون بررسی نسخه فعلی اسکریپت اجرا کرد.
- هیچ commit، push، ویرایش یا پاک‌سازی در ریپوی **larnzs/cs2-kus-addons** از این مرحله انجام نمی‌شود. همه کارهای این پارت فقط برای آماده‌سازی VM و تست محلی‌اند.
- هیچ ادعایی مبنی بر اجرای موفق یک سرور CS2 روی Debian ثبت نشده است؛ سرور Linux هنوز اجرا نشده است.

### وضعیت فعلی پارت ۲

**وضعیت کلی: Pending — آماده‌سازی Debian و اتصال Shared Folder انجام شده؛ توسعه فضای دیسک، کپی نصب بازی و اجرای آزمایشی CS2 هنوز انجام نشده‌اند.**

گام بعدی پس از بازگشت به این پارت: ابتدا فضای آزاد میزبان را بررسی کن؛ سپس VM را خاموش کرده، دیسک مجازی را به ۳۰۰ GB افزایش بده و خروجی دستورات تشخیص دیسک را بفرست. قبل از کپی ۹۰ GB فایل، ساختار جدید دیسک و فضای قابل استفاده داخل Debian باید تأیید شود.

## ۱۲. دفتر کامل فرمان‌های اجراشده در Debian و بررسی اولیه دیتابیس

این بخش، سابقه عملی پارت ۲ را برای ادامه کار نگه می‌دارد. خروجی‌های حجیم ترمینال عیناً تکرار نشده‌اند، اما فرمان‌ها، نتایج مهم و خطاهای مشاهده‌شده ثبت شده‌اند. این سابقه باید از دستورهای پیشنهادیِ اجرا‌نشده جدا در نظر گرفته شود.

### ۱۲.۱. بررسی سیستم‌عامل و منابع

فرمان‌هایی که برای بررسی اولیه اجرا شدند:

    cat /etc/os-release
    uname -m
    ip -br address
    ip route
    free -h
    df -h /
    nproc
    systemctl status ssh --no-pager

نتایج ثبت‌شده:

| بررسی | نتیجه مشاهده‌شده |
|---|---|
| سیستم‌عامل | Debian GNU/Linux 13 (Trixie)، DEBIAN_VERSION_FULL=13.7 |
| معماری | x86_64 |
| CPU مجازی | nproc مقدار 4 |
| رابط شبکه | ens33 فعال |
| IP داخلی | 192.168.1.5/24 |
| Gateway | 192.168.1.1 |
| SSH | ssh.service در وضعیت active (running) |
| RAM قبل از تغییر VM | ابتدا حدود 1.9Gi در خروجی free -h دیده شد؛ این مقدار با هدف ۶ گیگابایت سازگار نبود |
| RAM پس از تغییر VM | total برابر 5.6Gi، used برابر 1.1Gi، free برابر 4.0Gi و available برابر 4.5Gi |
| Swap | حدود 6.1Gi؛ در خروجی آخر مصرف صفر داشت |
| فایل‌سیستم / | قبل از افزایش احتمالی دیسک: 112G ظرفیت، 5.0G مصرف و 101G آزاد |

محیط گرافیکی Debian نصب شده و فعلاً عمداً نگه داشته می‌شود تا کاربر تازه‌کار بتواند از رابط گرافیکی استفاده کند. حذف آن تصمیم این مرحله نیست.

### ۱۲.۲. بررسی اتصال اینترنت

فرمان‌های اجراشده:

    getent hosts github.com
    curl -I --max-time 15 https://github.com
    curl -I -L --max-time 20 https://steamcdn-a.akamaihd.net/client/installer/steamcmd_linux.tar.gz
    sudo apt update

نتایج مشاهده‌شده:

- DNS برای github.com آدرس 140.82.121.3 برگرداند.
- درخواست HTTPS به GitHub پاسخ HTTP/2 200 داشت.
- درخواست به Steam CDN نیز HTTP/2 200 دریافت کرد.
- sudo apt update مخازن Debian Trixie، trixie-updates و trixie-security را با موفقیت بررسی کرد و در زمان آن تست، همه بسته‌ها به‌روز گزارش شدند.

این تست‌ها دسترسی اینترنت را در همان زمان تأیید می‌کنند؛ تضمین دسترسی دائمی یا مجازبودن Remote MySQL از سمت هاست نیستند.

### ۱۲.۳. نصب و بررسی ابزارهای VMware Shared Folders

فرمان اجراشده:

    sudo apt install -y open-vm-tools open-vm-tools-desktop fuse3 rsync

خروجی نشان داد هر چهار بسته نصب بوده و نسخه‌های فعلی به‌روز هستند؛ بسته جدیدی نصب یا به‌روزرسانی نشد.

فرمان زیر:

    vmware-hgfsclient

خروجی:

    W

سپس اشتراک با این فرمان‌ها mount شد:

    sudo mkdir -p /mnt/hgfs
    sudo vmhgfs-fuse .host:/ /mnt/hgfs -o allow_other
    ls -la /mnt/hgfs

در ادامه برای mount مجدد، این فرمان‌ها هم اجرا شدند:

    sudo umount /mnt/hgfs
    sudo vmhgfs-fuse .host:/ /mnt/hgfs -o allow_other
    vmware-hgfsclient
    ls -la /mnt/hgfs

نتیجه نهایی نشان داد اشتراک W زیر مسیر /mnt/hgfs/W نمایش داده می‌شود.

**تفسیر مسیر:** فهرست واقعی /mnt/hgfs/W شامل DEPENDENCIES.json، .git، game، linux، server، steamcmd، tmp و دیگر اجزای ریشه ریپوی KUS است. بنابراین در پیکربندی فعلی، محتوای ریشه قابل مشاهده ریپو در /mnt/hgfs/W قرار دارد. مسیر /mnt/hgfs/W/cs2-kus-addons وجود ندارد؛ اسم W نام Shared Folder گزارش‌شده توسط VMware است.

> Shared Folder در حال حاضر mount شده است، اما Read-only بودن آن هنوز تأیید نشده است. پیش از هر عملیات پرریسک باید این گزینه در تنظیمات VMware بررسی و در صورت امکان فعال شود. فایل‌های منبع Windows نباید پاک، جابه‌جا یا بازنویسی شوند.

### ۱۲.۴. مسیرهای اشتباه امتحان‌شده و اصلاح آن‌ها

این مسیرها بررسی شدند اما در ساختار فعلی وجود نداشتند:

    ls -la /mnt/hgfs/KUS_SOURCE
    ls -la /mnt/hgfs/KUS_SOURCE/game
    ls -la /mnt/hgfs/KUS_SOURCE/linux
    ls -la /mnt/hgfs/KUS_SOURCE/server

    ls -la /mnt/hgfs/W/cs2-kus-addons
    ls -la /mnt/hgfs/W/cs2-kus-addons/game
    ls -la /mnt/hgfs/W/cs2-kus-addons/server

همه این مسیرهای درون‌اشتراک با خطای No such file or directory مواجه شدند. علت، مطابق فهرست موفق بعدی، این است که ریشه محتوای ریپو از قبل در /mnt/hgfs/W قابل مشاهده است و فولدر cs2-kus-addons یک سطح دیگر داخل آن نیست.

فرمان‌های درست برای بررسی ساختار فعلی:

    ls -la /mnt/hgfs/W/
    ls -la /mnt/hgfs/W/game
    ls -la /mnt/hgfs/W/game/csgo
    ls -la /mnt/hgfs/W/linux
    ls -la /mnt/hgfs/W/server

این فرمان‌ها فقط فایل‌ها و پوشه‌ها را فهرست می‌کنند و محتوا را تغییر نمی‌دهند.

### ۱۲.۵. اندازه پوشه‌ها و فایل‌های بازی موجود

فرمان‌های اجراشده:

    du -sh /mnt/hgfs/W/
    du -sh /mnt/hgfs/W/game
    du -sh /mnt/hgfs/W/server
    du -sh /mnt/hgfs/W/steamcmd
    du -sh /mnt/hgfs/W/tmp

نتایج گزارش‌شده:

| مسیر | اندازه تقریبی مشاهده‌شده |
|---|---:|
| /mnt/hgfs/W/ | 92G |
| /mnt/hgfs/W/game | 1.1G |
| /mnt/hgfs/W/server | 90G |
| /mnt/hgfs/W/steamcmd | 182M |
| /mnt/hgfs/W/tmp | 454M |

برای جست‌وجوی فایل‌های اجرایی و gameinfo.gi این فرمان هم اجرا شد:

    find /mnt/hgfs/W/server -maxdepth 8 \
      \( -iname cs2.exe -o -iname cs2 -o -iname gameinfo.gi \) \
      -print 2>/dev/null | head -50

فایل‌های مشاهده‌شده شامل این مسیرها بودند:

    /mnt/hgfs/W/server/game/bin/win64/cs2.exe
    /mnt/hgfs/W/server/game/core/gameinfo.gi
    /mnt/hgfs/W/server/game/csgo/gameinfo.gi
    /mnt/hgfs/W/server/game/csgo_lv/gameinfo.gi

این مشاهده وجود فایل اجرایی Windows را تأیید می‌کند؛ اما وجود یا نبود تمام فایل‌های Linux را به‌تنهایی ثابت نمی‌کند.

### ۱۲.۶. خطای Git در Shared Folder

فرمان اجراشده:

    git -C /mnt/hgfs/W rev-parse --show-toplevel

نتیجه:

    fatal: detected dubious ownership in repository at '/mnt/hgfs/W'

فعلاً دستور پیشنهادی Git برای افزودن safe.directory اجرا نشده است. برای کپی فایل‌ها و اندازه‌گیری پوشه‌ها لازم نیست Git روی Shared Folder اجرا شود. این پیام به‌تنهایی نشانه خرابی مخزن نیست.

### ۱۲.۷. تصمیم کپی فایل‌ها و تغییر اندازه دیسک

بر اساس اندازه‌های مشاهده‌شده و تصمیم کاربر:

- هدف جدید ظرفیت دیسک VM برابر 300 GB و از نوع Thin Provision است.
- افزایش دیسک مجازی هنوز انجام نشده است.
- کاربر تصمیم گرفته است کل پوشه نصب موجود Windows با اندازه تقریبی 90 GB از مسیر /mnt/hgfs/W/server به یک مقصد محلی داخل Debian کپی شود.
- عملیات موردنظر باید کپی باشد، نه جابه‌جایی؛ منبع Windows باید باقی بماند.
- Thin Provision فضای واقعی میزبان را مصرف می‌کند و مانع پرشدن درایوی که فایل‌های VMware روی آن قرار دارند نمی‌شود.
- فایل اجرایی Windows با نام cs2.exe برای اجرای مستقیم روی Linux قابل استفاده نیست. کپی کامل فقط برای نگهداری و بررسی فایل‌های موجود و جلوگیری از دانلودهای غیرضروری است؛ سرور Linux همچنان به فایل‌ها و runtime بومی Linux نیاز دارد.

### ۱۲.۸. دستورهای مرحله بعد که هنوز اجرا نشده‌اند

این دستورات برای بررسی دیسک پس از افزایش اندازه مجازی پیشنهاد شده‌اند، اما هنوز اجرا نشده‌اند:

    lsblk -o NAME,SIZE,FSTYPE,TYPE,MOUNTPOINTS
    lsblk -f
    findmnt /
    df -h /

ابتدا باید فضای آزاد واقعی درایو میزبان داخل Windows بررسی شود. سپس VM خاموش شود و دیسک مجازی در VMware به هدف 300 GB افزایش یابد. پس از بوت، خروجی دستورات بالا باید بررسی شود. افزایش اندازه دیسک مجازی لزوماً پارتیشن و فایل‌سیستم داخل Debian را خودکار بزرگ نمی‌کند؛ روش توسعه آن فقط پس از دیدن ساختار واقعی دیسک مشخص می‌شود.

تا پیش از تأیید فضای کافی و ساختار دیسک جدید، کپی 90 GB داده شروع نشود. همچنین هیچ‌یک از اسکریپت‌های نصب یا به‌روزرسانی KUS در این مرحله اجرا نشده‌اند. به‌خصوص linux/update.sh اجرا نشود؛ نسخه بررسی‌شده آن می‌تواند مسیر updater افزونه‌ها را فعال کند که برای push تغییرات به شاخه GitHub تلاش می‌کند.

## ۱۳. موضوع بعدی — اتصال افزونه‌ها به MariaDB مرکزی (باز و بدون تصمیم قطعی)

این موضوع یک مرحله معماری مستقل است. تا وقتی درباره مدل دسترسی، روش اتصال و رفتار سیستم هنگام قطع شبکه به جمع‌بندی نرسیده‌ایم، نباید این یادداشت‌ها را به‌عنوان طرح نهایی یا مجوز تغییر کد تلقی کرد.

### یافته‌های اولیه از دو ریپوی وب و Agent

- وب‌سایت PHP endpointهایی در پوشه agent دارد؛ از جمله db.php، agent_login.php، auth.php، heartbeat.php و sync_bulk.php.
- sync_bulk.php برای تعدادی از جدول‌های پلاگین‌ها نگاشت دیتابیس تعریف می‌کند و Bulk Upsert انجام می‌دهد.
- Agent فعلی هم از HTTPS API استفاده می‌کند و هم در بعضی سرویس‌ها مستقیماً به MySQL ریموت وصل می‌شود.
- DatabaseSyncService.cs ساختار و داده‌ها را بین دیتابیس محلی و ریموت همگام می‌کند. مسیر عمومی آن شامل پاک‌کردن جدول مقصد پیش از درج مجدد داده‌هاست؛ این روش برای همگام‌سازی چندنودی تأیید نشده است.
- ارسال Bulk Sync در ApiClient.cs باید از نظر هدر Authorization با انتظار sync_bulk.php بررسی و یکپارچه شود.
- جریان صدور و اعتبارسنجی توکن در endpointهای PHP یکدست نیست و باید قبل از گسترش استفاده بررسی شود.
- بعضی فایل‌های PHP دارای اطلاعات اتصال ثابت داخل سورس هستند. این سند عمداً جزئیات محرمانه را درج نمی‌کند. انتقال امن تنظیمات و چرخش credentialها باید برنامه‌ریزی شود تا سایت/API فعلی ناخواسته از کار نیفتد.

- آیا هاست فعلی، Remote MariaDB امن و پایدار را از IP ثابت مجاز می‌کند؟ آیا TLS معتبر در دسترس است؟
- کدام داده‌های پلاگین باید بین سرورهای رسمی FragCity مشترک باشند و کدام‌ها باید برای هر مشتری/سرور جدا بمانند؟
- کدام عملیات از HTTPS API انجام شوند و کدام پلاگین‌ها واقعاً به اتصال مستقیم SQL نیاز دارند؟
- حداقل مجوز SQL هر نود یا دسته پلاگین چیست؟
- هنگام قطع اینترنت یا دسترسی به دیتابیس، پلاگین‌ها باید چه کنند؟ آیا retry، صف محلی یا همگام‌سازی تأخیری لازم است؟
- Schema migration، بکاپ، بازیابی و جلوگیری از داده تکراری چطور مدیریت شوند؟
- کدام قسمت‌های PHP و Agent باید اصلاح شوند و چه بخش‌هایی باید تا پایان مهاجرت دست‌نخورده باقی بمانند؟

**وضعیت این مرحله:** تحقیق و جمع‌بندی هنوز ادامه دارد. هیچ تصمیم نهایی درباره اتصال Remote MariaDB ثبت نشده و هنوز هیچ تغییری در کد PHP، Agent یا ریپوی cs2-kus-addons برای این موضوع انجام نشده است.

## ۱۴. پیشنهاد اجرایی برای اتصال مستقیم پلاگین‌ها از طریق JSON

**وضعیت این بخش: نیاز جدید ثبت شده؛ پیشنهاد اولیه ارائه شده؛ تصمیم نهایی و پیاده‌سازی هنوز انجام نشده است.**

### ۱۴.۱. نیاز واقعی کاربر

پلاگین‌های CS2 مورد استفاده FragCity، از جمله پلاگین‌های Ranks، VIPCore و CS2-SimpleAdmin، برای اتصال دیتابیس تنظیمات اختصاصی JSON دارند. بسته به پلاگین و نسخه آن، این تنظیمات ممکن است مواردی مانند موارد زیر را بگیرند:

- Host یا DatabaseHost
- Port یا DatabasePort
- Database
- Username یا DatabaseUser
- Password یا DatabasePassword
- تنظیمات نوع دیتابیس و در برخی پلاگین‌ها تنظیمات SSL/TLS

بنابراین، **ترجیح اولیه برای کاهش کار دستی این است که پلاگین‌هایی که اتصال مستقیم MySQL/MariaDB را پشتیبانی می‌کنند، در صورت امکان مستقیماً به MariaDB مرکزی FragCity متصل شوند** و اطلاعات اتصال از JSON هر پلاگین تأمین شود. در این حالت، اگر همان داده باید بین چند سرور رسمی مشترک باشد، هر سرور می‌تواند از دیتابیس و schema مشترک مورد توافق استفاده کند؛ نوشتن داده‌ها مستقیم در MariaDB انجام می‌شود و برای همین داده‌ها دیگر نیازی به همگام‌سازی دوره‌ای کل جدول از طریق Agent نیست.

این قابلیت باید برای تک‌تک پلاگین‌ها و نسخه نصب‌شده آن‌ها تأیید شود. وجود نام فیلدهای اتصال در JSON به‌تنهایی تضمین نمی‌کند که پلاگین TLS معتبر، مدیریت قطع ارتباط، timeout یا reconnect را به شکل مطلوب پشتیبانی می‌کند.

نمونه‌های مستندشده عمومی:
- [راهنمای تنظیمات CS2-SimpleAdmin](https://github.com/daffyyyy/CS2-SimpleAdmin) — تنظیمات پلاگین و پشتیبانی دیتابیس MySQL/SQLite.
- [نمونه مستند تنظیمات MySQL در یک پلاگین CounterStrikeSharp](https://github.com/NeuTroNBZh/CS2-STATPLAY) — نشان می‌دهد پلاگین‌های CS2 می‌توانند تنظیمات میزبان، پورت، نام دیتابیس و حساب اتصال را از JSON دریافت کنند.
- [راهنمای رسمی MariaDB برای اتصال کلاینت راه دور](https://mariadb.com/docs/server/mariadb-quickstart-guides/mariadb-remote-connection-guide)
- [مستندات امنیت TLS برای اتصال‌های MariaDB](https://mariadb.com/docs/server/security/encryption/data-in-transit-encryption/secure-connections-overview)
- [مستندات Remote Database Access در cPanel](https://docs.cpanel.net/cpanel/databases/remote-mysql/)

### ۱۴.۲. پیشنهاد برای کمترین effort در فاز نخست

به‌جای ساخت یک لایه جدید C# برای کپی کردن داده‌های پلاگین‌ها، ابتدا امکان Remote MariaDB موجود در سرویس هاست فعلی سایت را بررسی می‌کنیم. اگر این قابلیت وجود داشته باشد و تمام شروط امنیتی و فنی لازم را تأمین کند، ساده‌ترین آزمایش این است:

1. یک دیتابیس آزمایشی جدا از داده‌های تولیدی انتخاب یا ایجاد شود.
2. امکان اتصال از بیرون هاست و محدودکردن مبدأ به IP عمومی ثابت اینترنت FragCity از پنل هاست یا پشتیبانی ارائه‌دهنده تأیید شود.
3. امکان TLS با اعتبارسنجی گواهی برای اتصال کلاینت بررسی شود. نباید فرض کنیم هر نسخه MariaDB یا هر پلاگین TLS را خودکار و درست فعال می‌کند.
4. یک حساب MariaDB اختصاصی با حداقل دسترسی لازم برای همان دیتابیس آزمایشی ساخته شود. حسابی که مالک همه دیتابیس‌های سایت است نباید داخل JSON سرورهای بازی استفاده شود.
5. با یک پلاگین غیرحساس یا محیط آزمایشی، اتصال، خواندن، نوشتن، قطع و وصل شبکه، restart سرور و رفتار پلاگین هنگام خطای دیتابیس بررسی شود.
6. فقط پس از موفقیت آزمایش، مدل اتصال برای پلاگین‌های بعدی و سپس داده‌های واقعی انتخاب شود.

اگر هاست فعلی اجازه Remote MariaDB ندهد یا TLS و محدودسازی مبدأ مناسب قابل فراهم‌کردن نباشد، گزینه جایگزین باید بررسی شود؛ نباید صرفاً برای راحتی، پورت 3306 روتر خانه را برای تمام اینترنت باز کنیم. گزینه‌های جایگزین می‌توانند VPN خصوصی از نودها به یک میزبان مجاز دیتابیس یا انتقال دیتابیس به میزبان مناسب‌تر باشند. انتخاب نهایی وابسته به محدودیت واقعی هاست است.

### ۱۴.۳. «دیتابیس مرکزی» لزوماً به معنی یک schema واحد نیست

پیشنهاد اولیه این است که MariaDB یک سرویس مرکزی باشد، اما دیتابیس اصلی سایت و دیتابیس‌های پلاگین‌ها از نظر منطقی جدا بمانند.

- دیتابیس هسته FragCity برای کاربران سایت، سفارش‌ها، مالکیت سرور و داده‌های تجاری استفاده می‌شود.
- برای پلاگین‌ها، در فاز اول بهتر است schemaهای جداگانه یا دست‌کم مرزهای مشخصی بر اساس خانواده پلاگین حفظ شود؛ این کار با ساختار فعلی نگاشت بعضی جدول‌ها در API سایت نیز سازگارتر است.
- سرورهای رسمی FragCity فقط برای داده‌هایی که باید مشترک باشند از schema مشترک استفاده می‌کنند؛ مانند آمار رتبه‌بندی، VIP یا اطلاعات مدیریتی مشترک، مشروط بر اینکه رفتار همان پلاگین چنین استفاده‌ای را پشتیبانی کند.
- برای دیتابیس‌هایی که نباید بین سرورها مشترک باشند، از schema یا تنظیمات جداگانه استفاده می‌شود.

به این ترتیب، می‌توان یک سرویس MariaDB مرکزی داشت بدون اینکه همه داده‌ها و همه مجوزها داخل یک دیتابیس واحد ادغام شوند.

### ۱۴.۴. نوشتن هم‌زمان از چند نود

اتصال مستقیم چند سرور به یک MariaDB امکان‌پذیر است، اما فقط وقتی مدل داده به‌درستی مشخص شود.

- اگر داده‌ای عمداً مشترک است، نودهای مجاز می‌توانند با مجوز محدود در همان دیتابیس بنویسند.
- اگر داده باید مختص هر سرور یا مشتری باشد، اتصال به schema مشترک بدون جداسازی مناسب ممنوع است.
- کلیدهای اصلی، unique indexها، محدودیت‌های دیتابیس و عملیات تراکنشی پلاگین باید برای نوشتن هم‌زمان بررسی شوند.
- Agent نباید هنگام انتقال داده، جدول مشترک را پاک و از یک snapshot محلی دوباره پر کند. مسیر فعلی DatabaseSyncService.cs که در همگام‌سازی عمومی از پاک‌کردن مقصد استفاده می‌کند، برای داده‌های چندنودی مشترک انتخاب مناسبی نیست.
- سیستم نباید فرض کند تمام پلاگین‌ها هنگام قطع اتصال خودکار داده را ذخیره و بعداً ارسال می‌کنند؛ این رفتار باید پلاگین‌به‌پلاگین تست شود.

### ۱۴.۵. جداسازی داده‌های سرورهای رسمی و سرورهای اجاره‌ای

این تفاوت باید از اولین طراحی تنظیمات در نظر گرفته شود.

**سرورهای رسمی FragCity:** امکان استفاده از دیتابیس مشترک برای داده‌هایی که عمداً بین سرورهای رسمی یکپارچه‌اند، وجود دارد؛ دسترسی‌ها محدود و مخصوص همان خانواده پلاگین هستند.

**سرورهای اجاره‌ای مشتریان:** رمز دیتابیس مشترک سرورهای رسمی نباید در JSON سروری قرار بگیرد که مشتری می‌تواند فایل‌هایش را بخواند یا کنترل کند. اگر مشتری به فایل JSON دسترسی داشته باشد، ممکن است نام کاربری، رمز و آدرس دیتابیس را استخراج کند و خارج از پلاگین نیز به دیتابیس متصل شود.

برای سرور مشتری، هر حساب اتصال باید به دیتابیس یا schema اختصاصی مجاز همان مشتری محدود باشد. اینکه بعضی داده‌ها مانند بن‌ها یا رتبه‌ها باید بین سرورهای اجاره‌ای مشتریان هم مشترک باشند، تصمیم محصول و حریم داده است و به‌صورت خودکار فعال نمی‌شود.

### ۱۴.۶. مدیریت تنظیمات JSON و رمزها

در آینده باید یک کاتالوگ تنظیمات برای پلاگین‌های پشتیبانی‌شده بسازیم که برای هر نسخه مشخص کند:

- مسیر دقیق JSON و نام صحیح فیلدهای دیتابیس.
- پشتیبانی از MySQL/MariaDB و گزینه‌های SSL/TLS.
- schema و نام جدول‌هایی که پلاگین می‌سازد یا استفاده می‌کند.
- مجوزهای لازم برای عملیات عادی و برای نصب یا schema migration.
- اینکه آیا چند سرور می‌توانند از یک دیتابیس مشترک استفاده کنند و کدام داده‌ها در آن مشترک می‌شوند.
- رفتار واقعی پلاگین هنگام timeout یا قطع دیتابیس.

در مدل ماژولار نودها، مقصد و اطلاعات اتصال باید از تنظیمات هر محیط/نود و روش امن مدیریت secret تأمین شوند؛ اما نباید یک رمز مشترک و پرمجوز را در تمام JSONها کپی کنیم. رمزها نباید در Git، README، کد مرورگر یا لاگ‌ها قرار گیرند. در صورتی که فایل‌های تنظیمات مشتری قابل دسترسی باشند، credential آن مشتری باید فقط همان داده‌های خودش را مجاز کند.

### ۱۴.۷. چیزهایی که باید از هاست فعلی پرسیده یا آزمایش شوند

تا زمانی که این موارد مشخص نشده‌اند، امکان Remote MariaDB را قطعی فرض نمی‌کنیم:

- آیا طرح هاست فعلی اتصال Remote MySQL/MariaDB را فعال می‌کند یا این قابلیت توسط ارائه‌دهنده غیرفعال شده است؟
- نام میزبان و پورت واقعی برای اتصال ریموت چیست؟ نباید آدرس localhost سایت را به‌عنوان آدرس Remote فرض کرد.
- آیا می‌توان IP عمومی ثابت FragCity را در allowlist ثبت کرد؟
- آیا TLS فعال است و پلاگین انتخاب‌شده قادر به اعتبارسنجی گواهی سرور است؟
- ارائه‌دهنده چه محدودیت‌هایی برای تعداد اتصال هم‌زمان، زمان اتصال، queryها و اتصال‌های طولانی دارد؟
- آیا دسترسی‌ها اجازه می‌دهند برای هر plugin/database یک کاربر محدود ایجاد شود؟
- آیا بکاپ و بازیابی دیتابیس‌های پلاگین قابل انجام و آزمایش است؟

مستندات cPanel می‌گویند امکان Remote Database Access می‌تواند بر اساس تنظیمات ارائه‌دهنده فعال یا غیرفعال باشد؛ بنابراین باید وضعیت واقعی پنل/هاست بررسی شود، نه اینکه صرفاً فرض کنیم این قابلیت فعال است.

### ۱۴.۸. وضعیت واقعی هاست فعلی و تصمیم مرحله بعد

**وضعیت تأییدشده در ۱۶ اکتبر ۲۰۲۶:** کاربر تأیید کرده است که وب‌سایت FragCity و MariaDB فعلی روی **هاست اشتراکی cPanel** قرار دارند. این موضوع به‌تنهایی اثبات نمی‌کند که اتصال Remote MariaDB فعال است؛ وضعیت قابلیت در پنل و محدودیت‌های سرویس هنوز بررسی نشده‌اند.

در نسخه‌های جدید cPanel، قابلیت دسترسی ریموت ممکن است با نام **Remote Database Access** نمایش داده شود؛ در نسخه‌های قدیمی‌تر نام **Remote MySQL** دیده می‌شود. مستندات cPanel تأکید می‌کنند که شرکت میزبان می‌تواند این قابلیت را فعال یا غیرفعال کرده باشد:
- [مستند رسمی Remote Database Access در cPanel](https://docs.cpanel.net/cpanel/databases/remote-database-access/)

#### بررسی اولیه در پنل

1. وارد cPanel شو و در جست‌وجوی پنل عبارت‌های `Remote Database Access` یا `Remote MySQL` را پیدا کن.
2. اگر قابلیت وجود دارد، صرفِ وجود صفحه را به معنی فعال‌بودن کامل اتصال در سمت سرور فرض نکن؛ امکان افزودن IP، آدرس و پورت اتصال ریموت را با میزبان تأیید کن.
3. از ارائه‌دهنده بپرس آیا اتصال از IP عمومی ثابت نود FragCity مجاز است، آیا TLS با اعتبارسنجی گواهی پشتیبانی می‌شود و محدودیت تعداد اتصال هم‌زمان، مدت اتصال و queryها چیست.
4. اگر امکان اتصال تأیید شد، فقط برای یک دیتابیس آزمایشی و حساب اختصاصی با دسترسی محدود آزمایش انجام شود. فقط IP عمومی خروجی نود مجاز شود؛ از wildcard یا بازکردن عمومی دسترسی استفاده نشود.
5. قبل از ورود به تولید، از محیط Debian اتصال واقعی را آزمایش کن و سپس رفتار یک پلاگین مشخص را در اتصال عادی، قطع شبکه و restart بررسی کن. رمز یا فایل credential را در چت، Git یا خروجی لاگ قرار نده.

#### توصیه معماری با توجه به هاست اشتراکی

- **برای اثبات مفهوم (PoC):** اگر Remote Database Access، محدودکردن IP، TLS و محدودیت‌های لازم تأیید شوند، می‌توان یک دیتابیس کم‌خطر و حساب محدود را روی همین هاست برای آزمایش مستقیم یک پلاگین به‌کار برد.
- **برای تولید و رشد چندنودی:** فعلاً هاست اشتراکی cPanel را میزبان قطعی و بلندمدت تمام اتصال‌های مستقیم پلاگین‌ها فرض نکن. ابتدا محدودیت‌های واقعی میزبان و الگوی اتصال پلاگین‌ها اندازه‌گیری شوند. اگر این سرویس برای بار و سیاست امنیتی مورد نیاز مناسب نبود، دیتابیس افزونه‌ها می‌تواند روی یک میزبان مدیریت‌پذیر جداگانه قرار گیرد و وب‌سایت فعلاً روی cPanel باقی بماند؛ مسیر امن اتصال بین سایت و دیتابیس در آن مرحله جداگانه طراحی می‌شود.
- **برای نودهای متعدد:** هرگز دسترسی دیتابیس را برای تمام اینترنت باز نکن. حساب‌ها و مجوزها باید بر اساس خانواده پلاگین و دامنه داده محدود شوند. هر جا امکان دارد، دسترسی به میزبان دیتابیس باید با allowlist دقیق IP یا شبکه خصوصی محدود شود.
- این نتیجه فعلاً **توصیه مشروط** است، نه تصمیم نهایی درباره مهاجرت دیتابیس، حذف C# یا بازطراحی API. ابتدا باید امکان‌های هاست فعلی را بررسی کنیم.

### ۱۴.۹. جمع‌بندی پیشنهادی (هنوز نه تصمیم نهایی)

برای کمترین effort، مسیر کاندیدای اول این است:

**پلاگین پشتیبانی‌شده → JSON اختصاصی همان پلاگین → MariaDB مرکزی با Remote Access محدود و TLS → schema و حساب مجاز همان داده‌ها.**

این روش می‌تواند نیاز به Agent برای همگام‌سازی ردیف‌های دیتابیس پلاگین را حذف کند و چند سرور رسمی را مستقیماً به داده‌های مشترک وصل کند. اما آن را فقط وقتی انتخاب می‌کنیم که Remote MariaDB هاست، TLS، مجوزهای حداقلی، رفتار هنگام قطع ارتباط و جداسازی مشتری‌ها تأیید شده باشند.

اگر Remote MariaDB هاست امن و قابل اتکا نباشد، قبل از ساخت API اختصاصی برای تقلید از SQL باید VPN خصوصی یا میزبان دیتابیس جایگزین را بررسی کنیم. API برای عملیات مدیریتی نودها همچنان مستقل باقی می‌ماند؛ این تصمیم صرفاً مربوط به persistence پلاگین‌هایی است که خودشان SQL مستقیم را پشتیبانی می‌کنند.

**وضعیت نهایی این موضوع:** پیشنهاد برای بررسی و آزمایش ثبت شد؛ هنوز هیچ مدل Remote MariaDB نهایی نشده و در کد PHP، C#، فایل‌های JSON پلاگین‌ها یا ریپوی cs2-kus-addons هیچ تغییری انجام نشده است.

### ۱۴.۱۰. نتیجه اولین تست شبکه از Debian

**تاریخ آزمایش: ۱۶ اکتبر ۲۰۲۶**

از ماشین مجازی Debian با دستور زیر اتصال TCP به آدرس و پورت آزمایشی بررسی شد:

```bash
nc -vz -w 5 89.39.208.82 3306
```

خروجی واقعی:

```text
nc: connect to 89.39.208.82 port 3306 (tcp) timed out: Operation now in progress
```

**برداشت دقیق از نتیجه:** در زمان این آزمایش، اتصال TCP از Debian به `89.39.208.82:3306` برقرار نشد و درخواست با timeout مواجه شد. این نتیجه به‌تنهایی اثبات نمی‌کند که سرویس MariaDB خاموش است یا پورت قطعاً بسته است؛ فایروالِ حذف‌کننده بسته‌ها، IP مبدأِ مجازنشده، آدرس/پورت Remote نادرست یا محدودیت شبکه میزبان می‌توانند نتیجه مشابه ایجاد کنند. `Connection timed out` با `Connection refused` یکسان نیست.

#### گام‌های تشخیصی بعدی

1. IP عمومی خروجی فعلی Debian با `curl -4 https://api.ipify.org` بررسی شود.
2. همان IP عمومی دقیق در cPanel بخش **Remote Database Access** ثبت شود؛ از IP خصوصی Debian یا wildcard عمومی استفاده نشود.
3. آدرس و پورت مخصوص **اتصال Remote دیتابیس** از ارائه‌دهنده هاست تأیید شود. نباید فرض کرد IP وب‌سایت لزوماً مقصد صحیح MariaDB ریموت است یا پورت حتماً 3306 باقی می‌ماند.
4. پس از تأیید موارد بالا، تست `nc` با مقصد واقعی تکرار شود.
5. اگر timeout ادامه داشت، از پشتیبانی هاست پرسیده شود آیا فایروال سمت میزبان اتصال MariaDB خارجی را برای IP مبدأ محدودشده اجازه می‌دهد و آیا برای Remote Database Access به فعال‌سازی سمت سرور نیاز است.

تا زمان موفقیت تست شبکه، نباید سراغ واردکردن رمز دیتابیس به پلاگین‌ها یا آزمایش روی schema تولیدی رفت. در این مرحله هیچ رمز یا داده‌ای ارسال نشده و هیچ تغییری در دیتابیس، PHP، C#، JSON پلاگین‌ها یا ریپوی `cs2-kus-addons` انجام نشده است.

## ۱۵. استقرار عامل C# روی Debian بدون بازنویسی کامل

**وضعیت:** مسیر پیشنهادی ثبت شده؛ هیچ پروژه‌ای در این مرحله تغییر یا روی Debian مستقر نشده است.

### ۱۵.۱. تصمیم پایه

به‌دلیل در دسترس نبودن اتصال Remote MariaDB روی پورت `3306` از بیرون هاست اشتراکی، اتصال مستقیم عامل به دیتابیس سایت مسیر فعلی نیست. مسیر قابل‌بررسی این است:

```text
DB محلی پلاگین‌ها روی نود FragCity
        │
        ▼
عامل سبک C# روی Debian
        │ درخواست خروجی HTTPS روی TCP/443
        ▼
API احرازشده FragCity روی cPanel
        │
        ▼
PHP روی خود هاست ── اتصال داخلی/مجاز ──> MariaDB سایت
```

عامل به پورت ورودی جدید روی Debian نیاز ندارد؛ خودش درخواست HTTPS را آغاز می‌کند و پاسخ را دریافت می‌کند. پورت FTP/21 برای این الگو نقشی ندارد. این مدل به شرطی کار می‌کند که ارتباط خروجی Debian به HTTPS سایت مجاز باشد و API روی هاست بتواند به دیتابیس خودش دسترسی داشته باشد.

**محدودیت مهم:** دانستن اینکه هاست فقط پورت‌های 21، 80 و 443 را ارائه می‌کند، به‌تنهایی درباره قوانین خروجی فایروال Debian یا اتصال داخلی PHP به دیتابیس چیزی ثابت نمی‌کند. این دو مسیر باید جداگانه تست شوند.

### ۱۵.۲. چرا نباید برنامه فعلی را صرفاً کپی و اجرا کرد؟

در ریپوی `larnzs/FragCity-WebAPIClient`، پروژه‌های هسته و Host از `.NET 10` و چارچوب عمومی `net10.0` استفاده می‌کنند؛ این یک نقطه شروع مناسب برای کار روی Linux است. مستندات Microsoft نیز نصب .NET 10 روی Debian 13 را پشتیبانی می‌کنند. اما سازگاری Target Framework به معنی سازگاری کل برنامه نیست.

مشاهدات نسخه فعلی:

- `FragCity.Agent.Host/Program.cs` برای ورود تعاملی کاربر، دریافت مسیر پوشه و منوی کنسولی طراحی شده و کلیدهای لغو/خروج را از کنسول دریافت می‌کند؛ برای اجرای بی‌ناظر توسط `systemd` مناسب نیست.
- `AgentService` و چند سرویس Core با `SupportedOSPlatform("windows")` علامت‌گذاری شده‌اند.
- مسیرهای پیش‌فرض به شکل `E:\\instances` و `E:\\cs2-modded-server\\server` هستند.
- Agent کنونی چند وظیفه را با هم اجرا می‌کند: مانیتورینگ نود، مدیریت instanceهای CS2، RCON، عملیات سفارش/نصب، خواندن دیتابیس و همگام‌سازی.
- `DatabaseSyncService` برای اتصال مستقیم به دیتابیس مقصد روی 3306 طراحی شده و رشته اتصال‌هایش `SslMode=none` دارند؛ این مسیر با محدودیت فعلی هاست سازگار نیست و نباید به عنوان موتور سینک تولیدی اجرا شود.
- پروژه UI از `net10.0-windows` و Windows Forms استفاده می‌کند و جزو برنامه مناسب اجرای سروری Debian نیست.

### ۱۵.۳. کمترین تغییر منطقی

پیشنهاد این نیست که C# را از نو بنویسیم. پیشنهاد این است که یک entry point مستقل و بدون UI، مثلاً `FragCity.Agent.SyncWorker`، بسازیم که از مدل‌ها، تنظیمات و بخش‌های قابل‌حمل Core استفاده کند؛ مسئولیتش تنها همگام‌سازی API باشد.

1. پروژه SyncWorker را به صورت یک Worker Service/BackgroundService برای اجرای طولانی‌مدت بسازیم.
2. وابستگی به کنسول، مسیرهای Windows، RCON و ساخت/نصب instance را از فرآیند سینک جدا نگه داریم؛ در این پارت لازم نیست آن بخش‌ها به Linux منتقل شوند.
3. دیتابیس مبدأ محلی را فقط با کاربر دیتابیس محدود و فقط در سطح جدول‌های موردنیاز بخوانیم.
4. داده‌ها را به endpoint مشخص HTTPS بفرستیم و پاسخ موفق/ناموفق را اعتبارسنجی کنیم.
5. در Debian، Worker را به عنوان سرویس `systemd` با کاربر غیر root، restart کنترل‌شده، لاگ محدود و تنظیمات خارج از Git اجرا کنیم.
6. پس از تست محدود، فقط بخش DB sync را فعال کنیم؛ سایر قابلیت‌های عامل فعلی تا زمانی که جداگانه port و تست نشده‌اند، فعال نشوند.

نسخه Debian 13 از .NET 10 به طور رسمی پشتیبانی می‌شود. برای ساخت نسخه Linux می‌توان از `dotnet publish -c Release -r linux-x64` استفاده کرد؛ در صورت انتشار self-contained، Runtime همراه خروجی می‌آید. بااین‌حال، **این دستور به تنهایی برنامه فعلی را cross-platform نمی‌کند**؛ ابتدا باید entry point و وابستگی‌های Windowsمحور تفکیک/اصلاح و سپس build واقعی آزمایش شود.

### ۱۵.۴. وضعیت endpoint موجود برای ارسال دسته‌ای

فایل `agent/sync_bulk.php` در ریپوی PHP وجود دارد و جدول‌هایی از خانواده MatchZy، Ranks، SimpleAdmin، VIPCore و WeaponPaints را به دیتابیس مقصد نگاشت می‌کند. از نظر ساختاری، این endpoint نقطه شروعی برای **ارسال یک‌طرفه از نود به سایت** است؛ اما هنوز نباید آن را به عنوان راهکار کامل سینک چندطرفه در نظر گرفت.

مشکلات دیده‌شده در نسخه فعلی:

- متد `SendBulkSyncDataAsync` در C# هدر Bearer را اضافه نمی‌کند؛ در مقابل `sync_bulk.php` توکن را الزامی می‌داند.
- `agent_login.php` یک توکن تصادفی تولید و برمی‌گرداند، اما در همان مسیر آن را داخل `agent_tokens` ثبت نمی‌کند؛ endpointهای بررسی توکن به آن جدول رجوع می‌کنند. بنابراین مسیر صدور و اعتبارسنجی توکن هم‌راستا نیست.
- endpoint فعلی push عمومی مجاز برای همان جدول‌های فهرست‌شده است؛ API مشخصی برای pull/sync دوطرفه عمومی با cursor یا version در همین مسیر دیده نشده است.
- داده‌های ارسال‌شده و نام ستون‌ها نیازمند اعتبارسنجی دقیق schema هستند؛ استفاده از parameterized values به‌تنهایی نام ستون‌های واردشده در JSON را ایمن نمی‌کند.
- رفتار همگام‌سازی برای حذف رکورد، نوشتن هم‌زمان از چند نود و بازیابی بعد از قطعی شبکه هنوز باید برای هر پلاگین تعریف شود.

در نتیجه، مسیر کم‌تغییر این است که API موجود با طراحی احراز هویت و validation اصلاح و سپس یک Worker کوچک به آن متصل شود؛ نه اینکه سینک عمومی دیتابیس بدون بررسی به API تبدیل شود.

### ۱۵.۵. آیا ابزار آماده GitHub این را جایگزین می‌کند؟

ابزارهایی مانند [SymmetricDS](https://github.com/JumpMind/symmetric-ds) یا [ReplicaDB](https://github.com/osalvador/ReplicaDB) برای replication/انتقال دیتابیس طراحی شده‌اند، اما فرایندشان به اتصال قابل‌دسترسی به دیتابیس مبدأ و مقصد نیاز دارد. در معماری فعلی، دیتابیس مقصد از طریق SQL روی 3306 از نود قابل‌دسترسی نیست و مسیر مجاز، API اختصاصی PHP روی HTTPS است. این ابزارها به‌صورت drop-in جایگزین `sync_bulk.php` و منطق مختص جدول‌های FragCity نمی‌شوند؛ برای انطباق با API اختصاصی باز هم adapter یا کد سفارشی لازم خواهد بود.

یک API gateway عمومی برای SQL نیز مسئله را حل نمی‌کند مگر اینکه در محیطی قابل نصب شود که به دیتابیس دسترسی دارد و API آن با احراز هویت و دسترسی‌های محدود قابل ارائه باشد. اجرای سرویس دیتابیس/API جدید روی هاست اشتراکی cPanel معمولاً تحت کنترل کامل ما نیست و بازکردن دسترسی عمومی دیتابیس راهکار مناسبی نیست.

**نتیجه:** استفاده از پروژه C# موجود، افزودن یک Worker محدود و قابل‌حمل و استفاده امن از API سایت، از شروع دوباره کم‌هزینه‌تر و سازگارتر با شرایط فعلی به نظر می‌رسد.

## ۱۶. ممیزی امنیتی اولیه — C# Agent و PHP API

**دامنه ممیزی:** بازبینی ایستای فایل‌های مرتبط با authentication، heartbeat، bulk sync و DatabaseSyncService در شاخه `main` مخازن `FragCity-WebAPIClient` و `FragCity-RawPHPbackend`. این بازبینی تست نفوذ، اجرای کد، تست روی سرور زنده یا ممیزی کامل کل برنامه نیست. هیچ باگی در این مرحله اصلاح نشده است.

### ۱۶.۱. موارد با اولویت فوری

#### A. اطلاعات دیتابیس hard-code شده در سورس

در چند فایل PHP، اطلاعات اتصال دیتابیس مستقیماً داخل کد قرار گرفته‌اند. این مقادیر در تاریخچه Git نیز می‌توانند باقی بمانند؛ حذفشان از نسخه جاری به‌تنهایی به معنی باطل‌شدن credential نیست.

**اقدام پیشنهادی:** پس از برنامه‌ریزی برای جلوگیری از قطعی، credentialهای جدید با حداقل دسترسی ایجاد شوند، انتقال به تنظیمات خارج از Git انجام شود و credentialهای قبلی به‌صورت هماهنگ چرخانده/باطل شوند. مقدار هیچ secretی نباید در README، commit message یا لاگ قرار گیرد.

#### B. SQL identifier از JSON در `sync_bulk.php`

اسم جدول به map مجاز محدود شده، اما نام ستون‌ها از کلیدهای هر ردیف وارد رشته SQL می‌شوند. parameterized query برای مقادیر ردیف مفید است، ولی شناسه SQL را خودکار امن نمی‌کند.

**اقدام پیشنهادی:** برای هر جدول، فهرست مجاز ستون‌ها را از یک schema تعریف‌شده/اعتبارسنجی‌شده تعیین کنیم؛ کلیدهای ناشناخته رد شوند. نام جدول/ستون نباید مستقیماً از payload آزاد در SQL قرار بگیرد.

#### C. جریان صدور و بررسی توکن هماهنگ نیست

`agent_login.php` توکن تصادفی را به کلاینت برمی‌گرداند، اما در همان مسیر رکوردی برای آن داخل `agent_tokens` نمی‌سازد؛ endpointهایی مانند `heartbeat.php` و `sync_bulk.php` توکن را از این جدول بررسی می‌کنند. علاوه بر آن، C# پس از Login یک `ApiClient` دیگر داخل `AgentService` می‌سازد و انتقال صریح توکن تازه‌گرفته‌شده به نمونه دوم دیده نمی‌شود.

**اقدام پیشنهادی:** جریان ثبت/صدور/انقضا/ابطال توکن یکپارچه شود؛ هر نود credential مستقل و scope محدود خود را داشته باشد و همهٔ endpointهای حساس از یک روش احراز هویت مشترک استفاده کنند.

#### D. هدر Authorization در bulk sync ارسال نمی‌شود

`ApiClient.SendBulkSyncDataAsync` برای `sync_bulk.php` درخواست POST می‌فرستد، اما برخلاف متدهای heartbeat/task، `AddAuthHeader` را فراخوانی نمی‌کند. بنابراین با اجرای endpoint فعلی انتظار می‌رود درخواست فاقد توکن با 401 رد شود.

#### E. خطای نحوی در heartbeat

در `agent/heartbeat.php` دستور fetch رکورد موجود به صورت `$checkStmt$checkStmt->fetch(...)` دیده می‌شود. این عبارت از نظر نحوی نامعتبر به نظر می‌رسد و باید با lint واقعی PHP تأیید و اصلاح شود؛ تا پیش از آن heartbeat را سالم فرض نکنیم.

#### F. مسیر سینک مستقیم دیتابیس خطر از دست‌رفتن داده دارد

`DatabaseSyncService.SyncDataOneWayAsync` قبل از درج داده‌ها، جدول مقصد را با `DELETE FROM` خالی می‌کند و سپس ردیف‌ها را جداگانه درج می‌کند؛ این چرخه transaction اتمیک برای پاک‌کردن و درج دوباره ندارد. اگر داده منبع خالی باشد، متد پیش از پاک‌کردن مقصد برمی‌گردد، بنابراین داده‌های حذف‌شده از منبع در مقصد باقی می‌مانند. همچنین تشخیص دیتابیس/جدول با تطبیق تقریبی suffix و همگام‌سازی گسترده، ریسک انتخاب مقصد اشتباه را ایجاد می‌کند.

**اقدام پیشنهادی:** این سینک عمومی تا طراحی دوباره نباید در محیط تولید فعال شود. منطق جدید باید allowlist دقیق schema/table و جهت synchronization داشته باشد و عملیات اتمیک، idempotent و بازیابی‌پذیر ارائه کند؛ حذف داده نباید از طریق پاک‌کردن سراسری جدول به‌صورت ضمنی انجام شود.

### ۱۶.۲. موارد امنیتی و قابلیت اطمینان دیگر

- اتصال‌های MySQL مستقیم در C# با `SslMode=none` ساخته می‌شوند. هرگز این تنظیم را برای انتقال credential یا داده روی شبکه غیرقابل‌اعتماد استفاده نکنیم؛ البته مسیر مستقیم 3306 فعلاً انتخاب نشده است.
- در `AgentService` برای نبودن `AgentSecret` مقدار پیش‌فرض hard-coded وجود دارد. رفتار درست fail-closed است: اگر secret تنظیم نشده، قابلیت وابسته شروع نشود؛ credential مشترک پیش‌فرض نباید وجود داشته باشد.
- فایل `agentsettings.json` حاوی تنظیمات و احتمالاً passwordهاست و به صورت JSON عادی ذخیره می‌شود. در Linux باید دسترسی فایل به حساب سرویس محدود شود و secretها تا حد ممکن از تنظیمات قابل‌commit جدا باشند.
- `sync_bulk.php` کلیدهای ردیف و حجم/تعداد ردیف‌ها را به‌اندازه کافی به schema و سقف payload محدود نمی‌کند و متن exception را در پاسخ 500 برمی‌گرداند. پاسخ عمومی باید پیام بی‌خطر داشته باشد و جزئیات فقط در لاگ داخلی محافظت‌شده ثبت شوند.
- heartbeat بخشی از هدرهای proxy برای IP را از درخواست می‌خواند؛ IPهای forwarded نباید بدون پیکربندی اعتماد به proxy معتبر تلقی شوند.
- `fetch_tasks.php` در نسخه دیده‌شده، به جای دریافت واقعی وظایف، آرایه خالی برمی‌گرداند. این قابلیت هنوز کامل نیست.
- خواندن کل جدول در حافظه و درج ردیف‌به‌ردیف در سینک فعلی برای جدول‌های بزرگ می‌تواند RAM/زمان را افزایش دهد؛ batching محدود و cursor لازم است.
- مسیرهای خطا و catchهای خالی در چند متد مشاهده شده‌اند؛ خطاهای authentication، شبکه و synchronization باید تفکیک، ثبت و برای retry با backoff مدیریت شوند.

### ۱۶.۳. ترتیب پیشنهادی اصلاحات

1. غیرفعال نگه‌داشتن سینک مستقیم عمومی و جلوگیری از هر اجرا روی دیتابیس تولیدی تا بازطراحی.
2. مدیریت امن و چرخاندن هماهنگ credentialهایی که در سورس قرار گرفته‌اند.
3. اصلاح PHP syntax و طراحی یک authentication flow یکنواخت با token مستقل برای هر نود، scope محدود، expiry و revocation.
4. تکمیل endpointهای sync و اعتبارسنجی دقیق جدول، ستون، نوع داده، اندازهٔ payload، node identity و مجوز هر endpoint.
5. تعریف جهت و معناشناسی sync برای هر پلاگین: push/pull، upsert، حذف رکورد، هم‌زمانی، retry و بازیابی.
6. ساخت Worker مخصوص Linux و اجرای آن با systemd و حساب غیر root؛ پس از آن تست‌های unit/integration و تست fault/retry روی دیتابیس آزمایشی.
7. اجرای بازبینی امنیتی دوباره پس از اصلاح و تنها سپس استفاده محدود در تولید.

**نتیجه ممیزی اولیه:** بله، این سیستم قابل اصلاح است و نیازی به بازنویسی کامل C# از صفر ندارد؛ اما نسخه موجود را نباید بدون اصلاح authentication، مدیریت secret و منطق مخرب/ناامن sync روی دیتابیس واقعی فعال کرد.

- پشتیبانی مشتری و صورت‌حساب‌ها.

### ۱۷.۳. دسته دوم: فروشگاه، حساب مشتری و صورتحساب

#### گزینه A — Paymenter

- مخزن: https://github.com/Paymenter/Paymenter
- مستندات: https://paymenter.org/docs/
- محصولات: https://paymenter.org/docs/guides/products/
- تیکت پشتیبانی: https://paymenter.org/docs/guides/tickets/

Paymenter یک پلتفرم متن‌باز صورتحساب/فروش برای شرکت‌های میزبانی است و امکانات مشتری، محصول، پلن، صورتحساب و تیکت پشتیبانی را فراهم می‌کند. اتصال Pterodactyl در مستندات رسمی آن از API پنل استفاده می‌کند و تنظیمات محصول شامل مواردی مانند Egg، نود/Location، RAM، CPU، Disk، پورت‌ها، Backup و Database است. این موضوع می‌تواند بخش زیادی از فروش و Provisioning instance را بدون Instance Maker اختصاصی پوشش دهد.

**محدودیت تعیین‌کننده برای FragCity:** محصولات معمول Paymenter از نوع رایگان، یک‌باره یا دوره‌ای با فاصله زمانی روز/هفته/ماه/سال تعریف می‌شوند. این به‌تنهایی معادل مدل احتمالی FragCity یعنی کیف پول و کم‌کردن موجودی بر اساس دقیقه/ساعت مصرف سرور نیست. قبل از انتخاب، باید مدل دقیق شارژ و تمدید مشخص شود؛ ممکن است برای usage metering و مصرف اعتبار، یک ماژول کسب‌وکار اختصاصی لازم باشد.

**محدودیت زیرساخت:** مستندات نصب فعلی Paymenter، PHP 8.3 یا جدیدتر، Composer، وب‌سرور و MariaDB را فهرست می‌کنند؛ همچنین راهنمای نصب cron-job و یک queue worker دائمی با systemd و Redis را نشان می‌دهد. بنابراین امکان میزبانی امن و کامل روی هاست اشتراکی cPanel را نباید قطعی فرض کرد. حتی اگر PHP/MariaDB و Cron در cPanel موجود باشند، ممکن است queue worker دائمی یا سایر قابلیت‌های عملیاتی مورد نیاز در دسترس نباشند.

**ارزیابی اولیه:** نامزد اول برای فروشگاه/حساب مشتری، مشروط به اینکه مدل کیف پول/صورتحساب ساعتی و درگاه پرداخت واقعی FragCity با آن منطبق یا از طریق extension قابل اضافه‌شدن باشند. احتمالاً باید آن را روی VPS/محیطی با کنترل کامل سرویس‌های پس‌زمینه اجرا و سایت فعلی را ابتدا به‌عنوان بخش معرفی نگه داشت.

FOSSBilling هم یک سیستم متن‌باز مدیریت مشتری، صورتحساب، پرداخت، ارتباط و افزونه‌های میزبانی است و مجوز Apache-2.0 دارد. اما README رسمی فعلی پروژه صریحاً آن را در حال توسعه فعال و در وضعیت beta توصیف می‌کند. ماژول Pterodactyl که در این تحقیق یافت شد، یک افزونه جامعه‌ای جداگانه است، نه یک integration رسمی هم‌سطح Paymenter؛ تعداد ستاره‌ها یا فعالیت پروژه به‌تنهایی کافی نیست، اما سازگاری نسخه و مسیر نگهداری آن باید جداگانه بررسی شود.

**ارزیابی اولیه:** گزینه مقایسه‌ای برای صورتحساب؛ پایین‌تر از Paymenter در اولویت فعلی، مگر آنکه امکانات یا سازگاری با درگاه محلی بهتری در تست عملی پیدا شود.

### ۱۷.۴. وب‌سایت FragCity و تجربه کاربر

پیشنهاد این نیست که فوراً سایت PHP موجود را پاک یا با یک frontend جدید دوباره بازنویسی کنیم. ابتدا باید تفکیک مسئولیت برقرار شود:

1. **صفحات عمومی و برند FragCity:** معرفی سرورها، ویژگی‌ها، قیمت‌ها و راهنماها. در فاز انتقال می‌تواند روی هاست فعلی بماند.
2. **فروشگاه و پنل مشتری:** محصول، پرداخت، سفارش، صورتحساب و تیکت در یک سامانه مشخص مثل Paymenter.
3. **پنل مدیریت سرور مشتری:** توسط Pterodactyl یا GameAP فراهم شود.
4. **یکپارچگی:** لینک‌های HTTPS و APIهای مستند بین اجزا. ورود یکپارچه (SSO) در مرحله مناسب اضافه شود، نه اینکه در شروع دو سیستم احراز هویت پیچیده و موازی بسازیم.

این تقسیم‌بندی امکان مهاجرت مرحله‌ای را می‌دهد و از بازنویسی رابط کاربری قبل از انتخاب هسته صورتحساب/Provisioning جلوگیری می‌کند.

### ۱۷.۵. درگاه پرداخت، کیف پول و صورتحساب مصرفی

درگاه پرداخت محلی تا زمانی که نام ارائه‌دهنده و مستندات API آن مشخص نشود، انتخاب‌شده محسوب نمی‌شود. برای هر درگاه باید این موارد بررسی شوند:

- صفحه/فرایند checkout و بازگشت امن از درگاه.
- اعتبارسنجی server-to-server نتیجه پرداخت؛ اعتماد صرف به redirect مرورگر کافی نیست.
- idempotency در callback تا callback تکراری باعث دوبار شارژشدن موجودی نشود.
- ثبت immutable ledger برای شارژ و مصرف اعتبار به‌جای تغییر مبهم یک عدد balance.
- تطابق واحد پول، مبلغ، کارمزد، refund/لغو و وضعیت تراکنش.
- حفاظت از secret درگاه و محیط آزمایشی جدا.

قبل از پیاده‌سازی باید تعریف شود مصرف مشتری به معنی کدام حالت است: زمان روشن‌بودن process، زمان سرور فعال/قابل اتصال، یا زمان رزروشده طبق پلن. همچنین سیاست اعتبار منفی، تمدید، توقف خودکار، restart، قطع نود، اختلاف ساعت و بازگشت وجه باید مشخص شود. این موارد منطق تجاری‌اند و پنل مدیریت سرور به‌تنهایی آن‌ها را حل نمی‌کند.

### ۱۷.۶. دیتابیس و API در معماری جدید

**پورت 3306 دیتابیس سایت از بیرون هاست اشتراکی قابل استفاده نیست.** پس مسیر پیشنهادی برای API در این شرایط چنین است:

- دیتابیس مربوط به فروشگاه/سایت فقط از برنامه‌ای که مجاز به اتصال به آن است قابل دسترسی باشد.
- نود Debian به endpointهای HTTPS درخواست بفرستد؛ PHP همان endpoint به MariaDB محلی روی هاست دسترسی دارد.
- APIها برای هر عملیات قرارداد روشن داشته باشند؛ مثال: ثبت heartbeat، ارسال batch از آمار مشخص، به‌روزرسانی وضعیت سرویس، ثبت مصرف یا دریافت وظیفه.
- از «کپی‌کردن همه دیتابیس‌ها و جدول‌های هم‌نام» اجتناب شود. هر مجموعه داده باید منبع حقیقت، جهت انتقال، کلید یکتا و سیاست حذف مشخص داشته باشد.
- وقتی پنل بازی یا Billing مالک یک بخش از داده‌هاست، اطلاعات همان بخش از API رسمی آن منبع خوانده شود، نه از جدول‌های داخلی برنامه به روش وابسته به schema.
- برای همگام‌سازی پلاگین‌هایی که دیتابیس محلی دارند، API باید whitelist جدول/ستون، سقف payload، هویت نود، محدودیت نرخ، احراز هویت و عملیات retry امن داشته باشد.

**نتیجه:** C# فعلی نباید به‌عنوان replication عمومی دیتابیس حفظ شود. ابتدا بررسی می‌کنیم آیا Provisioning و کنترل instance کاملاً به پنل منتخب سپرده می‌شوند؛ سپس تنها برای کارهایی که محصول‌های آماده پوشش نمی‌دهند، Worker یا adapter سبک و محدود می‌سازیم. احتمالاً برای مصرف ساعتی و ارسال داده‌های پلاگین، یک جزء اختصاصی محدود باقی می‌ماند؛ برای RCON و ساخت عمومی سرور نباید بدون دلیل دوباره ابزار مستقل ایجاد کنیم.

### ۱۷.۷. پایش و قابلیت اطمینان

گزینه‌های آماده برای مرحله رشد:
- Prometheus Node Exporter: https://github.com/prometheus/node_exporter — گردآوری شاخص‌های سیستم Linux.
- Grafana: https://github.com/grafana/grafana — داشبورد، همبستگی شاخص‌ها و alerting؛ مجوز پیش‌فرض مخزن AGPL-3.0-only است و جزئیات مجوز پوشه‌ها باید رعایت شود.
- Uptime Kuma: https://github.com/louislam/uptime-kuma — بررسی availability سرویس‌ها و endpointها به شکلی ساده‌تر.

در شروع می‌توان از سلامت و metrics پنل منتخب استفاده کرد؛ پس از اضافه‌شدن نودها، Prometheus/Grafana برای CPU، RAM، disk، شبکه، مصرف سرورها، شکست sync و latency endpointها ارزیابی شود. مانیتورینگ جایگزین Backup و آزمایش بازیابی نیست.

### ۱۷.۹. پیشنهاد فعلی، بدون نهایی‌کردن انتخاب

**مقایسه‌ای که باید اول اجرا شود:**

- **مسیر A:** Paymenter + Pterodactyl/Wings؛ برای بررسی کمترین effort چون integration مستقیم رسمی میان Paymenter و Pterodactyl وجود دارد.
- **مسیر B:** GameAP + یک لایه صورتحساب؛ برای بررسی انعطاف API و SSO و اینکه آیا مدیریت چندنودی را با کدنویسی کمتر از مسیر A پوشش می‌دهد.
- **مسیر C:** OVHcloud Game Panel فقط به‌عنوان benchmark رابط/مدیریت CS2، نه انتخاب تجاری پیش‌فرض.
- **Pelican:** فقط اگر مزیت UI/عملی آن در تست روشن باشد و سازگاری integrationها و پیامد مجوز AGPL برای FragCity پذیرفته شود.

قبل از خرید یا مهاجرت، برای مسیر A و B در محیط آزمایشی این تست‌ها انجام شود:

1. نصب یک سرور تمیز CS2 با SteamCMD و فایل‌های لازم.
2. تخصیص خودکار IP/port، RAM، CPU و disk.
3. ایجاد سرور از API پس از پرداخت آزمایشی یا سفارش ساختگی؛ هنوز هیچ پرداخت واقعی انجام نشود.
4. کنسول، فایل‌ها، restart، stop، delete، Backup و Restore.
5. دو نود آزمایشی یا دست‌کم دو allocation/محدوده پورت مستقل، سپس اضافه‌کردن نود جدید فقط با تنظیمات.
6. توقف یا crash نود، timeout API، callback تکراری پرداخت، retry، جلوگیری از ساخت duplicate instance و reconciliation بعد از برگشت سرویس.
7. محاسبه اعتبار و مصرف دقیقه‌ای در تست مستقل، با ثبت دفتر تراکنش قابل ممیزی.
8. بررسی اینکه همه پورت‌های لازم برای بازی/مدیریت در firewall نودها باز و فقط endpointهای لازم از اینترنت قابل دسترسی باشند.

**نکته شبکه:** پورت‌های 21/80/443 هاست cPanel فقط درباره همان میزبان‌اند. سرورهای CS2 و پنل کنترل روی نود خودشان به پورت‌های مورد نیازشان نیاز خواهند داشت؛ ترافیک بازی (معمولاً UDP) با HTTPS سایت یکی نیست و باید جداگانه طراحی شود.

### ۱۷.۱۰. جمع‌بندی

از اینجا به بعد نباید Instance Maker یا RCON کنونی نقطه شروع خودکار توسعه باشند. آن‌ها را به‌عنوان نمونه‌ای از نیازهای اولیه نگه می‌داریم و ابتدا محصولات آماده را با معیارهای عملیاتی، امنیت، API، billing، هزینه نگهداری و مجوز مقایسه می‌کنیم.

**اولویت تحقیق بعدی:** یک PoC کوچک و قابل حذف برای **Pterodactyl + Paymenter** و یک PoC جدا برای **GameAP** طراحی شود؛ هیچ‌کدام فعلاً روی سرور تولیدی یا در ریپوی `cs2-kus-addons` نصب/اجرا نشوند. پس از نتیجه واقعی PoC، انتخاب قطعی و نقشه مهاجرت تدوین می‌شود.

## ۱۸. ماتریس تصمیم و آزمون PoC برای انتخاب پلتفرم FragCity

**تاریخ بازبینی نسخه‌ها:** ۱۶ اکتبر ۲۰۲۶  
**وضعیت:** پیشنهاد معماری و برنامهٔ آزمون ثبت شده؛ انتخاب نهایی مشروط به نتایج PoC است. هیچ محصولی در محیط تولید نصب یا جایگزین نشده است.

### ۱۸.۱. نظر فعلی و انتخاب پیشنهادی

**پیشنهاد فعلی برای PoC اول: Pterodactyl Panel + Wings + Paymenter.**

دلایل:
- Paymenter اتصال رسمی Pterodactyl دارد و از طریق API می‌تواند محصول را به سرور بازی متصل کند. تنظیمات محصول شامل Egg، Location، Node، port allocations، Backup، CPU، RAM، Disk و Server Name است؛ این دقیقاً بخش بزرگی از نیاز فعلی FragCity را پوشش می‌دهد.
- برای ساخت و کنترل instance نباید یک Instance Maker اختصاصی دیگر بسازیم، مگر اینکه پس از آزمایش قابلیت لازم در پنل منتخب وجود نداشته باشد.
- برای کنسول و عملیات سرور نیز API و قابلیت‌های پنل را باید مقدم بر پیاده‌سازی مستقل RCON قرار دهیم.
- Paymenter بخش قابل توجهی از فروش، سفارش، حساب مشتری، صورتحساب و پشتیبانی را پوشش می‌دهد.

من این انتخاب را به‌عنوان **مسیر مرجع آزمون** پیشنهاد می‌کنم؛ نه به‌عنوان حکم نهایی بدون آزمایش. نقطهٔ ضعف کلیدی آن در مدل FragCity، مصرف اعتبار/کیف پول بر اساس دقیقه یا ساعت است. صورتحساب دوره‌ای مرسوم لزوماً متر مصرف زنده را جایگزین نمی‌کند؛ احتمالاً یک extension کوچک اما با دقت مالی بالا نیاز خواهد بود.

### ۱۸.۵. معیار امتیاز نهایی و تصمیم

پس از PoC، برای هر مسیر همین وزن‌ها اعمال می‌شود و امتیاز بر اساس شواهد ثبت‌شده تغییر می‌کند. بااین‌حال، امتیاز کلی بالا نمی‌تواند یک شکست امنیتی یا مالی را جبران کند.

**شرط ورود به پایلوت با مشتری واقعی:**
- همه آزمون‌های مسدودکننده پاس شده باشند.
- نسخهٔ منتخب و تمام dependencyهای مهم بررسی و patch شده باشند.
- Backup/Restore واقعی تست شده باشد.
- سرور مشتری‌ها از نظر داده، فایل، کنسول، پورت و API از هم جداسازی شده باشند.
- نحوه کسر اعتبار، جلوگیری از کسر/پرداخت تکراری و سیاست توقف پس از اتمام اعتبار روشن و تست شده باشد.
- راهنمای عملیات، مانیتورینگ، هشدار و rollback وجود داشته باشد.

**قانون توقف:** هرگونه دسترسی بین مشتری‌ها، اختلاف مالی غیرقابل‌توضیح، از بین رفتن داده، ایجاد instance تکراری کنترل‌نشده یا آسیب‌پذیری بحرانی بدون patch به معنی توقف پایلوت است، حتی اگر سایر آزمون‌ها موفق باشند.

### ۱۸.۶. برنامه اجرای آزمون‌ها

1. **آزمون کاغذی و انتخاب نسخه:** بررسی releaseها، مجوزها، advisoryها و نیازهای نصب؛ تثبیت دقیق نسخهٔ Panel/Wings/Paymenter.
2. **PoC مسیر A:** Paymenter + Pterodactyl روی محیط آزمایشی جدا؛ ایجاد یک سرور CS2، کنترل چرخه عمر و اتصال API.
3. **آزمون billing:** بدون پرداخت واقعی، مدل اعتبار ساعتی و reconciliation را با داده ساختگی امتحان کنیم. اگر این بخش به extension بزرگ یا تغییرات خطرناک core نیاز داشت، آن کار را اندازه بگیریم، نه اینکه از قبل فرض کنیم ساده است.
4. **PoC مسیر B محدود:** فقط در صورتی اجرا شود که مسیر A مانع اساسی داشته باشد یا GameAP بتواند با توسعه کمتر همان نتیجه را بدهد. هدف بازسازی هم‌زمان همه سامانه‌ها نیست.
5. **انتخاب با شواهد:** به ماتریس امتیاز و شرایط مسدودکننده برگردیم؛ سپس تصمیم نهایی، نقشه مهاجرت و مسئولیت هر محصول را مشخص کنیم.

### ۱۸.۷. مرز مسئولیت اجزا در معماری پیشنهادی

- **Paymenter:** سفارش، مشتری، محصول، صورتحساب و جریان فروش؛ نه اجرای مستقیم فرایند سیستم‌عامل.
- **Pterodactyl Panel/Wings:** ساخت و مدیریت instance، منابع، فایل‌ها، کنسول و عملیات سرور.
- **FragCity custom extension/service:** فقط شکاف‌های واقعی مثل متریک مصرف دقیقه‌ای، ledger کیف پول یا قواعد تجاری مختص محصول، پس از اثبات نیاز.
- **PHP API فعلی:** در فاز انتقال به‌صورت محدود نگه داشته شود تا مدل داده و احراز هویت آن بازبینی شود. نباید کل دیتابیس را کورکورانه بین نود و سایت کپی کند.
- **نودها:** Linux و سرویس مدیریت instance؛ credentialها، secretها، محدوده پورت و ظرفیت مستقل هر نود.
- **هاست cPanel فعلی:** فعلاً وب‌سایت موجود و دیتابیس خودش؛ تا زمان بررسی شرایط عملیاتی، محل فرضی Panel/Wings/Worker دائمی یا queue worker نیست.

### ۱۸.۸. تصمیم پیشنهادی در یک جمله

**مسیر A — Paymenter + Pterodactyl/Wings را به‌عنوان مرجع آزمون انتخاب کن؛ از نسخهٔ پایدار patched استفاده کن، billing ساعتی را شرط مسدودکننده بدان، و GameAP را فعلاً فقط مسیر پشتیبان مقایسه‌ای نگه دار.** این کار بیشترین احتمال را دارد که توسعه تکراری فعلی (Instance Maker، مدیریت کنسول و بخشی از API) کاهش پیدا کند و کد اختصاصی فقط در منطق تجاری واقعی FragCity باقی بماند.

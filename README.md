# FragCity — مستند پایه معماری و مسیر توسعه

> **وضعیت سند:** پارت ۱ — تصمیم‌های پایه معماری و زیرساخت  
> **هدف:** ثبت تصمیم‌های فعلی پیش از ورود به طراحی جزئیات، انتخاب نهایی فناوری‌ها و پیاده‌سازی. این سند در پارت‌های بعدی تکمیل می‌شود؛ تصمیم‌های باز نباید بدون بررسی به‌عنوان تصمیم قطعی در نظر گرفته شوند.

## ۱. چشم‌انداز

FragCity قرار است بستری برای معرفی، مدیریت و در آینده ارائه سرورهای بازی CS2 به مشتریان باشد. معماری باید از همان ابتدا ماژولار طراحی شود تا بتوان با یک سیستم شروع کرد و سپس با اضافه‌شدن دو، چهار یا تعداد بیشتری سیستم فیزیکی، ظرفیت را افزایش داد؛ بدون آنکه برای هر سیستم جدید مجبور به بازنویسی سایت یا ساخت منطق اختصاصی جدید شویم.

**اصل کلیدی:** افزودن یک نود جدید باید عمدتاً از طریق یک فرایند نصب تکرارپذیر و تنظیمات همان نود انجام شود، نه با تغییر کد اصلی سایت.

این موضوع به معنی «فقط کپی‌کردن یک فایل و تمام‌شدن خودکار راه‌اندازی» نیست؛ ابزارهای نصب، ثبت نود، بررسی سلامت و تنظیمات استاندارد نیز باید یک‌بار طراحی شوند تا راه‌اندازی سیستم‌های بعدی از همان الگو پیروی کند.

## ۲. تصمیم‌های پایه این پارت

- **ویندوز میزبان فعلی** برای تست، توسعه و اجرای سرورهای موقتی خودمان باقی می‌ماند.
- **سرورهای مشتریان** روی لینوکس اجرا می‌شوند؛ در شروع، لینوکس داخل ماشین مجازی VMware روی سیستم فعلی اجرا خواهد شد.
- **Pterodactyl** گزینه اصلی مدیریت سرورهای مشتریان است؛ به‌جای بازسازی تمام قابلیت‌های مدیریت سرور در برنامه C#، از پنل و سرویس نود آن استفاده می‌کنیم.
- یک **Pterodactyl Panel مرکزی** می‌تواند چندین نود را مدیریت کند. روی هر نود لینوکسی، Wings سرورهای بازی را با Docker اجرا و مدیریت می‌کند.
- سایت FragCity و زیرساخت اجرای سرورها مسئولیت‌های جدا دارند. سایت نباید خودش مستقیماً فرایندهای سیستم‌عامل را برای اجرای سرورهای مشتری مدیریت کند.
- ریپوی موجود larnzs/cs2-kus-addons زیرساخت فعلی افزونه‌ها و کانفیگ‌های CS2 باقی می‌ماند. در این پارت نیازی به تغییر آن نیست.
- تعداد سرورها و منابع اختصاص‌یافته، بر اساس اندازه‌گیری واقعی و آزمایش مرحله‌ای تعیین می‌شود؛ نه صرفاً بر اساس برآورد اولیه رم.

## ۳. معماری منطقی پیشنهادی

~~~text
بازیکنان
   │
   ├── اتصال مستقیم به IP و پورت سرور بازی
   │
   ▼
سرورهای CS2 در نودهای لینوکسی
   ▲
   │ مدیریت اجرا، توقف، فایل‌ها و منابع
   │
Pterodactyl Wings + Docker (روی هر نود)
   ▲
   │ ارتباط مدیریتی
   │
Pterodactyl Panel (پنل مرکزی)
   ▲
   │ API و یکپارچه‌سازی کنترل‌شده
   │
هسته FragCity / وب‌سایت
   ├── کاربران و دسترسی‌ها
   ├── مالکیت سرورها و پلن‌ها
   └── سفارش‌ها و منطق کسب‌وکار (در پارت‌های بعدی طراحی می‌شود)
~~~

این نمودار مرز مسئولیت‌ها را مشخص می‌کند، نه پیاده‌سازی نهایی تمام سرویس‌ها.

### تفکیک مسئولیت‌ها

**سایت و هسته FragCity**
- مدیریت کاربران، مالکیت و ارتباط سرور با مشتری.
- نگهداری منطق کسب‌وکار و ارائه API برای رابط کاربری و بخش‌های دیگر.
- ارتباط با سامانه مدیریت سرورها از طریق رابط‌های مشخص؛ نه اجرای مستقیم فرایندهای سیستم‌عامل.

**Pterodactyl Panel**
- مدیریت نودها، سرورها و عملیات مدیریتی از طریق یک نقطه مرکزی.
- ارائه API برای یکپارچه‌سازی با FragCity.

**Wings و Docker**
- اجرا و مدیریت سرورهای بازی روی نود لینوکسی.
- کمک به جداسازی محیط هر سرور و اعمال محدودیت‌های RAM و CPU.

**سرور CS2**
- بازیکنان مستقیماً به پورت بازی متصل می‌شوند؛ پنل وب مسیر عبور ترافیک بازی نیست.
- افزونه‌ها و کانفیگ‌های فعلی KUS تا وقتی نیاز مشخصی برای تغییر وجود ندارد، حفظ می‌شوند.

مستندات رسمی:
- [معماری Pterodactyl و ارتباط Panel/Wings](https://docs.pterodactyl.io/v1/project/how-it-works)
- [نصب Wings و سیستم‌عامل‌های پشتیبانی‌شده](https://docs.pterodactyl.io/v1/wings/installing)
- [محدودیت منابع CPU و RAM در Docker](https://docs.docker.com/engine/containers/resource_constraints/)

## ۴. ماژولار بودن و اضافه‌کردن سیستم‌های فیزیکی جدید

معماری باید از ابتدا مفهوم **نود (Node)** را مستقل از یک کامپیوتر مشخص بشناسد. یک نود یعنی ماشینی که سرویس اجرای سرورها روی آن نصب و مدیریت می‌شود؛ ممکن است در شروع یک ماشین مجازی باشد و در آینده یک سیستم فیزیکی مستقل.

### الگوی توسعه نودها

1. سایت و هسته FragCity نباید به IP، مسیر نصب یا پورت ثابت یک سیستم خاص وابسته باشند.
2. هر نود باید شناسه، نام، وضعیت، آدرس‌های شبکه و ظرفیت خودش را داشته باشد.
3. نصب وابستگی‌ها و سرویس‌های لازم باید به‌صورت خودکار و تکرارپذیر انجام شود.
4. اطلاعات مختص هر نود از تنظیمات همان نود خوانده شود؛ منطق عمومی در اسکریپت‌ها یا کد اصلی مشترک بماند.
5. اضافه‌کردن یک نود جدید نباید نیازمند تغییرات اختصاصی در کد سمت سایت باشد؛ سایت باید بتواند نود جدید را از مسیر استاندارد شناسایی و مدیریت کند.
6. ظرفیت هر نود باید مستقل قابل تنظیم باشد تا با سخت‌افزار متفاوت، محدودیت منابع متفاوت تعریف شود.
7. خرابی یا آفلاین‌شدن یک نود نباید باعث از دست‌رفتن اطلاعات مالکیت، سفارش یا مشخصات سرورهای سایر نودها شود.
8. عملیات نصب و به‌روزرسانی باید تا حد ممکن تکرارپذیر و قابل بررسی باشند و اطلاعات حساس را در خروجی عمومی یا مخزن کد قرار ندهند.

### طرح تنظیمات

در زمان پیاده‌سازی، تنظیمات را به دو سطح جدا می‌کنیم:

- **تنظیمات عمومی محیط:** آدرس سرویس‌های مرکزی و تنظیمات مشترک محیط.
- **تنظیمات هر نود:** شناسه و نام نود، آدرس‌های شبکه، محدوده پورت‌های اختصاص‌یافته، محدودیت منابع، برچسب‌ها و ظرفیت هدف.

توکن‌ها، رمزها، کلیدهای API و سایر اطلاعات محرمانه باید خارج از تنظیمات قابل انتشار و خارج از Git نگهداری شوند. فایل تنظیمات Wings نیز باید با روش معتبر خود Pterodactyl تولید و مدیریت شود؛ قرار نیست اطلاعات محرمانه پنل را داخل README یا کد سمت مرورگر قرار دهیم.

**هدف نهایی این بخش:** خرید سیستم جدید باید به معنی اجرای همان فرایند استاندارد نصب، واردکردن تنظیمات مخصوص نود، ثبت آن در پنل مرکزی و بررسی سلامت باشد؛ نه ساخت نسخه‌ای جداگانه از FragCity برای هر کامپیوتر.

## ۵. سخت‌افزار فعلی و ظرفیت شروع

### مشخصات فعلی

| بخش | وضعیت |
|---|---|
| پردازنده | AMD Ryzen 5 8400F، دارای ۶ هسته و ۱۲ رشته |
| رم | ۱۶ گیگابایت DDR5 با سرعت ۵۶۰۰ مگاهرتز |
| میزبان فعلی | Windows |
| نود اولیه مشتریان | ماشین مجازی Linux روی VMware |
| اتصال اینترنت | IP ثابت، اینترنت و Port Forwarding در دسترس هستند |
| سرور و افزونه‌ها | سرورهای فعلی KUS روی ویندوز تست شده‌اند؛ مسیر لینوکسی نیز طبق تست‌های انجام‌شده کار می‌کند |

### رویکرد ظرفیت

- **هدف اولیه:** رسیدن به ۵ سرور پایدار.
- پس از اندازه‌گیری، ظرفیت را مرحله‌ای افزایش می‌دهیم.
- **۸ تا ۱۰ سرور هدف کششی است، نه تضمین فعلی.** امکان اجرای هم‌زمان به گیم‌مود، مپ، تعداد بازیکن، افزونه‌ها، مصرف واقعی RAM، بار CPU و منابعی که برای ویندوز و خود VM مصرف می‌شوند بستگی دارد.

برآورد ۵۰۰ مگابایت تا ۱ گیگابایت رم به‌ازای هر سرور، صرفاً تخمین شروع است. باید مصرف واقعی در حالت خالی و در زمان بازی اندازه‌گیری شود.

### برنامه سنجش

ظرفیت را مرحله‌ای و با ثبت داده بررسی می‌کنیم:

1. اجرای یک سرور و ثبت مصرف پایه.
2. اجرای سه سرور و بررسی مصرف RAM، CPU و پایداری.
3. اجرای پنج سرور و آزمایش با بار نزدیک به استفاده واقعی.
4. فقط در صورت وجود حاشیه کافی، افزایش تعداد سرورها.

هنگام این تست‌ها باید مصرف خود ویندوز، حافظه اختصاص‌یافته به VM، سیستم لینوکس، Docker و سرویس‌های مدیریتی نیز محاسبه شود. پرشدن RAM یا فشار بیش از حد CPU می‌تواند باعث افت کیفیت یا ناپایداری شود؛ بنابراین محدودیت منابع باید واقعی و متناسب با نود تنظیم شود.

## ۶. لینوکس و امنیت پایه

هدف، استفاده از سیستم‌عاملی سبک و بدون محیط گرافیکی است تا منابع اضافه صرف سرویس‌های غیرضروری نشود.

- **انتخاب اولیه برای آزمایش: Debian Minimal.** نسخه دقیق نهایی پس از نصب آزمایشی و تأیید سازگاری Pterodactyl، Docker، سرور CS2 و افزونه‌ها تثبیت می‌شود. مستندات فعلی Pterodactyl نسخه‌های Debian 12 و 13 را برای نصب Panel و نسخه‌های 11 تا 13 را برای Wings فهرست کرده‌اند.
- نودهای مشتریان باید از طریق Docker و محدودیت‌های منابع مدیریت شوند؛ کانتینر به‌تنهایی تضمین امنیت کامل نیست.
- سرویس‌های مدیریتی و پورت‌های بازی باید جداگانه برنامه‌ریزی شوند.
- دسترسی مدیریتی غیرضروری نباید بی‌دلیل در اینترنت عمومی باز باشد.
- روش تهیه نسخه پشتیبان، ثبت رویدادها، به‌روزرسانی امن و بازیابی پس از خرابی در پارت‌های بعدی مشخص خواهد شد.

## ۷. شبکه و پورت‌ها

IP ثابت، اینترنت و Port Forwarding فعلی در دسترس هستند. برای نود لینوکسی داخل VMware، حالت **Bridged** گزینه اولیه برای آزمایش است تا VM در شبکه محلی آدرس مستقل داشته باشد و مسیر هدایت پورت‌ها ساده‌تر شود.

در طراحی نهایی باید این موارد مستقل از کد سایت و برای هر نود قابل تنظیم باشند:
- آدرس مدیریتی نود و آدرس قابل دسترسی بازیکنان.
- محدوده پورت‌های اختصاص‌یافته به سرورهای بازی.
- پورت‌ها و مسیرهای ارتباطی مورد نیاز Panel و Wings.
- قوانین فایروال و دسترسی‌های مدیریتی.

جزئیات واقعی آدرس‌دهی و تخصیص پورت در مرحله نصب نود و تست شبکه تعیین می‌شوند؛ این README جایگزین تنظیمات اجرایی نیست.

## ۸. حفظ زیرساخت فعلی KUS

ریپوی larnzs/cs2-kus-addons و کانفیگ‌های فعلی، زیرساخت بازی موجود هستند و در این مرحله تغییر نمی‌کنند.

هنگام پیاده‌سازی باید:
- نصب و اجرای سرور روی Linux با ساختار نودهای Pterodactyl هماهنگ شود.
- روش به‌روزرسانی افزونه‌ها و فایل‌های بازی تا حد ممکن با فرایند فعلی سازگار بماند.
- فایل‌های شخصی، کانفیگ‌ها و تنظیمات موجود بدون نیاز مشخص و بررسی اثر تغییر، حذف یا بازنویسی نشوند.
- تست Windows و Linux به‌عنوان دو محیط جدا در نظر گرفته شود؛ تأیید یک محیط به‌تنهایی جایگزین تست محیط دیگر نیست.

## ۹. مواردی که در پارت ۱ هنوز تعیین تکلیف نشده‌اند

این موارد عمداً باز می‌مانند تا قبل از تصمیم‌گیری، معماری موجود و گزینه‌ها به‌صورت جداگانه بررسی شوند:

- انتخاب نهایی فناوری هسته وب و نحوه توسعه یا نوسازی بخش PHP.
- نقش آینده برنامه C# و اینکه کدام مسئولیت‌ها باید حذف، حفظ یا به API منتقل شوند.
- مدل دقیق اتصال سایت به Pterodactyl و اینکه کدام عملیات از رابط اختصاصی FragCity انجام شوند.
- مدل داده و مرجع اصلی اطلاعات کاربران، سفارش‌ها، مالکیت سرورها و وضعیت اجرای آن‌ها.
- سیاست بکاپ، مانیتورینگ، به‌روزرسانی و بازیابی.
- نحوه مهاجرت از پیاده‌سازی موجود، بدون قطع سرویس یا از دست‌رفتن کانفیگ‌ها.
- ظرفیت نهایی سرورها برای سخت‌افزار فعلی و معیارهای لازم برای اضافه‌کردن نود جدید.

## ۱۰. خروجی مورد انتظار پارت ۱

در پایان این پارت، تصمیم پایه این است:

> FragCity به‌صورت یک سامانه مرکزی و ماژولار ساخته می‌شود که مدیریت کسب‌وکار را از اجرای سرورهای بازی جدا نگه می‌دارد. ویندوز فعلی برای تست و سرورهای موقت باقی می‌ماند؛ سرورهای مشتریان از طریق نودهای لینوکسی و Pterodactyl مدیریت می‌شوند. معماری از روز اول برای چند نود طراحی خواهد شد، به‌طوری که افزودن سیستم‌های فیزیکی جدید از فرایند نصب استاندارد و تنظیمات اختصاصی نود پیروی کند، نه از تغییر کد اصلی سایت.

**پارت بعدی:** بررسی معماری سایت و هسته FragCity، ارتباط با Pterodactyl و تعیین نقش واقعی برنامه C#؛ بدون شروع بازنویسی یا تغییر ریپوها تا زمانی که تصمیم‌ها مستند و روشن شوند.
